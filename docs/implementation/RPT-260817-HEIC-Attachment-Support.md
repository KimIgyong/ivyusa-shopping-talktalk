## 1. 결론

**구현·스테이징 배포·스모크 완료.** 아이폰 사진(HEIC)이 위젯·콘솔·외부 메신저 세 경로 모두에서
정상 첨부되고, 서버에서 JPEG로 변환되어 모든 브라우저에서 열린다. 배포된 컨테이너에서
12MP 실측 **1.0~1.2초/장**, EXIF 제거 확인.

가장 중요한 검증은 **S-3**: 12MP HEIC 5장을 동시 업로드하는 동안 `/health`가 **2~26ms**를 유지했다.
워커 스레드가 없었다면 약 5초간 API 전체가 멈췄을 구간이다.

## 3. 무엇을 바꿨나

### 3.1 왜 화이트리스트 한 줄이 아니었나

스테이징 컨테이너 실측: sharp 0.33.5 / libvips 8.15.3의 `heif.input.fileSuffix`가 **`['.avif']`**
뿐이고 바이너리에 **de265 심볼이 0건**이다 — libheif의 AV1 절반만 들어 있다. 아이폰의 HEVC
코딩 HEIC는 디코드 자체가 불가능하므로, 확장자만 열면 ①썸네일 없음 ②Safari 외 렌더 불가
③**EXIF 잔존**이 된다. ③이 핵심이다 — 이 시스템에서 EXIF 제거는 별도 스크러버가 아니라
**재인코딩의 부산물**이라(PLN-260814 SI-10), 디코드 실패는 곧 GPS가 박힌 원본을 저장·서빙하는
프라이버시 회귀다.

### 3.3 계획에 없던 판단 두 가지

- **AVIF도 JPEG로 저장.** REQ FR-8은 AVIF를 "추가 비용 0"으로 봤지만, 기존 경로는 입력 포맷을
  유지해 재인코딩하므로 **AV1 인코딩**이 돌아간다 — 12MP 사진 기준 **3,763ms vs JPEG 1,027ms**(실측).
  공개 업로드 엔드포인트에서 요청당 3.8초 CPU는 자해 DoS라 JPEG 변환으로 통일했다. REQ FR-8 정정.
- **인바운드 안내가 고객에게도 발신된다.** `system` 메시지는 아웃박스를 통과한다. 막지 않고
  문구를 "다시 보내달라"는 고객 대상 안내로 쓰고 세션 언어로 현지화했다 — 사진을 다시 보낼 수
  있는 사람은 고객뿐이다.

### 3.4 리뷰에서 잡힌 실제 결함 3건 (커밋 `e93d7a0`)

| 결함 | 왜 위험했나 |
|---|---|
| **유휴 워커에 `error` 리스너 없음** | `release()`가 리스너를 전부 떼고 풀에 넣어, 유휴 상태에서 죽은 워커의 `'error'`가 **uncaught exception → API 프로세스 중단**. 이제 리스너는 워커 수명 내내 유지되고 죽은 워커는 풀에서 제거된다 |
| **큐 무제한 + 타임아웃이 대기시간 미포함** | 대기 job이 업로드 버퍼(장당 최대 10MB)를 붙든 채 요청이 15초를 훨씬 넘겨 매달림. 큐 상한(32)+E5044, 마감은 **enqueue 시점에 기동** |
| **투명 픽셀이 검게 저장** | JPEG는 알파가 없어 RGBA(255,0,0,0)이 **RGB(1,2,0)** 로 인코딩됨(실측). 두 변환 경로 모두 흰색 평탄화 |

**반영하지 않은 지적**: 손댄 React 컴포넌트의 kebab-case 리네임 — 이 리포는 React 컴포넌트를
PascalCase로 일관되게 쓰고 있고(CLAUDE.md §2도 "React components PascalCase"), 이 브랜치와
무관한 광범위 변경이 된다.

## 8. 예방 패턴 (일반화)

- **"이미 읽을 수 있다"와 "싸게 처리할 수 있다"는 다른 문제다.** AVIF는 sharp가 읽으므로
  무비용으로 보였지만, 기존 경로가 입력 포맷을 유지해 재인코딩하는 바람에 AV1 인코딩이
  걸렸다. 포맷을 새로 열 때는 **디코드 가능 여부가 아니라 그 포맷으로 다시 쓰는 비용**을 봐야 한다.
- **폴백은 그 경로의 보안 전제를 알지 못한다.** "디코드 실패하면 원본을 그대로 저장"은
  다른 포맷에선 관대함이지만, EXIF 제거를 재인코딩에 의존하는 경로에선 개인정보 유출이다.
  폴백을 상속하기 전에 **그 폴백이 무엇을 무력화하는지** 확인해야 한다.
- **리스너를 떼는 정리 코드는 죽음의 경로까지 정리해 버린다.** 워커를 풀에 반납하며
  `'error'` 리스너까지 제거하면, 유휴 중 사망이 uncaught exception이 되어 프로세스를 죽인다.
  수명이 긴 자원의 리스너는 **작업 단위가 아니라 자원 단위**로 붙여야 한다.
- **큐에 상한이 없으면 타임아웃도 거짓말이 된다.** 마감을 "작업 시작"에 걸면 대기 시간은
  마감 밖이다. 요청이 매달리는 총 시간을 기준으로 재야 한다.
- **용량 제한은 픽셀 수를 제한하지 않는다.** 7MB짜리 56MP HEIC는 10MB 제한을 통과하고도
  디코드 시 수백 MB를 요구한다(36MP에서 RSS 771MB 관측).
