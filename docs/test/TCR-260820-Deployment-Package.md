## 3. 스테이징 호스트 격리 리허설 (실행 완료)

`shoptalk-rehearsal` 프로젝트명·포트 8099·MySQL 3399로 기존 스테이징과 완전 분리해 실행.

| ID | 시나리오 | 결과 |
|---|---|---|
| R-1 | 빈 상태에서 전체 스택 기동 | ✅ health ok · `/widget/` 200 · `/` 200 · 시드 성공 · `successfully started` |
| R-2 | **첨부 업로드 → API 컨테이너 강제 재생성** | ✅ **sha256 동일** — 볼륨이 실제로 붙어 있다(이 패키지의 존재 이유) |
| R-3 | 백업 → 볼륨 비우기 + 첨부 행 삭제 → 복원 | ✅ 행 1 · 파일 없는 행 0 · 복원 후 첨부 **sha256 동일** |
| R-4 | 미적용 SQL이 있으면 배포가 멈추는가 | ✅ 목록 출력 후 중단, `--check` 모드도 정상 |
| R-5 | placeholder 시크릿이면 부팅 거부되는가 | ✅ `Refusing to start in production with insecure secrets. Aborting.` |

리허설 환경은 컨테이너·볼륨·이미지까지 정리했고 기존 스테이징에는 영향이 없다.

## 5. 리뷰 반영 (배포 전)

| 지적 | 조치 |
|---|---|
| `--check`가 `widget-config.js`를 쓴다 | **수정.** nginx가 이 파일을 호스트 마운트에서 바로 서빙하므로, "아무것도 안 바꾼다"고 안내한 점검이 **라이브 위젯의 apiBase를 바꿀 수 있었다** |
| 콘솔 응답이 합격 조건에 없다 | **수정.** web이 502여도 `Deployed.`가 찍혔다 |
| `RABBITMQ_URL`이 `CHANGE_ME`로 남는다 | **수정.** 생성기가 비밀번호를 URL에 넣어 출력한다. 안내대로 붙여넣으면 RabbitMQ는 새 비번, API는 옛 URL이 되어 인증이 깨졌다 |
| 복원 중 API가 살아 있다 | **수정.** 경고문 대신 API를 정지하고, 업로드 볼륨은 일회용 컨테이너로 복원한 뒤 다시 기동한다 — 복원 중 들어온 대화가 정합성 검사를 깨뜨리던 경합을 없앴다 |
| 메타데이터 조회 실패를 성공으로 처리 | **수정.** 조회 실패는 "미적용 59건"이 아니라 오류로 끝낸다 |
| `#` 주석 미처리 · `ANTHROPIC_MODEL` 설명 | 수정 |
| **베이스 이미지 digest 고정 · 비root 실행** | **미반영(백로그).** `docker/staging`·`docker/production`과 함께 정해야 할 리포 전체 정책이고, 새 파일에만 적용하면 세 스택의 관행이 갈린다. 별도 요구로 다룬다 |
| 가이드 파일명 규칙 | 미반영 — `docs/guide`는 이 리포에서 접두사를 쓰지 않는다(기존 가이드 전부) |

바뀐 복원 경로는 스테이징 호스트에서 별도 볼륨으로 재검증했다: **API가 정지된 상태에서**
볼륨 탐색 → tar 복원 → 파일 존재 확인까지 통과.

## 6. 알려진 한계

- 리허설은 **스테이징 호스트**에서 했다. 고객사 클라우드(AWS·Matbao)의 네트워크·스토리지 특성은
  실제 설치 때 확인해야 한다.
- 이미지는 호스트에서 빌드한다(레지스트리 발행은 비범위). 모노레포 빌드라 첫 설치에 수 분 걸린다.
- 데이터 전용 SQL 3건은 스키마로 상태를 읽을 수 없어 검출기가 "확인 불가"로 표시한다 — 사람이
  판단해야 한다.
- 자동 백업 스케줄은 고객사 운영 도구에 위임한다(스크립트만 제공).
- **컨테이너가 root로 돈다.** 침해 시 볼륨 파일 권한까지 닿는다 — 세 스택 공통 정책으로
  비root 전환을 별도 요구로 잡아야 한다.
- 베이스 이미지가 태그로 고정돼 있어(`node:20-alpine` 등) 재빌드 시점에 따라 내용이 달라질 수 있다.
