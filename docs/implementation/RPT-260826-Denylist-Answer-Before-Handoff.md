## 2. 원인

**결함이 아니라 설정대로 동작한 것**입니다. tenant 3에 `환불계좌`·`계좌변경` 정책 deny 규칙이
있고, deny 분기는 **검색보다 먼저** 실행되며 설계상 LLM을 부르지 않습니다. 콘솔
`/knowledge/ask`에는 deny 검사가 없습니다(`denyMatch` 호출부는 코드 전체에서 한 곳).
두 화면의 답이 다른 이유는 지식 품질이 아니라 **경로**였습니다.

측정: 인계 메시지가 고객 발화 **290ms** 뒤 기록(모델 호출이 들어갈 수 없는 간격), 7일간 인계
9건 중 3건이 이 키워드, 고객 대기 **약 2분**.

**아이러니**: 이 질문에 답하는 문서가 6건 있었고 그중 2건(2377·2378)은 **바로 이 대화들에서
상담원 답변을 승격시킨 것**이었습니다. 지식 폐루프가 배운 답을 deny-list가 봉인하고 있었습니다.

## 3. 수정

deny-list가 **"사람이 처리한다"** 와 **"고객에게 아무 말도 하지 말라"** 를 한데 묶고 있었습니다.
규칙마다 `mode`를 둡니다.

| mode | 동작 |
|---|---|
| `silent` (기본·기존) | 답하지 않고 인계 |
| `answer_then_handoff` | 지식베이스로 답한 뒤 **그대로 인계** — 상담원 호출·이슈·SLA 전부 동일 |

**기본값을 침묵으로 둔 이유**: 기존 규칙은 전부 이 필드가 생기기 전에 작성됐고, 없음을 "답하라"로
읽으면 지불거절·법적 분쟁 같은 항목이 말없이 자동 응답으로 바뀝니다. 주제마다 운영자가 켭니다.

답이 나오지 않는 경우(신뢰도 미달·모더레이션 차단)는 기존 인계로 되돌아가되, **deny 규칙의
type/label을 그대로 실어** 이슈가 엉뚱한 데스크로 가지 않게 했습니다.

### 3.1 배포 후에만 드러난 두 갈래

리뷰와 스테이징이 각각 하나씩 잡았습니다. 둘 다 **"답변 먼저"가 인계를 미루는 게 아니라
없애버리는** 형태였습니다.

| 경로 | 증상 | 조치 |
|---|---|---|
| 잡담으로 분류된 deny 주제 | 친근한 응답만 하고 **상담원 호출 안 됨** | 즉시 인계(리뷰 지적, #394) |
| 비회원 + `needsOrderData` | 로그인 안내만 → 답도 사람도 없음 | 답변 경로로 통과, 주문맥락 없이 지식으로만 답하고 인계(#395) |

두 번째가 이 사건의 실제 문장이었습니다. `환불계좌 변경 규정이 어떻게 되나요?`는 고쳐진
직후 정상 동작했지만, **고객이 실제로 친 `환불계좌 바꾸고 싶어`는 분류기가 주문 데이터가
필요하다고 표시**해 로그인 게이트에 걸렸습니다. 문장 하나 차이로 결과가 갈렸고, 그건
스테이징에서 **원문 그대로** 넣어보기 전에는 보이지 않았습니다.
