  세션별 메시지 수 · 처리 및 만족도 · 고객 질문 시간대

## 1. AS-IS

`/statistics`는 **고객 질문 통계 한 종류**입니다 — 의도·인용지식·키워드·유사질문 4개 렌즈가
`question_stats_daily`(20,101행, 2026-07-01~08-25) 위에 얹혀 있습니다. 요청하신 6종은 하나도
없습니다.

관련 있는 것들이 여기저기 흩어져 있습니다.

| 있는 것 | 어디 | 이번 요청과의 관계 |
|---|---|---|
| 대시보드 KPI | `/dashboard` | 총량 위주, 축(채널·상담원)이 없음 |
| 고객여정 리포트 | 라이브챗 그룹 | 그룹 단위 서술형, 집계가 아님 |
| AI 사용량 | 설정 > AI 사용량 | 토큰·비용 축, 대화 품질 축 아님 |
| `agent_daily_stats` 테이블 | — | **§3 — 보이는 것과 다릅니다** |

## 2. 데이터는 있는가 — 항목별 실측

오늘 스테이징 숫자로 각 요청 항목을 실제로 뽑아봤습니다.

### 2.1 채널별 유입 메시지 · 세션 수 · 세션당 메시지 (요청 1·3·4) — **바로 가능**

```
channel     대화수   메시지수   대화당 메시지
widget       287      1,688        5.9
kakao         60      7,901      131.7
sms           47        756       16.1
zalo          12         51        4.3
line           6         54        9.0
wechat         6         12        2.0
viber          4         10        2.5
telegram       2          9        4.5
whatsapp       2          4        2.0
```

`conversations.channel`이 축입니다. **오늘(2026-08-26) 릴레이 출처 매핑을 고치기 전이었다면
이 표의 절반이 `relay` 한 줄로 뭉쳐 있었습니다**([[RPT-260826-Relay-Source-Labeling]]).
카카오의 대화당 131.7건은 그룹채팅이 섞인 값이라, 표에 **1:1/그룹 구분**이 필요합니다.

### 2.2 처리 및 만족도 (요청 5) — **가능하되 표본이 얇음**

```
전체 대화 426 · 상담원 배정 23 · 이관(escalated) 227 · CSAT 평점 10
```

- 처리 판정은 **새로 만들지 않습니다.** 고객여정 리포트의 `classifyOutcome`이 이미 정의를
  갖고 있습니다(CSAT 응답 / 상담원 종료 / 유도 후 종료 / 고객이 마지막 / 미종료).
  같은 정의를 쓰지 않으면 두 화면이 서로 다른 해결률을 말하게 됩니다 — 이전에 이 정의 하나로
  해결률이 100%에서 15%로 뒤집힌 적이 있습니다.
- **만족도는 426건 중 10건(2.3%)** 뿐입니다. 평균값만 크게 띄우면 표본 3건짜리 채널이 1위로
  보입니다. **응답 수를 항상 같이 표기**하고, 임계 미만은 값 대신 "표본 부족"으로 표시합니다.

### 2.3 상담원 상담통계 (요청 2) — **AI는 가능, 사람은 절반**

**AI 에이전트**: `sessions.ai_agent_id`로 집계됩니다(대화 426건 중 23건이 특정 에이전트에
고정, 나머지는 테넌트 기본). 에이전트별 대화수·이관율·평균 신뢰도·만족도까지 가능합니다.

**사람 상담원**: `agent_daily_stats` 테이블이 답처럼 보이지만 **아닙니다.**

```
컬럼:  handled  avg_first_response_sec  avg_handle_sec  resolved  escalated
       csat_avg  online_sec  blocked_msgs
실제로 쓰이는 컬럼:  csat_avg 하나뿐 (chat.service.ts:404 — CSAT 평점이 들어올 때만 기록)
행 수: 4 (테넌트 2곳, 8/10~8/24)
```

**9개 지표 중 8개가 한 번도 기록된 적이 없습니다.** 이 테이블을 그대로 화면에 올리면
상담원 성과가 전부 0으로 보입니다 — 없는 것보다 나쁩니다.

원자료로는 계산 가능합니다: 담당 대화(`conversations.agent_id`), 첫 응답 시간(이관 시각 →
첫 상담원 메시지), 처리 시간(첫 상담원 메시지 → `ended_at`), 해결(위 §2.2 정의), 만족도.

### 2.4 질문 시간대 (요청 6) — **가능, 단 시간대 주의**

`messages.created_at`(고객 발화)으로 시간대별 분포를 냅니다. 함정은 **타임존**입니다.

```
tenants.timezone 설정 현황: 11곳 중 2곳만 설정 (amoebaorder=Asia/Seoul, HRV-Tata=Asia/Ho_Chi_Minh)
```

UTC로 그리면 한국 테넌트의 피크가 **9시간 밀립니다** — 오후 3시 상담 몰림이 새벽 6시로 보입니다.
MySQL `CONVERT_TZ`에 IANA 이름을 쓸 수 있는 것은 확인했습니다(스테이징 tz 테이블 적재됨).
미설정 테넌트는 폴백이 필요하고, **화면에 어느 시간대 기준인지 반드시 표기**해야 합니다.

## 4. 제안

### 4.1 집계 방식 — **원자료 직접 집계(live)** 권장

일 스냅샷 테이블을 새로 만들지 않고 `conversations`/`messages`를 기간 조회합니다.

- 스냅샷은 원자료와 어긋날 여지를 만들고, 백필·재계산 경로가 늘 필요합니다
- 인덱스만 보강하면 됩니다(`messages(tenant_id, created_at)` 등 — 현재 `idx_msg_tenant`는
  tenant 단일 컬럼)
- **한계는 명시합니다: 대화 로그 보존기간(기본 365일)을 넘는 과거는 조회할 수 없습니다.**
  더 긴 보존이 필요해지면 그때 `ai_usage_daily`처럼 별도 창을 가진 스냅샷을 붙입니다

### 4.2 화면 — 탭 1줄 추가

현재 페이지는 "질문 통계" 한 화면입니다. 여기에 탭을 얹습니다.

```
통계
┌──────────────────────────────────────────────────────────────────┐
│ [질문] [채널] [상담원] [처리·만족도] [시간대]      기간 [▾ 30일] │
└──────────────────────────────────────────────────────────────────┘
```

기존 4개 렌즈는 "질문" 탭 안에 그대로 둡니다(회귀 없음).

### 4.3 각 탭의 내용

| 탭 | 표 | 차트 |
|---|---|---|
| 채널 | 채널별 세션·메시지·대화당 메시지·이관율·1:1/그룹 | 유입 추이(스택) |
| 상담원 | **AI 에이전트**와 **사람 상담원** 두 표. 대화수·평균 응답/처리시간·해결·만족도(응답수 병기) | — |
| 처리·만족도 | 해결 사유 분포(§2.2 정의), 미해결 사유, CSAT 분포 | 일자 추이 |
| 시간대 | 요일×시간 히트맵(테넌트 타임존 명기) | — |

## 6. side-impact

- 스키마 변경 없음. **인덱스 2개 추가**(`messages(tenant_id, created_at)`,
  `conversations(tenant_id, created_at)`) — 온라인 DDL, 데이터 변화 없음
- 권한: 기존 `statistics` capability 그대로
- 여정 리포트와 **같은 해결 정의**를 공유하므로 두 화면 숫자가 일치합니다
- i18n 6개 언어 신규 문구 다수
- 성능: 기간 조회 + GROUP BY. 스테이징 규모(메시지 1만)는 즉시. 대형 테넌트는 인덱스로 대응하고,
  그래도 느려지면 그때 스냅샷(§4.1)
