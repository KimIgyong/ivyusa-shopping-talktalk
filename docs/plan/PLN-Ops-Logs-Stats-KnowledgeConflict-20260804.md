## 5. S3 — 고객질문 통계 4축 (7.5d, **스키마 변경 있음**)

### 5-1. 공통 설계 — 단일 스냅샷 테이블, 4개 축

4축을 각각 별도 테이블로 만들면 화면·API가 4벌이 됩니다. **`dimension` 축을 가진 단일 스냅샷
테이블**로 통일하면 집계 잡·조회 API·화면이 하나로 끝나고, 축 추가도 열 변경 없이 가능합니다.

```
question_stats_daily
  tenant_id · stat_date · dimension · dim_key · dim_label
  asked · escalated · blocked · avg_confidence · no_source
  UNIQUE (tenant_id, stat_date, dimension, dim_key)

dimension ∈ { intent, category, document, keyword, cluster }
```

**D3(스냅샷)** 를 이 테이블이 담당하므로 retention 퍼지(365일) 이후에도 추이가 남습니다.
스냅샷은 집계값이며 **원문 질문을 저장하지 않습니다**(§7 개인정보 항목 참조).

### 5-2. 축별 파이프라인

| 축 | 소스 | 구현 |
|---|---|---|
| **A1 의도** | `rag.classifyIntent()` 결과 | 현재 계산 후 버림 → `messages.intent`·`intent_confidence` 적재. **LLM 추가 호출 없음**(이미 호출 중) |
| **A2 근거 문서·카테고리** | `messages.retrieval_trace.citations` | `JSON_EXTRACT`로 문서 id 추출 → 문서축·카테고리축 2개 dimension 동시 생성. **신규 수집 불필요** |
| **A3 키워드** | 질문 본문 | 언어별 정규화 → 불용어 제거 → en/es 유니그램, **ko는 2-gram**(형태소 분석기 미도입, `kb_documents`의 ngram FULLTEXT와 동일 전략). 상위 N만 적재 |
| **A4 유사질문 클러스터** | 질문 임베딩 | 일별 distinct 질문을 **배치 임베딩**(voyage-4) → 기존 센트로이드와 코사인 비교, `≥0.80`이면 편입·미만이면 신규 군집. 라벨 = 군집 대표(medoid) 질문 |

**A4 비용**: 하루 500질문 × 약 30토큰 ≈ 15k 토큰/일 ≈ 월 45만 토큰.
무료 한도(200M) 대비 무시 가능한 수준입니다. 배치 호출이므로 기존 429 백오프가 적용됩니다.

### 5-3. 집계 잡

- `question-stats.job.ts` — 매일 03:00(테넌트 타임존 무관, UTC 기준) 전일 데이터 집계
- **재실행 안전**: `UNIQUE` 키에 UPSERT → 같은 날 여러 번 돌려도 중복 없음
- `agent_daily_stats`(현재 0건) 적재 잡도 **같은 스케줄러에 함께 추가** — ③ 화면의 요약 배지가 이 값을 씁니다
- 백필: 기존 messages 범위(최대 365일)를 1회 소급 집계하는 `--backfill` 옵션

4개 탭이 **동일한 표·차트 컴포넌트를 공유**하고 `dimension` 파라미터만 바뀝니다.
`근거 없음(no_source)` 지표가 "지식에 없는 질문"을 드러내며 ⑤로 이어집니다.

### 5-5. 대시보드 정리

기존 `popularQuestions`(최근 5건 나열)는 **삭제하고** 통계 상위 5건으로 교체, `unresolvedTopN`은
실제 의미(대기 건수)에 맞게 `waitingCount`로 이름을 바로잡습니다.

## 6. S4 — 지식 충돌 · 출처 · 노후 관리 (3.5d, **스키마 변경 있음**)

### 6-1. 문서 메타 확장 (**D7**)

`kb_documents`에 추가: `created_at`, `source_url`, `owner_user_id`, `effective_from`(기준일),
`review_interval_days`(검토주기), `reviewed_at`, `reviewed_by`, `superseded_by`.
전부 **nullable/기본값** → 기존 236건 무중단 적용.

**노후 판정**: `reviewed_at + review_interval_days < today` 또는 `effective_from`이 가장 오래된 쪽.
기본 검토주기는 카테고리별 기본값(정책 180일, FAQ 365일)을 제안값으로 채우고 편집 가능.

### 6-2. 충돌 탐지 (**D5** 3단 구조)

```
① 후보 추림   각 문서 벡터로 Qdrant search(limit=5) → 유사도 ≥ 0.85 쌍
              (같은 테넌트, active=1, 이미 판정된 쌍 제외)
       ↓
② LLM 판정    두 문서 발췌를 주고 JSON_MODE로 판정
              {verdict: conflict|duplicate|complementary, rationale, key_difference}
              → ModerationService 통과 후 저장 (POL-020 준수)
       ↓
③ 사람 결정   콘솔에서 채택본 지정 → 반대편 active=0 (D6)
```

`kb_conflicts` 테이블: `tenant_id`, `doc_a_id`, `doc_b_id`, `similarity`, `verdict`, `rationale`,
`status`(pending/resolved/dismissed), `resolved_by`, `resolved_at`, `detected_at`,
UNIQUE `(tenant_id, doc_a_id, doc_b_id)`.

탐지는 **수동 트리거 + 주간 배치**. 236건 기준 전수 스캔은 Qdrant 236회 + LLM 판정 후보 수십 건
수준이라 부담이 없습니다.
