## 1. ① ProductInfo / CounselInfo 그룹

### 현행
- 문서 분류축은 **`kb_documents.category`(varchar 64, 자유 입력)** 하나뿐입니다.
- 스테이징 실사용: `policy_legal` 46 · `policy_shipping` 27 · `policy_return` 24 … **총 18종**.
- 콘솔 좌측 카테고리 네비게이터가 이 값을 그대로 나열합니다.

### 갭
- 요구하는 ProductInfo/CounselInfo는 **카테고리보다 한 단계 위**의 묶음입니다.
  현재 18개 카테고리를 그대로 두면서 그 위에 2개 그룹을 얹으려면 **축이 하나 더 필요**합니다.
- 카테고리를 그룹으로 재사용하면(예: category='ProductInfo') **기존 18종 분류가 통째로 사라집니다** —
  정책 문서의 세부 분류는 검색·통계(문서/카테고리 렌즈)에서 이미 쓰이고 있어 손실이 큽니다.
- 그룹은 **검색 단계에도 반영되어야 실효**가 있습니다. 상품 질문에 상담 정책이 섞여 나오거나
  그 반대가 되면 답변 품질이 떨어집니다(§4-1 참조).

### 고려사항
- **기존 230건의 일괄 배정**이 필요합니다 — 전부 CounselInfo. 마이그레이션에서 기본값으로 처리 가능.
- 그룹은 **닫힌 집합**(2종)이 적절합니다. 자유 문자열이면 오타로 그룹이 갈라집니다.
- 통계 4축의 `category` 렌즈와 별개로 **group 렌즈**를 추가할지 결정 필요(작은 추가 작업).

## 2. ①-b 상품정보 CSV 업로드

### 현행
**파일 업로드 경로가 존재하지 않습니다.**

| 확인 항목 | 결과 |
|---|---|
| `FileInterceptor` / `@UploadedFile` / multer | API 전체 **0건** |
| `kb_files` 테이블 | 존재하나 **0행**, `fileRepo`는 주입만 되고 **호출 0건** |
| 기존 문서 유입 경로 | 콘솔의 `POST /knowledge/documents`(제목+본문 수기) 또는 CLI `kb-import.ts`(JSON) |

### 갭
- 업로드 엔드포인트, 파일 크기·MIME 검증, 저장 위치(디스크/S3), CSV 파싱, 행→문서 변환,
  배치 임베딩까지 **전 구간 신규**입니다.
- CSV 1행을 문서 1건으로 만들 때 **어떤 컬럼을 제목/본문/카테고리로 쓸지**가 파일 구조에 달려 있는데,
  파일이 없어 확정할 수 없습니다.

### 2-1. CSV 실측 (v1.0.1)

`ivyusa_kbeauty_skincare-1.csv` — **144개 상품 / 11개 컬럼**, 307KB.

| 컬럼 | 채움률 | 평균 길이 | 고유값 | 용도 |
|---|---|---|---|---|
| `Product Name` | 100% | 103자 | **144** | 문서 제목 |
| `Handle` | 100% | 63자 | **144** | **업서트 키(D8)** |
| `Product URL` | 100% | 92자 | 144 | `source_url`(S4 필드) |
| `Detail` | 100% | 1,271자 | 137 | 본문 주력 |
| `Brand` | 96% | 8자 | 21종 | 본문·필터 |
| `SKU` | 95% | 5자 | 135 | 키로 **부적합** |
| `Price(USD)` | 96% | — | 49종 | **RAG 본문 제외 권고** |
| `Image URL` | 96% | 105자 | 136 | 메타(답변 미사용) |
| `How to Use` | 72% | 442자 | 84 | 본문 보조 |
| `Tags` | 96% | 169자 | 83 | 본문 보조 |
| `Category` | **65%** | 17자 | 11종 | 보조(빈 값 50건) |

**실측이 바꾼 판단 3가지**

1. **업서트 키는 `SKU`가 아니라 `Handle`입니다.** `SKU`는 144건 중 **7건 공란 + 중복 8건**
   (`MED04`·`MED01` 등)이라 키로 쓰면 서로 다른 상품이 서로를 덮어씁니다. `Handle`은
   **144/144 고유**이고 Shopify URL 슬러그라 안정적입니다.
2. **`Category`를 분류축으로 쓸 수 없습니다** — 65%만 채워져 있고 **50건이 빈 값**입니다.
   ProductInfo 하위 분류는 `Brand`(21종, 96%)나 `Tags`가 낫습니다.
3. **본문이 깨끗합니다** — HTML 태그 **0건**, 한국어 0건. 정제 파서가 필요 없습니다
   (엔티티 흔적 2건만 치환). 문서 본문 예상 평균 1,870자·최대 2,882자로 임베딩 한도에 여유가 큽니다.

**임베딩 비용**: 144건 1회 약 **67K 토큰** — 무료 쿼터(200M) 대비 무시 가능. 배치 3회로 끝납니다.

### 고려사항
- **재업로드 시 동작**을 정해야 합니다. 정책 문서 임포트는 `(tenant_id, title)` 기준 멱등 upsert였습니다.
  상품도 SKU 같은 안정적 키가 CSV에 있어야 "갱신"이 되고, 없으면 매번 중복 생성됩니다.
- 상품 수가 많으면 임베딩 호출량이 큽니다. Tier 1(2,000 RPM) 확보로 여유는 있으나
  **배치 처리 필수**(단건 루프는 재시도 경로가 없어 throttle에 취약 — 2026-08-04 실사고, PR #95).
- 상품 정보는 **가격·재고처럼 자주 바뀌는 값**을 포함할 수 있습니다. RAG 지식으로 굳히면
  낡은 값이 답변에 남습니다 — §5 D4 참조.

## 3. ② board / repository / gdrive 실제 동작

### 실측 결과 — **셋 다 동작하지 않습니다**

| 타입 | 등록 | 주소 입력 | 수집 | RAG 전환 |
|---|---|---|---|---|
| `board` | ✅ 가능 | ❌ `config_json` 미사용 | ❌ 글 작성 API는 있으나 **`kb_documents` 미생성** | ❌ |
| `repository` | ✅ 가능 | ❌ | ❌ **코드 자체가 없음** (`octokit`/`github` 참조 0건) | ❌ |
| `gdrive` | ✅ 가능 | ❌ | ❌ **코드 자체가 없음** (Drive API 호출 0건) | ❌ |

스테이징 실데이터:
```
knowledge_sources
  1  board   IVY Help Center  active  config_json=NULL
  2  gdrive  policy           active  config_json=NULL

kb_documents:  knowledge_store 230건 (source_id 있는 것 5건)
kb_board_posts: 0행      kb_files: 0행
```

- `config_json`은 **저장·조회만 되고(mapper) 해석하는 코드가 없습니다.** 주소를 넣어도 아무 일도 안 납니다.
- 콘솔의 소스 생성 폼은 **이름과 타입만** 받습니다 — 주소 입력란 자체가 없습니다.
- `kb_documents.source`는 `knowledge_store`/`google_drive` 두 값을 상정하고 RAG에 우선순위 보너스
  (POL-013)까지 있지만, **`google_drive`를 쓰는 코드가 없어** 그 분기는 한 번도 실행된 적이 없습니다.

### 갭 (타입별)

**board** — 가장 가깝습니다. `kb_board_posts`에 글은 쌓을 수 있으나 지식이 되지 않습니다.
"참조할 게시판"이 **내부 게시판**인지 **외부 URL**인지에 따라 작업이 갈립니다(§5 D5).

**repository (GitHub)** — 인증(PAT/App), 대상 지정(레포·브랜치·경로 글롭), 파일 형식(.md 위주),
변경 감지(웹훅 또는 폴링), 파일→문서 매핑이 전부 필요합니다. **가장 큰 작업**입니다.

**gdrive** — OAuth 또는 서비스 계정, 폴더 순회, Google Docs/Sheets export(문서→텍스트),
변경 감지가 필요합니다. `integration_credentials`에 `google_drive` provider 자리는 **이미 있습니다**
(시드에 존재) — 자격증명 저장·암호화 인프라는 재사용 가능합니다.

### 고려사항
- **공통 파이프라인이 필요합니다.** 세 타입 모두 "외부에서 원문을 가져와 → 텍스트로 만들고 →
  `kb_documents`로 upsert → 임베딩"이 같습니다. 어댑터 3종 + 공용 수집기 구조가 자연스럽습니다.
- **동기화 방향과 주기**를 정해야 합니다. 수동 트리거만? 주기 폴링? 웹훅?
- **삭제 동기화** — 원본에서 사라진 문서를 어떻게 할지(숨김/삭제/유지)가 정책 결정입니다.
- **S4에서 만든 출처 메타**(`source_url`·`effective_from`·검토주기)와 자연스럽게 이어집니다 —
  수집기가 원문 URL을 채우면 콘솔에서 바로 원본으로 이동할 수 있습니다.

## 4. 공통 관찰

### 4-1. 그룹은 검색에 반영되어야 의미가 있습니다
현재 RAG는 테넌트 내 **모든 활성 문서**를 대상으로 검색합니다(`rag.service.ts`). 그룹을 만들어도
검색이 이를 무시하면 상품 질문에 정책 문서가 섞입니다. 최소한 **의도/질문 유형에 따라 그룹 가중치**를
주거나, 상품 질의로 분류되면 ProductInfo를 우선하는 처리가 필요합니다.
> 다행히 **의도 분류기(`classifyIntent`)가 이미 매 메시지에 동작하고 결과를 저장**하고 있어
> (S3에서 적재 시작) 이를 그룹 선택 신호로 쓸 수 있습니다 — 신규 분류 로직이 필요 없습니다.

### 4-2. ①과 ②는 같은 파이프라인을 씁니다
CSV 업로드도 결국 "외부 원문 → 텍스트 → 문서 upsert → 임베딩"입니다. ②의 공용 수집기를 먼저
만들고 CSV를 그 위의 어댑터 하나로 붙이면 중복이 없습니다. 반대로 ①을 급히 따로 만들면
②에서 같은 코드를 다시 씁니다.

### 4-3. 기존 자산 재사용 가능
| 자산 | 재사용처 |
|---|---|
| `kb-import.ts`의 `(tenant_id, title)` 멱등 upsert | 모든 수집기의 문서 갱신 규칙 |
| 배치 임베딩(64건) + stub 폴백 거부 가드 | 대량 수집 시 필수 (PR #94/#95) |
| `integration_credentials` AES-GCM 암호화 | GitHub PAT / Google 서비스 계정 키 저장 |
| S4 출처 메타(`source_url`·`owner`·검토주기) | 수집한 문서의 원본 추적 |
| 수정 이력(`kb_document_revisions`) | 동기화로 바뀐 내용도 자동 기록됨 |

## 7. 권고 진행 순서

1. ~~D1·D5 회신~~ → **해소**. 남은 결정 D2·D3·D4·D6·D7·D9는 전부 권고안대로 진행 가능합니다.

   상품 데이터를 git에 올리면 가격이 바뀔 때마다 커밋이 필요해집니다.

   맞닿아 효용이 큽니다. repository는 개발 문서 성격이라 상담 지식으로서의 우선순위가 낮습니다.
