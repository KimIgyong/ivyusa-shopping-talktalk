## 3. 설계 판단 기록

- **숫자는 코드가, 서술은 모델이.** 프롬프트가 "모든 숫자는 METRICS에서 복사하라, 없으면
  측정되지 않았다고 말하라"를 명시합니다. 모델에게 세게 하면 그럴듯하고 틀린 숫자가 나오고,
  **리포트라는 형식이 그것을 근거처럼 보이게** 만듭니다.
- **비동기.** 큰 그룹은 수십 초, nginx는 60초에 끊습니다 — 카탈로그 변환이 이미 겪은 함정.
- **행이 곧 작업.** 리포트가 결과물이라 메모리에 둘 수 없습니다. 재시작 유실을 막기 위해
  부팅 시 30분 넘은 `pending`을 사유와 함께 `failed`로 정리합니다 — *"아직 생성 중"*과
  *"한 시간 전에 죽음"*은 운영자가 할 일이 완전히 다릅니다.
- **모더레이션 차단 시 저장 안 함.** 구멍 난 리포트보다 사유가 적힌 실패가 낫습니다.
- **샘플은 기간 전체에 고르게.** 최신 N개는 운영자가 방금 읽은 것입니다.
- **세션 스냅샷.** 그룹은 뷰라 구성원이 바뀝니다. 없으면 같은 리포트를 다시 못 만듭니다.
- **기준은 최대 버전 = 현재.** 활성 플래그를 따로 두면 두 번째 진실 원천이 되고, 과거 리포트가
  자기 버전을 고정하므로 둘이 어긋나면 무엇이 실제로 썼는지 알 수 없습니다.
- **비교 시 버전 상이를 먼저 말합니다.** 없으면 **우리 규칙이 바뀐 것이 고객이 바뀐 것으로**
  읽힙니다.
- **하지 않은 것**: 점수화된 관계 등급, 개인 심리 프로파일링, Aware/Appeal 추정, 매슬로우 단정.

## 4. 실데이터가 설계를 정당화한 지점 ⭐

배포 후 스테이징 그룹 2에 집계를 돌리고 SQL과 대조했습니다. **모든 수치가 정확히 일치**했고,
그 과정에서 이것이 드러났습니다.

```
종료된 대화 13건
  ├ 해결      2건  (상담원 종료 1 · 묻고-닫음 1)
  └ 미해결   11건  (묻고-닫음이나 고객이 마지막으로 말함)

"종료 = 해결"로 셌다면  →  13건 · 해결률 100%
실제 규칙으로 세면      →   2건 · 해결률 15%
```

**6.5배 차이입니다.** REQ에서 "방치된 대화가 가장 빠른 해결로 집계된다"고 적은 것이 실데이터로
확인됐습니다. 이 그룹은 고객이 마지막으로 말하고 답을 못 받은 채 닫힌 대화가 대다수인데,
순진한 정의였다면 **해결률 100%짜리 우수 사례**로 보였을 것입니다.

정의 하나가 리포트의 결론을 뒤집습니다. 그래서 그 정의를 리포트 본문에 인쇄합니다.
