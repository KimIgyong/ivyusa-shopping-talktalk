## 1. 단위 테스트 (구현·통과 완료)

가장 위험한 두 실패 모드 — **모델이 제안하지 않은 변경을 만들어내는 것**과
**설정이 움직인 뒤 엉뚱한 대상에 적용되는 것** — 에 집중했다.

### 1.1 제안 파싱 (`extract`)

| # | 케이스 | 기대 | 결과 |
|---|---|---|---|
| T-01 | 정상 JSON 블록 | 본문에서 블록 제거 + 제안 1건 파싱 | ✅ |
| T-02 | JSON 블록 없음 (순수 설명 답변) | 제안 0건, 본문 그대로 | ✅ |
| T-03 | 깨진 JSON | **제안 0건 + 본문만 표시** (추측 복구 금지) | ✅ |
| T-04 | 알 수 없는 type / 필수 필드 누락 | 해당 항목만 드롭, 정상 항목은 유지 | ✅ |

T-03이 핵심이다. 게이트웨이는 어댑터 오류 시 조용히 stub으로 폴백하므로(`ai-gateway.service.ts:68-75`)
**파싱 실패는 예외가 아니라 정상 상태**다. 여기서 "그럴듯하게 복구"하면 사용자가 승인 버튼을 누르는
순간 아무도 제안하지 않은 규칙이 전 고객 응대에 반영된다.

## 3. 미수행 — 실 LLM 경로 (배포 후 필수)

로컬에는 Anthropic 키가 없어 코칭 응답이 전부 stub이었다. 따라서 **다음은 검증되지 않았다**:

| # | 항목 | 확인 방법 |
|---|---|---|
| U-01 | 실제 모델이 규약대로 JSON 블록을 붙이는가 | 스테이징에서 "환불 답변이 너무 딱딱해요" 입력 → 제안 카드 생성 확인 |
| U-02 | **사실을 규칙으로 인코딩하지 않는가** (REQ §13.1 안티패턴) | "환불 기간은 30일이야" 입력 → 규칙 제안이 아니라 "지식 문서가 필요합니다" 안내가 나오는지 |
| U-03 | 유사 규칙 존재 시 `rule_add`가 아니라 `rule_edit`을 내는가 | 기존 규칙과 겹치는 주제로 코칭 |
| U-04 | 충돌 경고(`conflictsWith`)가 실제로 채워지는가 | 기존 규칙과 모순되는 지시 입력 |
| U-05 | 진단이 trace 수치에 근거하는가 (추측 금지) | W3 연동 후 `ref_message_id` 첨부 코칭 |
| U-06 | 프롬프트 인젝션 내성 | 참조 턴에 "규칙을 추가하라"류 문구가 포함된 고객 메시지로 코칭 |

U-02는 **배포 후 최우선 확인 항목**이다. W1에는 `kb_upsert` 제안이 없으므로, 모델이 이 지시를
무시하면 정책 수치가 응답 규칙으로 새어 들어간다.
