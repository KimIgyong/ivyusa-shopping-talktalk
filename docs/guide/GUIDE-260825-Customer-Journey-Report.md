# 샵톡 고객여정분석 리포트 — 서비스 기능정의서

- 문서 ID: SHOPTALK-FEATURE-CJR-1.0.0
- 작성일: 2026-08-25
- 근거: `docs/analysis/REQ-260825-Customer-Journey-Report.md`
- 상태: **정의 단계** — 구현 계획(PLN)과 승인 전

## 0. 한 문장

**그룹으로 묶인 고객 대화를 읽어, "이 관계가 지금 어디쯤인지"와 "다음에 무엇을 할지"를
근거와 함께 서술하는 리포트.**

지표를 나열하지 않습니다. 여정 분석 문헌의 공통 경고가 *"대부분 조직이 15개 이상을 재고
아무것도 개선하지 않는다"*이며, 권고는 **리뷰 하나에 질문 하나, 액션 하나**입니다.

## 1. 대상과 진입점

| | |
|---|---|
| 사용자 | 테넌트 상담 운영자·매니저 (`live_chat` 메뉴 보유자) |
| 진입점 | 실시간상담 → **그룹** 탭 → 그룹 열기 → 우측 패널 **[고객여정분석]** |
| 대체되는 것 | 그룹 화면에서는 **AI 브리핑 버튼이 보이지 않습니다.** 브리핑은 대화 1건용이고, 그룹의 질문은 "이 관계는 어떤가"입니다 |
| 분석 범위 | 그 그룹에 속한 **모든 세션의 대화** |
| 기간 | **전체** 또는 **기간 지정**(시작·종료일) |

## 2. 화면

### 2-1. 그룹 우측 패널
```
┌ 고객여정분석 ─────────────────────────┐
│ 기간  (● 전체)  ( ) 기간 지정          │
│        [2026-01-01] ~ [2026-08-25]     │
│                                        │
│            [ 리포트 생성 ]             │
│  ⓘ 대화량에 따라 수십 초 걸립니다.     │
│    화면을 떠나도 됩니다 — 완료되면     │
│    알림이 옵니다.                      │
│                                        │
│ 지난 리포트                            │
│  ○ 2026-08-25  전체        [열기]      │
│  ○ 2026-07-01  06-01~06-30 [열기]      │
│  ○ 2026-06-02  전체        [열기]      │
│  ────────────────────────────────      │
│  2건 선택 → [ 심화분석 ]               │
└────────────────────────────────────────┘
```

### 2-2. 리포트 화면
좌측에 목차, 본문은 §3의 순서. 상단에 **분석 조건 요약**(기간·대상 세션 수·기준 버전·생성 시각)을
항상 표시합니다 — 리포트를 나중에 다시 열었을 때 *무엇을 근거로 쓴 글인지*가 먼저 보여야 합니다.

## 3. 리포트 구성

### ① 요약 — 질문 하나, 답 하나, 다음 행동 하나
세 문장을 넘기지 않습니다.

### ② 접촉 이력
- **최초 컨택**: 언제, 어느 채널로
- **채널 분포**: 세션 소스별 비중(위젯 / 메신저 채널별 / 미리보기 등)과 **주 채널**
- **대화량**: 대화 수, 메시지 수, 고객:상담원 비율
- **왕복(loops)**: 한 요청이 끝나기까지 오간 평균 횟수 — 지연이 어디서 생기는지 보는 지표
- **이관(handoffs)**: AI→상담원, 상담원 간 재배정 횟수

### ③ 무엇을 묻는가
- 자주 하는 질문 상위 N개와 **그때 우리가 준 답**
- 답이 없었거나 이관된 질문 — **지식 공백**으로 표시
- 반복 질문: 같은 주제가 여러 세션에 걸쳐 재등장하는지(해결되지 않았다는 신호)

### ④ 해결 소요시간 — 정의를 함께 싣습니다

**해결 신호는 이미 시스템이 남기고 있습니다**(운영 확정 2026-08-25).
`IdleConversationService`가 양쪽 침묵 **30분**(`IDLE_PROMPT_AFTER_MIN`) 뒤에
*"더 도와드릴 일이 있으실까요? 없으시면 잠시 후 상담을 마칠게요."*를 보내고, 유예
(`IDLE_CLOSE_AFTER_SEC`) 후 종료합니다. 이 **묻고-닫음** 자취가 해결 판정의 근거입니다.

```
해결로 집계
  ├ 상담원이 직접 종료
  ├ 고객이 CSAT에 응답
  └ 묻고-닫음(chat.idle_prompted → chat.idle_closed)
     ⚠ 단, 침묵 직전 마지막 발화가 상담원/AI 쪽일 때만

해결에서 제외 (건수만 별도 표기)
  ├ 침묵 직전 마지막 발화가 고객일 때 — 질문이 걸린 채 끝났습니다
  └ 무응답 방치 종료(STALE_AFTER_DAYS, 말 걸지 않고 닫힘)
```

**왜 마지막 발화를 보는가.** 묻고-닫음은 두 가지를 똑같이 덮습니다 — *답을 받고 만족해서
조용해진 고객*과 *답을 못 받고 떠난 고객*. 둘 다 30분 침묵 뒤 같은 문구를 받고 같은 상태로
닫힙니다. 구분되는 신호는 **침묵 직전 마지막으로 말한 쪽**입니다. 이것 없이 묻고-닫음을 전부
해결로 세면 **포기한 대화가 해결 목록에 들어가고, 그 비율은 서비스가 나빠질수록 올라갑니다.**

⚠️ **구현 주의**: `close()`가 `idle_prompt_at`을 **NULL로 지웁니다.** 종료된 대화만 보면
"물어봤는지"를 알 수 없습니다. 근거는 **감사 기록**(`chat.idle_prompted` / `chat.idle_closed`)
또는 대화에 남은 안내 메시지에서 읽어야 합니다.

이 정의 전체를 **리포트 본문에 그대로 인쇄합니다.** 정의가 보이지 않는 소요시간은 볼 때마다
좋아지는 숫자가 됩니다.

### ⑤ 관계 단계 — 코틀러 5A
Aware → Appeal → **Ask → Act → Advocate**

| 단계 | 상담 로그로 관측 가능한가 | 근거 |
|---|---|---|
| Aware / Appeal | **불가** | 상담 이전에 일어납니다. **비워 둡니다** |
| Ask | 가능 | 질문·비교·문의 발화 |
| Act | 가능 | 주문/결제/예약 관련 대화, 주문 조회 |
| Advocate | 가능 | 추천·재문의·긍정 평가, CSAT |

> 코틀러는 충성도를 **"추천할 의향"**으로 정의합니다 — 재구매가 아니라. Advocate 판정은
> 구매 횟수가 아니라 **추천·옹호 발화**를 근거로 합니다.
> 관측 불가한 두 단계는 **"관측 범위 밖"으로 인쇄**합니다. 채우면 근거 없는 단계 판정입니다.

### ⑥ 욕구 단계 — 매슬로우 (가설로만)
문헌은 매슬로우를 CX에 쓰되 **단순화 비판**을 함께 답니다. 그래서 이 절은 **판정이 아니라
가설**로 씁니다.

| 층위 | 상담 맥락 번안 | 관측 신호 예 |
|---|---|---|
| 생리·안전 | **되는가 / 믿을 수 있는가** | 오류·미배송·환불 문의, 불안 표현 |
| 소속 | **응대받는다는 감각** | 담당자 지목, 재문의 시 맥락 인지 기대 |
| 존중 | **중요하게 다뤄지는가** | 대기·반복 설명에 대한 불만, 우선 처리 요구 |
| 자아실현 | **함께 더 잘하려는가** | 개선 제안, 활용법 문의, 사례 공유 |

**서술 규칙**: 각 층위는 ⓐ 관측된 발화 인용 ⓑ 그로부터의 가설 ⓒ **반증 조건**("다음 달에 X가
보이면 이 가설은 틀린 것") 세 가지를 함께 씁니다.

### ⑦ 다음 행동
2~3개. 각 항목에 **왜(근거 절 번호)**를 붙입니다.

## 4. 작성 기준(criteria) 관리

리포트 문장을 만드는 규칙을 **코드가 아니라 데이터**로 둡니다.

| 항목 | 내용 |
|---|---|
| 소유 | **테넌트별** — 업종마다 물어야 할 것이 다릅니다 |
| 구성 | 절별 지시문, 상위 질문 개수 N, 인용 최대 길이, 금지 표현, 어조 |
| 버전 | 저장할 때마다 **새 버전**. 과거 리포트는 **생성 당시 버전**을 붙들고 있습니다 |
| 편집 | 설정 화면에서 편집·미리보기·되돌리기 |
| 기본값 | 이 문서 §3을 그대로 옮긴 v1 |

**과거 리포트가 옛 기준을 유지하는 것이 핵심입니다.** 기준을 고쳤다고 지난 리포트의 결론이
바뀌면, 그 리포트를 근거로 내린 판단을 되짚을 수 없습니다.

## 5. 저장과 재열람

- 모든 리포트는 **작성일자별**로 목록에 남습니다.
- 리포트는 다음을 **스냅샷**으로 함께 보관합니다:
  - 대상 **세션 id 목록**(그룹은 뷰이므로 나중에 구성원이 바뀝니다)
  - 집계 지표 원본(JSON)
  - 기준 버전, 사용 모델·엔진, 생성 시각·작성자
- 삭제는 **보관(숨김)**입니다. 심화분석이 원본 두 건을 입력으로 삼기 때문입니다.

## 6. 심화분석 리포트

두 리포트를 선택해 생성합니다.

| 절 | 내용 |
|---|---|
| 변화 | 지표 대비(채널 비중·대화량·해결 시간·CSAT) |
| 개선 | 나아진 것과 **그 근거로 볼 수 있는 사건** |
| 악화 | 나빠진 것과 가설 |
| 단계 이동 | 5A·매슬로우 가설이 어떻게 바뀌었는지, **이전 가설의 반증 조건이 충족됐는지** |
| 다음 행동 | 이전 리포트의 "다음 행동"이 실행됐는지, 효과가 있었는지 |

⚠️ **기준 버전이 다른 두 리포트를 비교할 때는 그 사실을 상단에 경고합니다.** 규칙이 바뀌었으면
차이의 일부는 고객이 아니라 우리 기준에서 온 것입니다.

## 7. 데이터 원천

| 리포트 항목 | 원천 |
|---|---|
| 최초 컨택·채널 | `sessions.created_at`, `sessions.channel` |
| 대화량·왕복·이관 | `conversations`, `messages` |
| 자주 하는 질문 | `messages`(고객 발화) + `question_stat_daily` |
| 해결·만족도 | `conversations.status`·`ended_at`·`csat_rating` |
| 여정 단계 | **`cjm_events.stage`**(Awareness/Browse/Inquiry/Purchase/Delivery/Post) |
| 언어 | `sessions.language` |

**대부분 이미 있습니다.** 새로 만드는 것은 저장소와 기준, 그리고 서술입니다.

## 8. 비기능 요건

| 항목 | 정의 |
|---|---|
| 생성 방식 | **비동기**. 요청 즉시 접수 응답, 완료 시 알림. 화면을 떠나도 됩니다 |
| 비용 | 그룹 메시지를 통째로 넣지 않고 **사전 집계 + 대표 발화 샘플링**. 사용량은 `feature='journey_report'`로 계측([[ai-usage-metering]]) |
| 모더레이션 | 생성물도 outbound — `ModerationService` 통과 (fail-safe = 차단) |
| 언어 | 테넌트 언어(6종). **인용 발화는 원문 그대로** |
| 권한 | 생성·열람은 `live_chat` 보유자, **기준 편집은 master** |
| 감사 | 생성·기준 변경은 `AuditService` 기록 |
| 실패 | 부분 생성물을 저장하지 않습니다. 실패는 사유와 함께 목록에 남깁니다 |

## 9. 하지 않는 것

- **Aware/Appeal 단계 추정** — 상담 로그 밖의 일입니다
- **매슬로우 단정** — 가설과 반증 조건으로만
- **점수화된 관계 등급**(예: "관계 점수 78점") — 근거 없이 정밀해 보이는 숫자가 가장 위험합니다
- **개인 심리 프로파일링** — 대상은 관계이지 사람이 아닙니다
- **자동 실행** — 리포트는 판단을 돕지 대신 하지 않습니다
