   **AI 답변의 근거가 되는 문서를 누가 언제 고쳤는지는 기록되지 않습니다.** ③은 화면을
   붙이는 문제가 아니라 **기록 자체를 시작하는 문제**입니다.

2. **반복 실패 12쌍이 실측으로 확인됐습니다.** 스테이징에서 스캔을 5회 돌린 결과 후보가
   121→85→55→26→12로 줄다가 **12에서 멈췄고, 이후 스캔은 12쌍을 매번 재판정하며 계속 실패**합니다.
   판정 실패 쌍은 저장하지 않는다는 설계(근거 없는 항목을 큐에 넣지 않음) 때문인데,

3. **본문이 작습니다** — 230건 평균 242자, 최대 914자, 전체 54KB. 스냅샷 방식 이력을 저장해도
   부담이 없어, ③의 설계 선택지가 저장 비용에 제약받지 않습니다.

## 1. 실패 사유 로깅 + 반복 실패 쌍 표시

### 현행
`KbConflictService.judge()`는 4가지 경로로 판정을 포기하고 `null`을 반환합니다.

| # | 위치 | 사유 | 로그 |
|---|---|---|---|
| 1 | `kb-conflict.service.ts:189` | 모델 호출 자체 실패(네트워크·5xx 등) | **WARN 있음** |
| 2 | `:198` | 응답 JSON 파싱 실패 | **무음** |
| 3 | `:201` | verdict가 허용 3값 밖 | **무음** |
| 4 | `:212` | 모더레이션이 근거 텍스트 차단 | **무음** |

`scan()`은 `judged`/`candidates` 수치만 반환하므로, 차이(12)로 "무언가 실패했다"는 사실만 알 수 있고
**무엇이 왜 실패했는지는 알 수 없습니다.**

### 갭
- **사유 구분 불가** — 대응이 완전히 다릅니다. 파싱 실패는 모델·프롬프트 문제(모델 교체나 프롬프트 보강),
  모더레이션 차단은 **테넌트 모더레이션 규칙이 과도하게 넓다**는 신호(규칙 수정)입니다.
  현재는 어느 쪽인지 알 수 없어 조치를 고를 수 없습니다.
- **반복 실패 영구 재시도** — 실패 쌍은 `kb_conflicts`에 저장되지 않으므로 `knownPairs()`에 걸리지 않고
  매 스캔 후보로 재등장합니다. 실측 12쌍 × 스캔 횟수만큼 모델 호출이 낭비됩니다.
- **운영자 가시성 없음** — 콘솔에는 "판정 실패" 개념 자체가 없습니다. 후보 121쌍 중 110쌍만
  목록에 나타나는데 **나머지 11~12쌍이 어디로 갔는지 화면상 단서가 없습니다.**

### 1-1. 실측 결과 (2026-08-04, 스테이징 · 진단 스크립트 1회 · DB 무변경)

§7의 선행 제안대로 판정 4경로를 분류해 측정했습니다. 결과는 **한쪽으로 완전히 쏠렸습니다.**

| 사유 | 건수 |
|---|---|
| 모델 호출 실패 | 0 |
| JSON 파싱 실패 | 0 |
| 허용 밖 verdict | 0 |
| **모더레이션 차단** | **11 / 11** |

차단된 근거 텍스트는 전부 평범한 분석 문장입니다. 예:

```
"A states orders can be canceled before entering preparing status (a definite
 guarantee), while B says cancellation is only possibly available…"
```

**차단 규칙은 `content_filter_rules` id=1** — `type: word`, `pattern: "guarantee"`, `action: **warn**`,
`scope: both`. `moderation_logs`에 `rule_id=1 / action=warn / decision=blocked`로 남아 있습니다.

이로부터 **원인 두 가지**가 확정됩니다.

#### 원인 A — 내부 텍스트를 고객용 모더레이션에 통과시킨 설계 오류 (S4, 제 코드)
충돌 근거는 **콘솔에서 관리자에게만 보이는 내부 메모**이고 고객에게 나가지 않습니다.
POL-020이 요구하는 것은 **outbound(고객 대상) AI 출력**의 모더레이션인데, S4는 이를
`scope: 'ai'`로 고객용 게이트에 통과시켰습니다. 그 결과 *"문서 A가 보장한다고 서술한다"* 는
**설명**이, *"보장합니다"* 라는 **약속**과 동일하게 취급됩니다.

> 판정값(`conflict`/`duplicate`/`complementary`)은 3값 열거형이라 모더레이션 위반이 불가능합니다.
> 자유 텍스트는 근거뿐인데, **근거 하나 때문에 판정 전체를 버리고 있습니다.**

#### 원인 B — `warn` 액션이 `block`과 동일하게 동작 (기존 코드 결함)
`moderation.service.ts`:
```ts
if (action === MODERATION_ACTION.BLOCK || action === MODERATION_ACTION.WARN) {
  return this.finalize(input, MODERATION_DECISION.BLOCKED, action, '', rule.id);
}
```
운영자가 **경고**로 설정한 규칙이 **차단**으로 동작하며 본문을 비웁니다.

- **영향 범위는 이 기능 밖입니다** — 고객 대화 경로에서도 동일합니다. AI 답변에 `guarantee`가
  포함되면 **차단 후 상담원 이관**되는데, 운영자는 경고만 설정했습니다.
- **실측 피해는 아직 없습니다** — `moderation_logs`에서 `conversation_id IS NOT NULL`인 차단은
  **0건**입니다(기록된 차단 60건은 전부 오늘 제 스캔). 즉 **잠재 위험이며 현재 진행형 장애는 아닙니다.**
- `/ai-setting` 콘솔의 액션 선택지는 `block|mask|rephrase`뿐이라 신규 규칙으로는 `warn`을
  만들 수 없습니다. 문제의 규칙은 **시드 데이터**(2026-06-30 생성)입니다.

### 고려사항
- 실패 쌍을 그냥 저장하면 **"설명 없는 항목이 검토 큐에 쌓이는"** 상황이 됩니다 — S4에서 의도적으로
  피한 결과이므로, 저장하되 **검토 큐와 분리된 상태**로 두는 설계가 필요합니다.
- 모더레이션 차단이 원인이라면 이는 **기능 결함이 아니라 설정 문제**일 수 있습니다.
  실측으로 사유 분포를 먼저 확인해야 우선순위가 정해집니다.
- 재시도 정책도 결정 대상입니다 — 영구 포기 / N회 후 포기 / 수동 재시도.

## 2. 충돌 화면에서 문서 편집

### 현행
- 충돌 카드(`ConflictReview.tsx` → `DocSide`)는 문서당 **발췌 400자**만 표시합니다
  (`kb-conflict.service.ts` `summarize()`).
- 제목을 클릭하면 `onOpenDocument(id)` → `KnowledgePage.setDetailId(id)`로
  **기존 상세 모달**이 열리고, 거기서 `편집` 버튼으로 제목·카테고리·본문·출처 메타를 수정·저장할 수 있습니다.
- 저장 시 본문이 바뀌었으면 재임베딩되어 검색에 즉시 반영됩니다.

### 갭
- **비교 맥락 상실 — 이 요구의 핵심.** 충돌 검토의 가치는 두 문서를 **나란히 놓고 어디가 어긋났는지
  보는 것**인데, 편집하려면 모달이 그 위를 덮어 **반대편 문서를 볼 수 없습니다.**
  "A는 3~5영업일, B는 발송 후 기준"을 맞추려면 양쪽을 보면서 고쳐야 합니다.
- 발췌 400자 — 평균 242자라 대부분 전문이 보이지만, **최대 914자 문서는 잘립니다.**
  잘린 뒷부분에 상충 지점이 있으면 카드만 보고는 판단할 수 없습니다.
- 편집 후 **충돌 재판정 경로가 없습니다.** 고친 뒤에도 카드의 판정·근거는 옛 내용 기준으로 남고,
  해당 쌍을 다시 판정하려면 전체 스캔을 돌려야 합니다(이미 저장된 쌍이라 재판정도 안 됨).
- 두 문서를 **동시에** 고쳐야 하는 경우(한/영 번역 불일치처럼) 저장을 두 번 왕복해야 합니다.

### 고려사항
- 실제 상충 2건 중 1건이 **`4.3 증빙서류` ↔ `4.3 Verification Documents`(한/영 동일 조항)** 입니다.
  이런 쌍은 **양쪽을 함께 고치는 것이 정상 작업 흐름**이므로 나란히 편집이 특히 필요합니다.
- 편집은 재임베딩을 유발하므로(본문 변경 시) **연속 저장 시 임베딩 호출량**을 고려해야 합니다.
  Tier 1 확보로 여유는 생겼습니다.

## 3. 수정 히스토리

### 현행
**존재하지 않습니다.**

| 확인 항목 | 결과 |
|---|---|
| 버전/이력 테이블 | 없음 |
| `kb_documents` 변경 추적 컬럼 | `updated_at`뿐 (누가 고쳤는지 없음) |
| 감사 기록 | `knowledge.*` action **0건** — `KnowledgeService`/`KnowledgeController`가 `AuditService`를 **주입조차 하지 않음** |
| 실측(스테이징 `audit_logs` action 14종) | `auth.*` `retention.*` `agent.*` `mfa.*` `tenant.*` — 지식 관련 전무 |

S4에서 `reviewed_at`/`reviewed_by`(검토 완료 도장)는 추가했지만, 이는 **"확인했다"이지 "고쳤다"가 아닙니다.**

### 갭
- **언제/누가/무엇을** 세 가지 모두 기록되지 않습니다.
- 잘못된 편집을 **되돌릴 수 없습니다** — 이전 내용이 어디에도 남지 않습니다.
- 충돌 검토에서 채택(`resolution`)·보류는 `kb_conflicts`에 `resolved_by`/`resolved_at`으로 남지만,
  **문서 본문 편집은 그 옆에서 아무 기록 없이 일어납니다.**
- ⑤(S4) 기능이 "오래된/틀린 지식을 고친다"는 목적인데 **고친 행위 자체가 추적되지 않는** 모순.

### 고려사항 (설계의 핵심 갈림길)
요구 문언("언제 누가 어떤 **항목**을 수정했는지")은 **필드 단위 기록**으로 충족됩니다. 다만
지식베이스의 목적상 **이전 본문을 보고 되돌리는 것**까지 필요한지가 규모를 크게 가릅니다.

| 방식 | 답할 수 있는 것 | 못 하는 것 | 규모 |
|---|---|---|---|
| **A. 감사 로그만** (`knowledge.document_updated` + 변경 필드명) | 언제·누가·어떤 항목 | 이전 값, 되돌리기, 차이 보기 | 소 |
| **B. 스냅샷 이력 테이블** | 위 전부 + 이전 본문·차이·되돌리기 | — | 중 |
| **C. A + B 병행** | 전부. 작업로그(`/work-log`)와 문서별 이력이 각각 자연스러움 | — | 중 |

- **저장 비용은 제약이 아닙니다** — 230건 평균 242자, 전체 54KB. 편집마다 전문을 저장해도 미미합니다.
- 이력은 **retention 퍼지 대상이 아니어야** 합니다(대화 로그와 수명이 다름).
- 이력에 고객 PII가 섞일 여지는 낮으나(정책 문서), 열람 권한은 편집 권한(`KNOWLEDGE_SOURCE_MANAGE`)과
  동일하게 두는 것이 자연스럽습니다.
- **소급 불가** — 이번 구현 이전의 편집 이력은 복원할 수 없습니다. 시작 시점부터 쌓입니다.

## 4. 공통 관찰

1. **세 요구가 한 화면(`/knowledge`)에서 이어집니다** — 실패 쌍을 보고(①) → 문서를 나란히 고치고(②)
   → 누가 고쳤는지 남는다(③). 각각 따로 붙이면 화면이 분절되므로 **한 흐름으로 설계**해야 합니다.
2. **③은 지식 도메인 전체에 걸립니다** — 충돌 화면뿐 아니라 문서 목록·상세·QA 패널의 편집,
   생성·삭제·활성 토글까지 같은 기록 대상입니다. 충돌 화면에만 붙이면 반쪽입니다.
3. 기존 `/work-log`(S2)가 이미 **감사 추적의 렌즈**로 동작하므로, ③을 감사 기반으로 만들면
   상담원 작업로그와 **같은 화면에서 지식 편집까지** 조회됩니다.

| E2 | 되돌리기(restore) 제공 여부 | 제공 / 보기만 | **제공** — 되돌리기 없는 이력은 사고 시 수작업 복원 |
| E3 | 이력 기록 범위 | 충돌 화면 편집만 / **지식 도메인 전체**(생성·수정·삭제·활성토글·검토완료) | **전체** — 반쪽 이력은 신뢰할 수 없음 |
| E4 | 판정 실패 쌍 처리 | 저장 안 함(현행) / **실패 상태로 저장** / 검토 큐에 함께 노출 | **실패 상태로 저장** + 검토 큐와 분리 표시. 재스캔 낭비 제거 |
| E5 | 실패 쌍 재시도 정책 | 영구 포기 / **N회 후 중단 + 수동 재시도** / 매번 재시도 | **3회 후 중단 + 수동 재시도 버튼** |
| E6 | 충돌 화면 편집 방식 | 모달 유지 / **카드 내 인라인 편집** / 좌우 분할 편집기 | **카드 내 인라인** — 비교 맥락 유지가 요구의 핵심 |
| E7 | 편집 후 재판정 | 수동 전체 스캔 / **해당 쌍만 재판정 버튼** | **해당 쌍만 재판정** |
| E8 | 발췌 400자 | 유지 / **전문 표시(접기)** | **전문 + 접기** — 최대 914자라 부담 없음 |
