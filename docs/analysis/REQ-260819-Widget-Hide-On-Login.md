# REQ-260819-Widget-Hide-On-Login

로그인 화면에서 챗위젯이 노출되지 않아야 한다.

- 작성일: 2026-08-19
- 대상: tenant 3 `amoebaorder` / `https://amoebaorder.cafe24.com/` (Cafe24 클래식몰)
- 요청: "cafe24 용 챗위젯 - 로그인시 챗위젯은 hide 되어야 한다"
- 관련: `REQ-260819-Cafe24-Login-Amoebaorder.md`, `FIX-260819-Cafe24-Mall-Tenant-Binding.md`

## 1. AS-IS (실측)

`https://amoebaorder.cafe24.com/member/login.html`을 열어 DOM을 확인했다.

```
#ivy-talktalk-frame  →  존재함 (96×96, fixed, 우하단)
```

로그인 폼 위에 챗 런처가 그대로 떠 있다.

로그인 흐름의 다른 페이지도 확인했다.

| 페이지 | 위젯 |
|---|---|
| 몰 스킨 `/member/login.html` | **뜬다** ← 문제 지점 |
| Cafe24 시스템 `/api/v2/oauth/authorize` | 안 뜬다 (스킨이 적용되지 않는 페이지) |
| 우리 API `customer-auth/start`·`callback` | 안 뜬다 (다른 origin) |

즉 **로그인 흐름 전체에서 위젯이 뜨는 지점은 몰 스킨 로그인 페이지 하나**다. 고칠 곳도 하나다.

## 2. 왜 이게 단순한 미관 문제가 아닌가

### 2-1. redirect 복귀가 조용히 깨진다 ⭐

`embed.js`는 로그인으로 나가기 전에 `sessionStorage['ivy:reopen'] = 'orders'`를 남기고,
복귀한 페이지에서 그 값을 **읽고 지운 뒤** 위젯을 주문탭으로 다시 열어준다.

문제는 이 읽고-지우기가 **스크립트가 실행되는 모든 페이지에서** 일어난다는 것이다.
로그인 페이지도 같은 몰 호스트라 스크립트가 실행된다.

```
상품페이지  set 'orders'
   ↓
로그인페이지  ← 여기서 플래그를 소비해버린다 (로그인 화면 위에서 위젯이 주문탭으로 열림)
   ↓
authorize → callback → 원래 페이지 복귀
   ↓
복귀 페이지  플래그 없음 → 위젯이 열리지 않는다
```

로그인 티켓 교환은 성공하는데 **위젯은 닫힌 채로 돌아온다.** 로그인하고 돌아오면 주문이
보이게 하려고 만든 기능이, 로그인 페이지가 같은 몰에 있다는 이유만으로 무력화된다.
이 결함은 화면에 오류로 나타나지 않아서 "로그인이 또 안 됐나?"로 보인다.

### 2-2. popup 모드에서는 팝업 창 안에 위젯이 뜬다

popup 모드는 480×720 팝업에서 `start → authorize`를 태우는데, 회원이 로그인돼 있지 않으면
Cafe24가 그 팝업을 **몰 로그인 페이지로** 보낸다. 그 페이지에서 스크립트가 또 실행된다.

`embed.js`에는 팝업 안에서는 위젯을 띄우지 않는 가드가 이미 있지만 —

```js
if (window.name === 'ivy_auth_popup' && window.opener && …) { … return; }
```

— Cafe24 팝업의 이름은 `ivy_cafe24_auth`다. **가드가 Shopify 팝업 이름만 검사한다.**
Cafe24 팝업은 걸리지 않는다.

### 2-3. 로그인 화면에서 게스트 세션이 생긴다

위젯이 뜨면 신원 응답(비로그인)을 받고 게스트 세션을 연다. 로그인하러 온 사람에게
익명 대화가 하나 열리는 셈이고, 로그인 직후 세션이 교체되므로 그 대화는 버려진다.

## 3. TO-BE

로그인 화면에서는 **위젯을 아예 mount 하지 않는다.**

"숨긴다(`display:none`)"가 아니라 "만들지 않는다"여야 하는 이유가 있다.

- iframe이 로드되지 않아야 게스트 세션이 생기지 않는다 (§2-3)
- 스크립트가 **reopen 플래그를 건드리기 전에** 빠져나가야 복귀가 살아난다 (§2-1)

즉 판정은 `embed.js` 최상단, 플래그를 읽기 전에 있어야 한다.

## 4. 제약

| # | 제약 | 함의 |
|---|---|---|
| C-1 | `embed.js`는 테넌트 설정을 모른다 — 설정은 위젯 iframe이 API에서 받아온다 | 경로 판정은 embed.js 로컬 규칙이어야 한다. 서버에 물어보면 왕복 동안 위젯이 먼저 떠서 깜빡인다 |
| C-2 | 몰 스킨은 편집돼 있을 수 있고 커스텀 도메인도 가능 | 기본 규칙 + `IVY_WIDGET_CONFIG` 오버라이드가 필요하다 |
| C-3 | 몰 스킨을 다시 건드리지 않고 적용돼야 한다 | `embed.js`는 우리 origin에서 서빙되므로 **위젯 재배포만으로 전 테넌트에 적용**된다 |
| C-4 | 로그인 페이지 경로는 플랫폼마다 다르다 | Cafe24 `/member/…`, Shopify `/account/login` |

## 5. 범위 판단이 필요한 것

| # | 질문 | 제안 |
|---|---|---|
| S-1 | 로그인 페이지만인가, 회원가입·아이디/비번 찾기도인가 | **같이 숨긴다.** 전부 신원 입력 화면이고 위젯이 폼을 가린다 |
| S-2 | `/member/` 아래 약관·개인정보처리방침도인가 | **숨기지 않는다.** 읽다가 문의할 수 있는 페이지다 |
| S-3 | Shopify(`/account/login`)도인가 | **같이 적용한다.** §2-1 플래그 소실은 Shopify에서도 동일하게 성립한다 |
| S-4 | 로그인 **후**에도 숨기나 | **아니다.** 요청은 로그인 화면에 대한 것이고, 로그인한 회원이야말로 주문 문의 대상이다 |

## 6. 확인하지 못한 것

- 몰 스킨이 커스터마이즈된 다른 테넌트에서 로그인 경로가 표준과 다른지 (C-2 오버라이드로 대응)
- popup 모드 실동작 — tenant 3 자격증명이 아직 잘못돼 있어 `start`가 실패한다
  (`FIX-260819` §8). 재연결 후 확인 필요
