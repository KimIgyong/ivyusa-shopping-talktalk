## 1. AS-IS — 두 개의 상품 저장소

F1 작업은 `products_cache`를 **표시 전용**으로 명시 설계했습니다(엔티티 주석: *"Display data only — the KB `doc_group='product'` documents remain the recommendation/RAG source"*). 즉 이번 요구는 **설계 위반이 아니라, 그 주석이 예고한 다음 단계**입니다.

| | `products_cache` (F1, 표시용) | `kb_documents` `doc_group='product'` (RAG용) |
|---|---|---|
| 건수 | **2,275** (전부 active) | **144** |
| 출처 | 스토어프론트 공개 `/products.json` (Admin API 스코프 불필요) | 운영자 업로드 CSV |
| 동기화 | 자동 6시간(`PRODUCT_SYNC_INTERVAL_MIN=360`) | 수동 업로드 |
| 본문 | HTML 제거 평문, 2,000자 상한, **평균 658자** | 정제 문서, **평균 1,894자** (`Brand:` / 상세 / `How to use:` / `Tags:`) |
| 벡터 색인 | ❌ 없음 | ✅ Qdrant |
| 링크 | `product_url` | `source_url` → 인용에 실제 링크로 노출(검증됨) |

**조인 키는 이미 검증됨** — KB 상품문서 144건이 **전부**(144/144) 카탈로그 `handle`과 일치합니다. 즉 두 저장소는 이미 같은 열쇠를 쓰고 있고, 중복 생성 없이 합칠 수 있습니다.

## 3. 갭 분석

### 3-1. 커버리지 — 핵심 갭
144 / 2,275 = **6.3%**. §0의 립 제품 사례가 정확히 이 갭입니다. 나머지 93.7%는 존재하지만 AI에게는 **없는 상품**입니다.

### 3-2. 문서 품질 등급 차이
사람이 정제한 144건(1,894자, 사용법 포함) vs 카탈로그 자동 본문(658자, 마케팅 카피). 카탈로그 쪽이 **더 나쁘지는 않지만 균질하지 않습니다.**
→ 자동 생성분이 **기존 정제 문서를 덮어쓰면 품질 후퇴**입니다. 원본 구분(`source`)과 우선순위 규칙이 필요합니다.

### 3-3. 변형(variant) 군집 — 그대로 넣으면 바로 문제
제목 앞 28자가 같은 **260개 제품군에 1,048행**(카탈로그의 46%)이 몰려 있습니다. 색상·사이즈만 다른 압 네일 세트가 대표적입니다.

- **검색 슬롯 잠식**: top-K 6이 같은 제품의 6개 색상으로 채워지면 추천의 폭이 사라집니다.
- **충돌 스캐너 폭증**: 후보 임계 `CANDIDATE_THRESHOLD = 0.85`인데 변형끼리는 거의 1.0입니다. 판정 상한이 스캔당 40건이라, 상품군이 들어오면 **판정 예산 전부를 "같은 제품의 다른 색"에 소모**합니다(230건 코퍼스에서도 중복 28건이 잡혔던 기능입니다).

### 3-4. 가격·재고의 실시간성
가격은 KB 본문에 넣지 않는 원칙이 이미 있습니다(변하면 조용히 낡고, 틀린 가격은 오타가 아니라 분쟁). 카탈로그 변환에도 **동일 적용**하고, 가격·재고는 `products_cache` 실시간 조회로 유지해야 합니다.

### 3-5. 단종·품절 전파
카탈로그 동기화는 사라진 상품을 `archived`로 바꿉니다(하드 삭제 안 함). **KB 문서에 이 상태가 전파되지 않으면 단종품을 계속 추천**합니다. `archived → kb_documents.active = 0`이 필요합니다.

### 3-6. 분류축 불일치
KB 상품문서의 `category`는 **브랜드**(Arocell, LUNA), 카탈로그는 **product_type**(False Nails …)이며 39.5%가 결측입니다. 카테고리 네비게이터·통계(문서/카테고리 렌즈)가 두 체계로 갈라집니다. → **브랜드(vendor) 축 권장**(결측 0, 45개로 적정).

### 3-7. 코퍼스 균형 역전
현재 상담 230 : 상품 144(38%). 전량 투입 시 상담 230 : 상품 2,275(**91%**)로 뒤집힙니다. 그룹 선호는 **가산점이지 필터가 아니며**, 의도 분류가 `fallback`이면 선호 자체가 없습니다. 배송·환불 질문이 상품 문서에 밀릴 위험 → **그룹별 슬롯 쿼터** 검토 필요(예: top-K 6 = 상담 최소 2 + 상품 최대 4).

### 3-8. 언어
카탈로그 본문은 영문 전용이고 KB에는 언어 컬럼이 없습니다. ko/es 질문은 **교차언어 임베딩(voyage-4)에 의존**합니다 — 현재도 그렇게 동작 중이라 신규 리스크는 아니나, 한국어 상품 질문의 정확도는 실측 대상입니다.

### 3-9. 모더레이션 표면 확대
상품 카피에는 *"heals dry, cracked lips"*, *"powerful anti-aging"*, *"clinically shown to reduce pore volume by 32%"* 같은 표현이 있고, 테넌트 규칙에는 **"의료·법률 조언 또는 검증 불가 환불 약속 차단"**(context/LLM 판정)이 있습니다.
현재 144건 기준으로는 **차단 없이 통과**함을 실증했으나, 2,275건으로 늘면 표면이 16배가 됩니다. 차단은 조용한 무응답으로 나타나므로 **투입 후 모더레이션 차단율 모니터링**이 필요합니다.

| **ㄴ. 제품유형별 공통 사용법 (권장)** | "압온 네일 붙이는 법", "시트마스크 사용법"처럼 **유형 단위 사용법 문서**를 상담지식(`counsel`)으로 수십 건 등록. 상품 문서는 Detail만 담고, 추천 시 두 문서가 함께 검색되어 모델이 조합 | **수십 건 작성** | 적정기술 관점 최적 — 실제로 사용법은 제품이 아니라 **유형**에 붙는 지식 |
| ㄷ. Shopify 메타필드 | `read_products` 스코프 추가 승인 후 Admin API로 수집 | 파트너 승인 + 개발 | **데이터 존재 미확인**(상품 페이지에 렌더링조차 안 됨) — 헛수고 위험 |
| ㄹ. LLM 생성 | 모델이 사용법을 지어냄 | 적음 | **비권장** — 화장품 사용법 환각은 안전·분쟁 이슈 |

**ㄴ + ㄱ(상위 판매 제품 한정) 병행**을 권장합니다. 유형 사용법으로 바닥을 깔고, 판매 상위 품목만 개별 사용법을 CSV로 보강하는 방식입니다.

> 검색 관점에서 ㄴ이 성립하는 근거: RAG는 top-K **6건**을 함께 넘기므로, "이 립오일 어떻게 발라요?" 질문에 **상품 문서(Detail) + 유형 사용법 문서**가 동시에 인용될 수 있습니다. 한 문서에 모든 게 들어 있을 필요가 없습니다.

### B안 변환 규칙 (초안)

```
kb_documents (doc_group='product', external_key=handle, source='product_catalog')
  title    = products_cache.title
  category = products_cache.vendor          (브랜드 축 — §3-6)
  content  = title
             + "\n" + description           (HTML 제거 평문, 가격 제외)
             + "\nTags: " + tags            (속성 사전)
  source_url = product_url
  active   = (status = 'active')
```
- **군집 대표**: 제목 정규화 키가 같은 행은 대표 1건만 문서화하고, 나머지 변형은 대표 문서의 태그로 흡수(예: `Variants: This Luv, Baby Doll, …`).
- **우선순위**: 같은 handle에 사람이 만든 문서(`source='knowledge_store'`)가 있으면 **덮어쓰지 않음**. 카탈로그분은 신규 handle만 생성, 기존은 링크·활성상태만 갱신.
- **충돌 스캔**: `doc_group='product'`은 기본 제외(상담 지식의 사실 상충 검출이 원래 목적).
