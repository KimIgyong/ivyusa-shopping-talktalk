# PLN-260819-Login-Wrong-Store-Hint

로그인이 반복 실패할 때 "상점 주소가 맞는지" 힌트를 띄운다.

- 작성일: 2026-08-19
- 승인: 사용자 in-chat("로그인 힌트 개선 진행해줘"). 제안 내용 그대로 구현
- 발단: 한 운영자 계정이 **자기 상점이 아닌 상점의 로그인 주소**에서 시도 → 그 계정은
  해당 상점에 없으므로 성공 불가능 → 그 시도들이 잠금 카운터를 소모 → 5회 도달 시 429
  (구체적 계정·상점은 감사 로그에만 두고 문서에는 남기지 않는다)

## 1. 문제

로그인은 URL 슬러그로 테넌트를 정한다(`/<slug>` → `tenant_slug`). 다른 상점 계정으로
접속하면 **비밀번호가 맞아도 절대 성공하지 않는데**, 화면은 그냥 "자격 증명이 올바르지
않습니다"만 보여준다. 사용자는 비밀번호를 의심하며 재시도하고, 15분/5회 잠금에 걸린다.

## 2. 설계 원칙 — 계정 존재 여부를 흘리지 않는다

"이 이메일은 이 상점에 없습니다"는 **테넌트 간 계정 열거**를 허용한다. 그래서:

- 힌트는 **실패 횟수만으로** 뜬다. 서버가 준 실패 사유를 절대 참조하지 않는다.
- 문구는 비밀번호 오류든 상점 불일치든 **완전히 동일**하다.
- 사용자가 이미 아는 사실(지금 어느 상점 화면인지)만 다시 말해준다.

즉 이 힌트는 새 정보를 주지 않는다. **이미 화면에 있던 정보를 실패한 시점에 다시
들이미는 것**이고, 그게 이번 사고에서 부족했던 전부다.

## 3. 와이어프레임

### 3-1. 평상시 (변경 없음)

```text
┌────────────────────────────────┐
│            ✦                   │
│         amoebaorder            │  ← 상점명(기존)
│          ShopTalk              │
│  ┌──────────────────────────┐  │
│  │ 이메일  [            ]   │  │
│  │ 비밀번호[            ] 👁 │  │
│  │ ☐ 아이디 저장            │  │
│  │ [       로그인        ]  │  │
│  └──────────────────────────┘  │
└────────────────────────────────┘
```

### 3-2. 2회 실패 후 — 힌트 추가

```text
┌────────────────────────────────┐
│            ✦                   │
│         amoebaorder            │
│          ShopTalk              │
│  ┌──────────────────────────┐  │
│  │ ⚠ 로그인이 계속 실패하나요?│  │ ← 신규 (amber, role="status")
│  │   지금 접속한 상점은      │  │
│  │   **amoebaorder** 입니다. │  │
│  │   다른 상점 계정이라면    │  │
│  │   해당 상점 주소로        │  │
│  │   접속해야 합니다.        │  │
│  │   shoptalk.amoeba.site/…  │  │
│  ├──────────────────────────┤  │
│  │ 이메일  [            ]   │  │
│  │ 비밀번호[            ] 👁 │  │
│  │ [       로그인        ]  │  │
│  └──────────────────────────┘  │
└────────────────────────────────┘
```

### 3-3. 429 잠금 — 같은 힌트 + 잠금 안내

```text
│  │ ⛔ 시도가 너무 많습니다.   │  │ ← red, 잠금 전용 문구
│  │   잠시 후 다시 시도하세요. │  │
│  │                           │  │
│  │ ⚠ 지금 접속한 상점은       │  │ ← 힌트는 그대로 유지
│  │   **amoebaorder** 입니다.  │  │
```

⚠️ 잠금 문구에 **남은 시간을 표시하지 않는다.** 서버가 `Retry-After`를 주지 않고,
추측한 숫자를 보여주면 그게 더 나쁜 안내가 된다.

## 4. 구현

| # | 내용 |
|---|---|
| S1 | `TenantLoginPage`에 `failCount` / `rateLimited` 상태. 로그인 실패 시 `failCount+1`, 에러 `code === 'E1008'`이면 `rateLimited` |
| S2 | `LoginTroubleHint` 컴포넌트 신규 — 상점명·슬러그를 받아 렌더. `failCount >= 2 \|\| rateLimited`일 때만 |
| S3 | 성공 시 상태 초기화(불필요하지만 MFA 단계 이동 시 잔상 방지) |
| S4 | 429 토스트를 코드 기준 로컬라이즈 — 지금은 백엔드 영문이 그대로 뜬다 |
| S5 | i18n 6개 언어 |
| S6 | 관리자 로그인(`/admin/login`)에는 **넣지 않는다** — 상점 개념이 없다 |

## 5. 사이드 임팩트

| 영역 | 영향 |
|---|---|
| 백엔드 | **없음.** 서버 동작·잠금 정책 모두 그대로 |
| 보안 | 계정 열거 경로 추가 없음(§2) |
| 관리자 로그인 | 무변경 |
| SSO 배너 | 기존 배너와 세로로 공존 |

## 6. 하지 않는 것

- 잠금 임계값(5회/15분) 조정 — 이번 사고의 원인이 아니다
- 잠금 키를 테넌트별로 분리 — 이메일 단위 보호가 의도된 설계다
- "이 계정은 다른 상점에 있습니다" 안내 — §2 위반
