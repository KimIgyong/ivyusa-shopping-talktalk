## 1. 작업

### P0-1 집계 스케줄러 (D-1)

| 파일 | 변경 |
|---|---|
| `analytics/question-stats.service.ts` | `OnModuleInit` — 부팅 5분 뒤 1회 + `QUESTION_STATS_INTERVAL_HOURS`(기본 24) 주기. **부팅 시 최근 `QUESTION_STATS_BACKFILL_DAYS`(기본 7)일 중 비어 있는 날을 채움** |
| `env/backend/.env.*`, `docker/**/.env*.example` | 새 변수 2개 (env:check 게이트가 템플릿 누락을 잡음) |

**어제 하루만 돌리지 않고 결손을 메웁니다.** 스테이징에서 8/23이 통째로 비어 있고 테넌트 5·6이
8/19에 멈춰 있었던 것은 "누가 수동으로 돌렸는가"의 흔적입니다 — 하루치만 도는 스케줄러였다면
그 구멍은 영원히 남습니다.

`0` 이하면 비활성(리텐션 스케줄러와 동일 규약).

### P0-2 대시보드에서 미리보기 제외 (D-2)

`dashboard()`의 대화 카운트 4종(`activeChats`·`totalEnded`·`unresolvedTopN`·`totalConversations`)에
대화 검색이 이미 쓰는 것과 **같은 조건**을 적용합니다.

```sql
NOT EXISTS (SELECT 1 FROM sessions ps WHERE ps.id = c.session_id AND ps.channel = 'preview')
```

### P0-3 해결 정의 일원화 (D-3)

| 파일 | 변경 |
|---|---|
| `global/util/resolution.util.ts` | 신규 — `classifyOutcome` + 사유 상수를 여정 리포트에서 이관 |
| `journey/journey-metrics.service.ts` | 이관된 함수를 import (동작 무변화) |
| `analytics/analytics.service.ts` | `aiResolutionRate`를 같은 정의로 계산 |

`classifyOutcome`의 인자를 `messages[]` → **`lastNonSystemSender`** 로 바꿉니다. 판정에 실제로
쓰이는 값이 그것 하나이고, 대시보드가 전체 메시지를 읽지 않고도 같은 정의를 쓸 수 있게 됩니다.
배열을 넘기는 형태로 두면 "마지막 비-시스템 발화자만 본다"는 사실이 호출자 쪽 가정으로 남고,
나중에 함수가 다른 걸 보기 시작하면 두 화면이 조용히 갈라집니다.

**대시보드 해결률 숫자가 바뀝니다**(스테이징 기준 11% → 재계산값). 화면에 정의를 한 줄 붙이고
RPT에 이전/이후를 남깁니다.

### P0-4 집계 신선도 노출 (D-1)

`GET /analytics/questions` 응답에 `lastAggregatedAt`(최신 `stat_date`)와 `staleDays`를 싣고,
`/statistics` 상단에 **2일 이상 밀리면 경고 줄**을 띄웁니다.

```
⚠ 집계가 3일 밀려 있습니다 (마지막 2026-08-23). 표의 숫자는 그 시점 기준입니다.
```

## 3. side-impact

- **스키마 변경 없음**
- 대시보드 해결률·대화 수가 바뀝니다(미리보기 제외 + 정의 변경). 이전 값과 비교 중인 사람이
  있으면 혼란이 되므로 RPT에 전/후를 남기고 화면에 정의를 적습니다
- 여정 리포트는 **값이 바뀌지 않습니다**(같은 함수를 옮기기만 함) — 스펙으로 고정
- 스케줄러는 API 컨테이너 1개에서만 돕니다(현재 단일 인스턴스). 다중화되면 중복 실행이
  가능하지만 `aggregateDay`는 upsert라 결과가 같습니다
- 부팅 시 결손 보정은 최대 7일치 → 첫 부팅에서 수 초~수십 초. 5분 지연 후 실행이라 부팅 자체는
  영향 없음
