## 0. 이 설계가 만드는 것

```
       [ 스토어프론트 /products.json ]         [ 운영자 CSV (144건, 사용법 보유) ]
                    │ 6h 동기화                            │ 수동 업로드
                    ▼                                      ▼
            products_cache 2,275                    kb_documents (curated)
             (+ sku  ← P0)                                 │
                    │                                      │ 우선순위: 사람이 만든 문서 불가침
                    │ P1 변환 (변형군 대표화)                 │
                    └──────────────► kb_documents(doc_group='product') ◄──┘
                                             ≈1,445건
                                                │
                        P2 ─► 유형별 사용법 문서 10~12건 (같은 그룹)
                                                │
                                     RAG top-K 6 = 상품문서 + 사용법문서 조합
```

**핵심 설계 판단**: 사용법을 상품마다 채우지 않습니다. RAG는 문서 6건을 함께 넘기므로, "이 립오일 어떻게 발라요?"에는 **상품 문서(Detail) + 유형 사용법 문서**가 같이 인용되면 충분합니다. 한 문서가 모든 걸 담아야 한다는 제약이 애초에 없습니다.

## 1. 실측 기반 규모 (2026-08-07, 스토어프론트 전량 조사)

| 항목 | 값 |
|---|---|
| 카탈로그 | 2,275건 |
| **변형군 흡수 후 문서 수** | **≈1,445건** (정규화 제목 첫 5단어 기준, 256개 군에 흩어진 1,038행을 대표 1건으로) |

## 2. 단계별 계획

### P0 — SKU 수집 (스키마 + 동기화)

| 항목 | 내용 |
|---|---|
| 변경 | `products_cache.sku VARCHAR(64) NULL` 추가 + `idx_prdc_sku(tenant_id, sku)` |
| 동기화 | `variants[]`에서 **첫 번째 비어있지 않은 sku** 채택 (원본 2,275/2,275 보유, 빈 값 29건) |
| 노출 | 상품 상세 응답(`product.response.ts`)에 `sku` 추가 — 상담원이 재고·주문 대조에 사용 |
| **비적용** | **KB 문서 본문에는 넣지 않음.** 기존 CSV 임포터가 SKU를 키로도 본문으로도 쓰지 않는 이유와 동일 — 공급 CSV에서 7건 공백·8건 중복이라 식별자로 신뢰할 수 없음(`product-import.service.ts` 주석) |
| 마이그레이션 | `sql/migration_products_sku.sql` — additive, **코드보다 먼저 적용** |

### P1 — 카탈로그 → 상품지식 변환기 (핵심)

**변환 규칙**

```
문서 1건 = 변형군 1개
  external_key = 대표 handle
  title        = 대표 상품 title
  category     = vendor                     ← 브랜드 축 (결측 0, 45개)
  source       = 'product_catalog'          ← curated 문서와 구분되는 새 값
  source_url   = 대표 product_url
  active       = (군 내 active 상품이 1건이라도 있으면 1)
  content      = title
               + "\n\n" + description       ← HTML 제거 평문, 가격 없음
               + "\nTags: " + tags
               + "\nVariants: " + 변형명 상위 20개 + " 외 N종"   (군 크기 > 1일 때만)
```

- **대표 선정**: 군 내에서 ① description 최장 → ② handle 사전순 (동률 시 안정적·재현 가능)
- **curated 불가침**: 같은 `external_key`에 `source != 'product_catalog'` 문서가 있으면 **본문을 덮어쓰지 않고** `source_url`·`active`만 갱신
- **보류**: description 80자 미만 **AND** 태그 없음 → 3건, 문서 생성하지 않고 리포트에 표기
- **임베딩**: `embedDocuments()` 64건 배치 재사용 (단건 경로 금지 — PR #95 실패 형태)
- **충돌 스캔 제외**: `kb-conflict.service`의 스캔 대상에서 `doc_group='product'` 제외. 변형끼리 유사도가 거의 1.0이라 스캔당 판정 40건 예산을 "같은 제품의 다른 색"에 전부 소모함

**실행 방식**: 콘솔 버튼 → **미리보기(dry-run) → 승인 → 실행**. 자동 상시 동기화는 P3.

### P2 — 유형별 사용법 문서

| 항목 | 내용 |
|---|---|
| 저장 | `doc_group='product'`, `category='How to Use'` — 상품 그룹 가산점을 함께 받아 상품 질문에서 같이 검색됨 |
| 초기 세트 | 압온 네일 · 네일 폴리시/젤 · 스트립/클러스터 속눈썹 · 속눈썹 접착제 · 헤어 컬러 · 가발/헤어피스 · 스킨케어(세럼/앰플/마스크/클렌저) · 메이크업(립/컨실러/마스카라) · 헤어브러시 · 프래그런스 — **10~12건** |
| 작성 주체 | **IVY/운영자** (내용은 도메인 지식). 우리는 템플릿·등록 화면·유형 매핑 제공 |
| 매핑 | 상품 → 유형은 `product_type`(90종) + 태그 키워드 규칙. 결측 899건은 태그로 유추 |
| 검증 | "이거 어떻게 써요?" 질문에 **상품 문서 + 사용법 문서가 동시 인용**되는지 실측 |

### P3 — 상태 전파 · 재동기화

- 카탈로그 동기화가 상품을 `archived`로 바꾸면 → 대응 KB 문서 `active = 0` (**삭제 아님** — 이력·통계 보존, SPEC §13 하드삭제 정책과 별개로 지식은 비활성 처리)
- 신규 상품 등장 시: 자동 생성하지 않고 **콘솔에 "미반영 N건" 배지** → 운영자가 동기화 실행
- 이유: 자동 생성은 임베딩 호출을 예측 불가능한 시점에 발생시키고(레이트리밋), 사람이 품질을 확인할 기회를 없앰

### P4 — 검색 균형 계측 (필요 시 쿼터)

전환 후 코퍼스는 상담 230 : 상품 ≈1,445(**86%**)가 됩니다. 그룹 선호는 **필터가 아니라 가산점**이고, 의도 분류가 `fallback`이면 선호가 아예 없습니다.

- **먼저 계측**: 배포 후 상담 질문 20종(배송·환불·교환·회원·결제)을 재실행해 인용 문서 구성과 confidence를 P1 이전과 대조
- **회귀가 확인될 때만** 그룹 쿼터 도입(예: top-K 6 = 상담 최소 2 + 상품 최대 4)
- 근거 없이 먼저 손대지 않습니다 — GROUP_BONUS는 이미 "필터가 아니라 가산점"으로 신중히 설계돼 있고, 쿼터는 그 설계를 되돌리는 변경입니다

## 4. 영향 범위 (side-impact)

| 영역 | 영향 | 조치 |
|---|---|---|
| **지식 충돌 스캔** | 변형 유사도 ≈1.0 → 판정 예산 고갈 | `doc_group='product'` **스캔 제외** (P1) |
| **고객질문 통계** | 문서·카테고리 렌즈 축이 브랜드 45종으로 확장 | 그대로 동작, 별도 작업 없음 |
| **카테고리 네비게이터** | 상품지식 카테고리가 144→45 브랜드로 재편 | 기존 CSV 문서의 category도 이미 브랜드라 일관 |
| **RAG 검색 균형** | 코퍼스 86%가 상품 | P4에서 계측 후 판단 |
| **모더레이션** | 상품 카피 표현 표면 16배 | 배포 후 차단율 모니터링 (차단은 무응답으로 보임) |
| **Voyage 레이트리밋** | 23회 배치 호출 | 배치 간 간격, 실패분 재시도 큐 |
| **모바일앱/PWA** | `products_cache`에 컬럼 추가(additive) | 기존 응답 불변, `sku`는 추가 필드 |
| **KB QA 콘솔** | 상품 질문 검증 가능해짐 | 이득 |
| **보존기간 퍼지** | 지식 문서는 대화 retention 대상 아님 | 영향 없음 |

## 8. 구현 순서와 산출물

```
P0 (SKU)  →  P1 (변환기+콘솔)  →  P2 (사용법 문서)  →  P3 (전파)  →  P4 (계측)
   │              │                    │                  │            │
   SQL 선적용     미리보기 필수         운영자 작성        배지 노출     회귀 판단
```

- P0·P1을 **한 PR**로 묶지 않습니다 — P0은 스키마 변경이라 선적용 검증이 따로 필요합니다.
- 각 단계 후 스테이징 배포 → 실측. 특히 **P1 직후 V1·V2를 즉시 측정**합니다(가장 되돌리기 쉬운 시점).
- 산출물: TCR(검증 케이스) → RPT(변경·파일·테스트·배포 상태)

## 9. 승인 요청 사항

이 계획대로 진행할지 확인 부탁드립니다. 특히 아래 3가지는 구현 전에 확정돼야 합니다.

1. **변형군 대표화** — 41개 색상 압 네일이 문서 1건이 됩니다. 색상별 추천이 필요하면 설계가 달라집니다.
2. **P2 사용법 문서 작성 주체** — IVY 측 작성으로 전제했습니다(10~12건). 초안을 우리가 만들고 검수받는 방식도 가능합니다.
3. **P3 자동화 수준** — 신규 상품 자동 문서화는 하지 않고 배지+수동 실행으로 설계했습니다.
