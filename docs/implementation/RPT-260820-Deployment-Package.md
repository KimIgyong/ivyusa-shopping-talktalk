## 1. 왜 필요했나 — 지금 넘겼으면 두 번째 배포에서 데이터가 사라졌다

REQ-260819에서 ivyusa(AWS)·skyliving(Matbao)·go2joy(자체 클라우드)를 **전용 배포**로 정한 뒤,
실제로 넘길 물건인 `docker/production/`을 대조한 결과:

| 발견 | 결과 |
|---|---|
| **업로드 볼륨 없음** | 첨부·로고가 컨테이너에 쓰이고 업그레이드마다 소멸 — **에러가 나지 않는 실패** |
| **위젯 서비스·Dockerfile 없음** | `talk.ivyusa.com`을 서빙할 수단 자체가 없음 |
| **env 템플릿이 87개 중 59개 누락** | `UPLOAD_DIR`·`CORS_ORIGINS` 등. `APP_PUBLIC_URL` 미설정 시 **아메바 스테이징으로 폴백** |
| 마이그레이션 순서·업로드 백업 절차 없음 | 새 코드 + 옛 스키마 = 500 / DB 덤프에 첨부 미포함 |

## 2. 산출물

| 구분 | 내용 |
|---|---|
| 스택 | `docker/self-hosted/` — compose(위젯 + **uploads 볼륨**) · Dockerfile 3 · nginx 3 · env 템플릿 |
| 스크립트 | `gen-secrets` · `deploy-self-hosted` · `check-migrations`(.sh/.mjs) · `backup`/`restore` |
| 게이트 | `npm run env:check` · `migrations:manifest --check` (둘 다 CI) |
| 문서 | `docs/guide/자체호스팅설치가이드_Self-Hosted-Install.ko.md` |

기존 `docker/staging`·`docker/production`은 **유지**했다 — 후자는 결정된 혼합 모델에서
아메바 운영 KR 리전 SaaS(Cafe24 몰용)가 쓸 자리다.

## 3. 설계에서 중요한 판단 4가지

### 3.1 env 템플릿을 손으로 유지하지 않는다
87개를 옮겨 적으면 다음 기능에서 또 어긋난다. 스크립트가 `apps/api/src`를 훑어 대조하고 CI가
막는다. **작성 중에 이미 1건을 잡았다**(`QUESTION_STATS_INTERVAL_HOURS`) — 손으로 했으면
고객사 현장에서 발견됐을 항목이다.

### 3.2 배포 시점 검사는 순수 bash다
고객사 호스트에 Node가 있으리라 가정할 수 없다 — **스테이징 호스트에 없다.** 그래서 SQL 파싱
결과를 `sql/artefacts.tsv`로 커밋하고, 배포 때는 bash + mysql 클라이언트만 쓴다. 매니페스트가
낡으면 "미적용을 적용됐다고 말하는" 최악의 오답이 되므로 CI가 최신성을 강제한다.

### 3.3 스크립트는 SQL을 실행하지 않는다
검출하고 멈춘다(kit 04 §3). 무인 DDL은 나쁜 마이그레이션이 새벽에 프로덕션에 닿는 경로다.

### 3.4 백업은 두 개이고, 복원은 스스로 검증한다
DB만 받으면 "대화는 있는데 사진이 없는" 시스템으로 복원된다. 복원 후 **첨부 행 대비 실파일**을
대조해 어긋나면 실패로 끝낸다(서로 다른 시점의 백업 두 개를 짝지은 경우가 여기서 걸린다).

## 4. 리허설이 잡은 결함 (고객 앞에 가기 전에)

스테이징 호스트에서 격리 프로젝트(`shoptalk-rehearsal`, 포트 8099)로 끝까지 실행했다.

| ID | 결함 | 조치 |
|---|---|---|
| **F-1** | **신규 설치가 부팅하지 못했다.** `init-sql/01-schema.sql`이 5개 테이블 뒤처져 시드가 `Unknown column 'Tenant.widget_tabs'`로 실패 | 그 파일 헤더가 스스로 지시한 대로 스테이징에서 재생성(73테이블). 재리허설에서 신규 설치가 **미적용 0건**으로 시작 |
| **F-2** | **파일명 순서 ≠ 의존성 순서.** `AFTER <컬럼>`이 나중 이름 파일의 컬럼을 참조해 알파벳순 적용이 3건 실패 | 안내를 릴리스 순서로 정정 + "Unknown column이면 그 파일 먼저" + 런북 경고 |
| F-3 | 검증이 컨테이너 이름을 하드코딩 → 부팅한 스택을 "0 boots"로 보고 | `API_CONTAINER` 사용, 부팅 카운트를 합격 조건에 포함 |
| F-4 | Dockerfile이 참조하는 앱 레벨 nginx 설정 2개 누락 | staging에서 이관 |
| F-5 | `DATABASE()`가 NULL이라 검출기가 전부 미적용으로 보고 | DB 명시 |

## 5. 리뷰가 잡은 결함

| 지적 | 왜 실제 문제였나 |
|---|---|
| **`--check`가 파일을 썼다** | nginx가 `widget-config.js`를 호스트 마운트에서 직접 서빙한다 → "아무것도 안 바꾼다"던 점검이 **라이브 위젯의 API 주소를 바꿀 수 있었다** |
| **`RABBITMQ_URL`이 `CHANGE_ME`로 남았다** | 생성기가 비밀번호만 출력하고 URL 반영은 사람에게 맡겼다 → RabbitMQ는 새 비번, API는 옛 URL |
| **복원이 API 정지를 사람에게 맡겼다** | 복원 중 들어온 대화·첨부가 정합성 검사를 깨뜨린다 → 스크립트가 직접 정지·복원·기동 |
| 콘솔 상태를 수집만 하고 미검사 | web이 502여도 `Deployed.` |

**미반영(백로그)**: 베이스 이미지 digest 고정, 비root 실행. 둘 다 타당하지만
`docker/staging`·`production`과 함께 정해야 할 **리포 전체 정책**이고, 새 파일에만 적용하면
세 스택의 관행이 갈린다.

## 6. 검증 (R-1~R-5 전부 통과)

| ID | 결과 |
|---|---|
| R-1 | 빈 상태 기동 → health ok · `/widget/` 200 · `/` 200 · 시드 성공 · `successfully started` |
| R-2 | **첨부 업로드 → API 강제 재생성 → sha256 동일** (이 패키지의 존재 이유) |
| R-3 | 백업 → 볼륨 비우기 + 행 삭제 → 복원 → **sha256 동일**, 파일 없는 행 0 |
| R-4 | 미적용 SQL이 있으면 배포가 멈추고 목록을 보여준다 |
| R-5 | placeholder 시크릿 → `Refusing to start in production with insecure secrets` |

리허설 환경(컨테이너·볼륨·이미지)은 정리했고 기존 스테이징에 영향이 없다. 리뷰 반영 후 바뀐
복원 경로는 별도 볼륨으로 재검증했다.

## 8. 예방 패턴 (일반화)

- **템플릿은 손으로 유지하면 반드시 어긋난다.** 코드가 진실이면 코드에서 생성하고 CI로 막아라.
  이번엔 작성 중에 이미 1건이 빠졌다.
- **리허설은 "되는지"가 아니라 "처음부터 되는지"를 봐야 한다.** 두 번째 실행은 이미 만들어진
  스키마 위에서 돌아 F-1을 숨긴다. 볼륨까지 지우고 다시 해야 신규 설치가 검증된다.
- **알파벳 순서를 의존성 순서로 착각하지 마라.** `AFTER <컬럼>`이 있는 마이그레이션 모음은
  이름순으로 적용되지 않는다.
- **"~하세요"라고 문서에 쓴 수동 절차는 스크립트가 대신할 수 있으면 대신해야 한다.**
  RabbitMQ URL도 복원 전 API 정지도, 사람에게 맡긴 그 한 줄이 곧 장애 시나리오였다.
- **`--check`/`--dry-run`은 정말로 아무것도 쓰지 않아야 한다.** 한 줄이라도 쓰면 그 플래그를
  믿고 실행한 사람이 라이브 시스템을 바꾼다.
