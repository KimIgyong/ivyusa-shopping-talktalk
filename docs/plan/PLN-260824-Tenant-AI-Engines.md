# PLN-260824-Tenant-AI-Engines

테넌트별 AI 엔진 모델 설정 — 구현 계획

- 근거: `docs/analysis/REQ-260824-Tenant-AI-Engines.md`
- 승인된 결정: D1(b) 신규 capability · D2(a) master만 · D3(b) 테넌트 키 선택 ·
  D4(b) 연결 테스트 선택 · **D5(a) D-2를 이번 작업에서 함께** · D6(a) 어댑터 있는 프로바이더만
- 원칙: **라우팅은 이미 있습니다**(REQ §0). 등록 경로를 열고, 그것이 활성화시키는 결함 2건을 닫습니다.

## 0. 이 작업의 모양

```
지금:   [어드민] ──만든다──> ai_engines(tenant_id=NULL) ──> 모든 테넌트가 공유
        [테넌트] ──연결만──> tenant_ai_settings(기능 → engine_id)

이후:   [어드민] ──만든다──> ai_engines(tenant_id=NULL)   플랫폼 제공(읽기 전용)
        [테넌트] ──만든다──> ai_engines(tenant_id=<나>)   내 엔진 (복수)
                 ──연결──> tenant_ai_settings(기능 → 내 엔진 또는 플랫폼 엔진)

라우팅(무수정): EXPLICIT → INHERITED → TENANT_DEFAULT → PLATFORM_DEFAULT
                                                        ↑ 여기에 tenant_id IS NULL 추가
```

**스키마 변경 없음** — `ai_engines.tenant_id`가 이미 있습니다. 마이그레이션도 없습니다.

## 1. 단계별 계획

### W1 — 백엔드 (PR 1)

**1-1. 결함 2건부터 닫습니다** (D5 — 등록 경로를 열기 전에)
- `ai-gateway.service.ts:158` 플랫폼 기본값 쿼리에 **`tenantId: IsNull()`** 추가.
  없으면 테넌트가 자기 엔진을 기본값으로 거는 순간 다른 테넌트가 그 엔진과 **그 API 키로**
  응답합니다. 회귀 테스트: 테넌트 A의 기본 엔진이 테넌트 B의 폴백에 **선택되지 않는다**.
- `AiEngineService.listEnabled()`를 **테넌트 스코프**로:
  `listEnabledFor(tenantId)` = `내 것 + tenant_id IS NULL`. 어드민 목록은 기존 전체 조회 유지.

**1-2. 테넌트 엔진 CRUD**
- 신규 컨트롤러 `tenant-ai-engine.controller.ts` — `@Controller('tenants/me/ai-engines')`
  - `GET /` 내 엔진 + 플랫폼 엔진(플랫폼은 `readOnly: true`)
  - `POST /` 생성 · `PATCH /:id` 수정 · `DELETE /:id` 삭제
  - `POST /:id/test` 연결 테스트 · `PUT /:id/default` 내 기본값 지정
- **`tenant_id`는 요청 본문에서 받지 않고 `@CurrentUser()`에서 강제**합니다.
  어드민 DTO는 `tenant_id`를 받지만(현행), 테넌트 경로에서 그걸 받으면 남의 테넌트에
  엔진을 심을 수 있습니다.
- 모든 조회·수정은 `where: { id, tenantId }` — **소유 확인을 쿼리에 넣습니다.**
  가져와서 비교하면 한 곳만 빠뜨려도 뚫립니다.
- 삭제 전 `tenant_ai_settings`에서 사용 중이면 **거부**(어떤 기능이 쓰는지 함께 안내).
  쓰던 엔진이 사라지면 그 기능이 조용히 폴백합니다.

**1-3. 권한** (D1·D2)
- `CAPABILITY.TENANT_AI_ENGINE_MANAGE` 신설(`packages/common/rbac/permission-matrix.ts`)
- `RANK_CAPS[MASTER]`에만 추가. director·manager·staff는 받지 않습니다 — API 키를 다루는 설정입니다.
- 기존 `AI_ENGINE_MANAGE`는 **어드민 전역 관리 의미 그대로 둡니다**(재사용하면 경계가 흐려짐).

**1-4. API 키** (C2·D3)
- 저장은 기존 `encryptSecret` 경로. 응답에는 **끝 4자만**(`sk-…a1b2`), 평문 재조회 라우트 없음.
- 키를 비우고 저장하면 **기존 키 유지**(빈 값으로 지우는 사고 방지). 삭제는 별도 동작.
- 키 없이 저장 가능(D3-b) — 그 엔진은 **플랫폼 키로 동작하지 않습니다.** 프로바이더가
  anthropic/openai면 키 없는 엔진은 `status`를 `disabled`로 두고 화면에 사유를 보입니다.

**1-5. 연결 테스트** (D4)
- `POST /:id/test` — 해당 어댑터로 **최소 호출 1회**(짧은 프롬프트, max_tokens 최소).
- 결과를 `ai_engines`에 남기지 않고 응답으로만 돌려주되, 콘솔이 배지로 표시.
  *(상태 컬럼 추가는 스키마 변경이므로 이번 범위 밖 — 화면 세션 동안만 유지)*
- 실패 사유를 4종으로 갈라 표시: 인증 실패 · 모델 없음 · 레이트리밋 · 연결 실패.
  ([[fail-classification-copy]] — 401을 "연결 실패"로 뭉뚱그리면 살아 있는 서버를 죽은 것으로 진단합니다)

**1-6. 프로바이더 범위** (D6)
- 선택지는 **어댑터가 있는 것만**: `anthropic`, `openai`. `custom`·`google`·`azure`는
  어댑터가 없어 저장돼도 동작하지 않으므로 목록에서 제외합니다.
- 서버에서도 검증(화면 목록만 믿지 않음).

**1-7. 테스트**
- 라우팅: 테넌트 기본값 > 플랫폼 기본값, **남의 테넌트 기본값은 선택되지 않음**(회귀)
- 목록 스코프: 내 것 + NULL만
- 소유: 남의 엔진 id로 PATCH/DELETE → 404
- `tenant_id` 스푸핑: 본문에 넣어도 무시
- 사용 중 삭제 거부, 키 빈 값 저장 시 유지, 응답에 평문 키 없음

### W2 — 콘솔 (PR 1에 포함)
- **설정 → AI 엔진** 카드 신설(§2 와이어프레임)
- **AI 설정** 화면의 엔진 선택지는 이제 `내 엔진 + 플랫폼`(D-1 해소 결과가 그대로 반영)
- 어드민 `AiEnginesPage`에 **소유 테넌트 열** 추가(G6)
- i18n **6개 언어** + `npm run i18n:check`
- 모든 저장에 성공/실패 피드백(CLAUDE.md §2 UX MUST)

### W3 — 배포·검증 + 문서 (PR 2 = docs)
- 스키마 변경 없음 → SQL 사전적용 불필요, PR에 "해당 없음" 명기
- 배포 검증 3종 + **내용 검증**: 신규 라우트 401, 테넌트 목록에 남의 엔진이 없음,
  플랫폼 폴백이 NULL 엔진만 고름
- TCR-260824 + RPT-260824 + 메모리 갱신

## 3. 사이드 임팩트

| 영역 | 영향 | 대응 |
|---|---|---|
| **플랫폼 폴백 쿼리** | `tenantId IS NULL` 추가 — **동작이 바뀝니다** | 현재 테넌트 소유 엔진이 0건이라 실질 변화 없음. 회귀 테스트로 고정 |
| `listEnabled()` 소비처 | 어드민 목록과 테넌트 목록이 갈림 | 어드민은 기존 메서드 유지, 테넌트는 신규 `listEnabledFor(tenantId)` |
| `tenant_ai_settings` | 무수정 — 기존 할당 그대로 | `upsert`의 소유 검사(`ai-setting.service.ts:88`)가 이미 맞음 |
| 기존 6개 테넌트 | 전부 플랫폼 엔진 2번 사용 중 | **무회귀** — 내 엔진을 만들기 전까지 아무것도 안 바뀜 |
| permission-matrix | capability 1개 추가 | master만. 32조합 스냅샷 테스트가 있으면 갱신 |
| 어드민 화면 | 소유 테넌트 열 추가 | 표시만 |
| DB 스키마 | **변경 없음** | PR에 Migration "해당 없음" |
| 과금 | 테넌트 키 사용 시 청구 주체가 바뀜 | 모달에 명시(D3), RPT에 운영 안내 |

## 4. 리스크

- **R1.** 폴백 쿼리 수정은 **모든 테넌트의 AI 호출 경로**를 지납니다. 지금은 테넌트 엔진이
  0건이라 결과가 같지만, 잘못 짜면 전 테넌트가 stub으로 떨어집니다 → 배포 후 실제 응답으로 확인.
- **R2.** 키 없는 엔진을 활성으로 두면 **조용히 stub 폴백**이 됩니다([[staging-ai-stub-blockers]]에서
  이미 겪음) → 키 없으면 비활성 + 화면에 사유.
- **R3.** 소유 검사를 서비스에서 하고 쿼리에서 빠뜨리면 한 곳만 놓쳐도 뚫립니다 →
  `where: { id, tenantId }`를 규칙으로.
- **R4.** 연결 테스트가 실제 과금 호출입니다 → 최소 토큰, 그리고 **연타 방지**.
- **R5.** 삭제된 엔진을 쓰던 기능은 조용히 폴백합니다 → 사용 중 삭제 거부(1-2).

## 5. 테스트 (TCR-260824에서 확장)
- 단위: 폴백 테넌트 격리 · 목록 스코프 · 소유 404 · `tenant_id` 스푸핑 무시 ·
  사용 중 삭제 거부 · 키 빈 값 유지 · 응답에 평문 키 없음 · 프로바이더 화이트리스트
- 통합: 내 엔진 지정 → 그 엔진으로 라우팅 · 지우면 플랫폼으로 복귀
- 배포: 신규 라우트 401 · 테넌트 목록에 남의 엔진 없음 · 폴백이 NULL 엔진만 고름
