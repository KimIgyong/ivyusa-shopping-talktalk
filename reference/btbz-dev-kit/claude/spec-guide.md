# Spec·문서 체계 가이드

> **버전**: 1.0 (2026-07-30)
> AMA에서 운영 검증된 프로젝트 문서 체계. Claude가 참조하는 문서의 위치·형식·강제 규칙을 정의한다.

---

## 1. 문서 지형도

```
{project}/
├── CLAUDE.md                     # AI 에이전트 지침 (claude/CLAUDE.md.template)
├── SPEC.md                       # 시스템 명세 정본 — 테이블/API/에러코드
├── spec/                         # 기술 표준 문서 (변경 드묾)
│   ├── CODE-CONVENTION.md        #   ← dev-kit 01 문서를 프로젝트에 복사/치환
│   ├── DEVELOPMENT-STANDARD.md   #   ← dev-kit 02
│   ├── GIT-BRANCH-STRATEGY.md    #   ← dev-kit 03
│   ├── DEPLOYMENT-GUIDE.md       #   ← dev-kit 04
│   └── INFRASTRUCTURE.md         #   서버/네트워크/도메인 구성 (프로젝트 고유)
├── docs/                         # 작업 문서 (일상적으로 생성)
│   ├── analysis/   REQ-{YYMMDD}-{제목}.md
│   ├── plan/       PLN-{YYMMDD}-{제목}.md
│   ├── test/       TCR-{YYMMDD}-{제목}.md
│   ├── implementation/ RPT-{YYMMDD}-{제목}.md
│   ├── bug-fix/    FIX-{YYMMDD}-{제목}.md
│   ├── manual/     MANUAL-{YYMMDD}-{제목}.md   # 사용자 매뉴얼 (다국어 병기 가능)
│   ├── guide/      GUIDE-*.md                   # 운영 가이드 (설정/이관/인프라 절차)
│   └── log/        YYYY-MM-DD/                  # 대화 로그 (.gitignore 등록)
└── sql/                          # DB 마이그레이션 SQL
```

## 2. 요구사항 작업 워크플로우 (REQ → PLN → 구현 → TCR → RPT)

`[요구사항]` 타이틀 요청은 반드시 이 순서로 진행한다:

| 단계 | 문서 | 필수 내용 |
|------|------|----------|
| 1. 분석 | `docs/analysis/REQ-{YYMMDD}-{제목}.md` | AS-IS 현황, TO-BE 요구사항, 갭 분석, 사용자 플로우, 기술 제약 |
| 2. 계획 | `docs/plan/PLN-{YYMMDD}-{제목}.md` | 단계별 구현 계획, 사이드 임팩트 분석, ⚠️ **화면구성도(ASCII 와이어프레임) 필수** |
| 3. 구현 | - | ⚠️ **PLN 사용자 승인 후에만 착수. 자동 구현 금지** |
| 4. 테스트 | `docs/test/TCR-{YYMMDD}-{제목}.md` | 단위 케이스, 통합 시나리오, 엣지 케이스 |
| 5. 보고 | `docs/implementation/RPT-{YYMMDD}-{제목}.md` | 구현 내용, 변경 파일 목록, 테스트 결과, **배포 상태** |

### PLN 화면구성도 규칙 (사용자 확정, 2026-06-11)
- UI가 추가/변경되는 **모든** PLN에 적용 — 신규 페이지, 모달, 섹션, 메뉴 항목.
- 그릴 것: 전체 레이아웃(헤더/사이드바/본문/버튼 위치), 모달 필드+액션, 메뉴 추가 위치, 상태 전환 흐름.
- REQ에 화면구성안이 있어도 **PLN에 반드시 다시 포함** (계획서 단독으로 충분해야 함).
- 백엔드 전용 PLN은 적용 제외 — 단 "UI 영향 없음"을 명시.
- ASCII로 어려운 복잡 UI는 Figma/Excalidraw 링크 + 핵심 설명으로 대체 가능.

## 3. 버그 수정 워크플로우 (FIX)

1. **원인 분석** — 에러 로그/재현 경로 기반 근본 원인 (증상 대증요법 금지)
2. **해결 방안 제시** — 수정 방법과 영향 범위
3. **최소 범위 수정**
4. **보고서** `docs/bug-fix/FIX-{YYMMDD}-{제목}.md` — 증상, 원인 분석, 수정 내용, 변경 파일, **재발 방지 패턴** (→ 일반화 가능하면 메모리/표준으로 승격)

## 4. 대화 로그 · 데일리 리포트

세션 간 연속성을 위해 모든 대화를 로컬 기록한다 (**git 제외** — `.gitignore`에 `docs/log/`).

- **로그**: `docs/log/YYYY-MM-DD/{HH}_{순번}_{작업요약}.md` — 세션 시작 시 생성, 주요 작업 단위마다 갱신. 내용: 요청 원문, 작업 요약, 변경 파일, 이슈/해결, **미완료 항목**.
- **데일리 리포트**: `docs/log/YYYY-MM-DD/DAILY-REPORT.md` — 당일 마지막 세션 종료 시 또는 요청 시. 완료 작업, 변경 파일 전체, 배포 상태, 미해결 이슈/다음 예정.

## 5. SPEC.md 유지 규칙

- 신규 모듈 추가 시 **테이블, API 엔드포인트, 에러코드**를 SPEC.md에 반영 (모듈 체크리스트의 일부).
- ⚠️ **핵심 운영 문서와 historical 문서를 구분**: 포트/도메인 등 운영 값이 바뀌면 CLAUDE.md·SPEC.md·spec/*.md는 **전부 즉시 갱신**하고, 과거 REQ/PLN/RPT는 작성 시점 기록으로 보존(수정하지 않음). AMA에서 포트 변경 후 문서 간 불일치(3009 vs 3019)가 표준 진단 지적 사항이 됐다.
- 표준 문서와 실코드가 어긋나면 방치하지 않고 **어느 쪽이 정답인지 판정 → 한쪽 정정** (AMA V2 진단 §4 방식).

## 6. 문서 작성 일반 규칙

- 파일명 날짜는 `YYMMDD` (예: `REQ-260730-...`). 문서 내부 날짜는 절대 날짜(`2026-07-30`)로.
- 다국어 매뉴얼은 언어 병기 파일 세트로 관리하고 정본 경로를 메모리(`manual_*.md`)에 포인터로 남긴다.
- 완료 보고(RPT)의 "배포 상태"는 구체적으로: PR 번호, 커밋 SHA, 환경별 배포/마이그레이션 여부, 검증 방법 — 이것이 이후 메모리와 재구현 방지의 근거가 된다.
