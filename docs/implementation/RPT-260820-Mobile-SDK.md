## 1. 왜 "웹 SDK를 WebView에 넣으면 된다"가 아니었나

WebView에서는 `window.parent === window`다. 위젯의 호스트 연동은 전부 부모 프레임을 전제로
하고 있어서 **네 개 훅이 모두 즉시 빠져나갔다** — 신원 핸드셰이크 없음, `identify`·`open` 도달
불가. 화면도 그대로 쓸 수 없었다:

| | 그대로 넣었다면 |
|---|---|
| 데모 스토어프론트 | 고객사 앱 안에 함께 렌더 |
| 런처 버튼 | 앱 자체 진입점과 중복해서 떠 있음 |
| 닫기(X) | 패널만 닫혀 **빈 화면**이 남음(앱에서는 위젯이 화면 전체) |

## 2. 만든 것

| 산출물 | 내용 |

| `apps/widget/src/lib/host-bridge.ts` | 호스트 채널 추상화 — 부모 프레임 · RN · WKWebView · Android |

## 3. 설계에서 중요한 판단 3가지

### 3.1 메시지 타입을 웹과 동일하게 유지했다
앱 전용 프로토콜을 만들면 같은 기능이 두 벌이 되고, 웹에서 고친 버그가 앱에 남는다. 브리지는
**채널만** 갈아끼운다. 그래서 `identify`·`open`·`logout`·`ready`가 네 플랫폼에서 같은 모양이다.

### 3.2 계약이 산출물이고 RN은 참조 구현이다
go2joy의 앱 스택을 아직 모른다. 네이티브라도 같은 계약에 스니펫 30줄이면 붙는다. 완성형
Swift/Kotlin SDK를 만드는 척하지 않았다.

### 3.3 닫기는 호스트에 요청한다
앱에서 패널만 닫으면 사용자는 **아무것도 없는 화면**을 본다. `ivy:close-request`를 보내고
패널은 유지한다 — 화면을 닫는 주체는 호스트다.

## 4. 검증이 잡은 결함 2건

| 발견 | 조치 |
|---|---|
| **마운트 전·구독 해제 후 네이티브 호출이 예외**였다 | WebView 안의 예외는 볼 방법이 없다. 앱은 화면 진입과 동시에 `identify`를 보내므로 마운트보다 빠른 것이 **정상**이다 → 전역을 모듈 로드 시 1회 설치하고 큐(20건)를 뒀다(로더 명령 큐와 같은 해법) |
| **앱 모드인데 런처 형상을 보고**하고 있었다 | 시뮬레이터 로그에서 발견 → 앱 모드에서는 보고하지 않는다 |

그리고 CI가 하나 더 잡았다: `packages/shoptalk-rn`이 `packages/*` 워크스페이스에 걸려
**lockfile 갱신 없이는 `npm ci`가 통째로 거부**된다. 로컬은 `npm install`이 이미 정리한 트리라
통과했고, **CI가 그 사실이 처음 확인되는 자리**였다.

## 6. 잔여 과제 (정직하게)

| ID | 내용 |

| R-1 | **실기기·실앱 검증 없음.** 시뮬레이터는 계약만 확인한다 |

| R-5 | 오리진 허용목록(S1)은 앱에 적용되지 않는다 — 앱의 방어선은 **서명 신원**이다 |

## 7. 예방 패턴

- **상태코드는 배포 증거가 아니다.** SPA 폴백은 없는 파일에도 200을 준다. 새 정적 자산은
  **내용으로** 확인해야 한다(이 리포는 exit code에 대해 같은 교훈을 이미 갖고 있다).
- **호스트가 준비되기 전에 말을 건다.** 스토어프론트 로더에서 겪은 것과 같은 문제가 앱에서
  그대로 재현됐다 — 새 호스트를 붙일 때는 **큐가 기본값**이라고 생각하는 편이 맞다.
- **WebView 안의 예외는 아무도 못 본다.** 콘솔이 없다. 호스트가 부르는 전역은 언제 불려도
  안전해야 한다.
- **워크스페이스 패키지를 추가하면 lockfile이 함께 간다.** 로컬은 이미 정리된 트리라 통과하고,
  CI가 그 불일치를 처음 만난다.
