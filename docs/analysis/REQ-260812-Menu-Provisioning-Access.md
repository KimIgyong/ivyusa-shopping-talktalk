- 관련: `design/chat-widget-menu-structure.md`(CHATWIDGET-MENU-1.0.0), `design/chat-widget-roles-rbac.md`(FR-056), PLN-260808-Console-Menu-Overview

## 1. AS-IS

### 1.1 메뉴는 프론트 하드코딩 배열이다

- `apps/web/src/layouts/nav-config.ts` — 테넌트 메뉴 **16개**(`TENANT_NAV`), 어드민 메뉴 4개(`ADMIN_NAV`)가 정적 배열로 선언되어 있고, 각 항목은 `capability` 한 개를 달고 있다.
- 사이드바(`Sidebar.tsx`)와 전체 메뉴 카드뷰(`MenuPage.tsx`)가 이 배열을 그대로 필터링한다.
- **서버는 메뉴라는 개념을 전혀 모른다.** 메뉴 코드도, 목록도 백엔드에 존재하지 않는다.

### 1.2 가시성은 프론트에 중복 구현된 rank×label 매트릭스로만 결정된다

- `apps/web/src/lib/rbac.ts` 의 `RANK_EXTRA`(직급별 기본) + `LABEL_CAPS`(라벨별 부여) 를 합쳐 `capabilitiesFor(principal)` 로 계산한다.
- 이것은 백엔드 `packages/common/src/rbac/permission-matrix.ts` 와 **별개의 사본**이다. 두 매트릭스의 축(capability 이름)조차 다르다 — 프론트는 `live_chat`/`history`/`statistics` 같은 화면 단위, 백엔드는 `conversation.handle`/`analytics.read` 같은 행위 단위.
- 결과적으로 **테넌트가 손댈 수 있는 부분이 하나도 없다.** 권한 조정은 코드 수정 + 배포뿐이다.

### 1.3 메뉴 ≠ capability 라서 해상도가 부족하다

한 capability에 여러 메뉴가 물려 있어, 지금 구조로는 개별 메뉴를 끌 수 없다.

| capability | 물려 있는 메뉴 |
|---|---|
| `live_chat` | 실시간 채팅, **이슈 보드** |
| `knowledge` | 지식, **상품** |
| `settings` | 설정, **개인정보 고지** |

### 1.4 테넌트별 기능 제공 여부(엔타이틀먼트) 개념이 사실상 없다

- `tenants` 테이블에 `plan varchar(32)`(starter/growth/enterprise, nullable)이 있으나 **어디서도 읽지 않는다.** 화면 표시용 배지일 뿐이다.
- 유일한 실제 엔타이틀먼트는 `tenants.workflow_mode`(`base`/`bridge`/`native`) — 이슈 워크플로우 유료 애드온용이며, 서버(`issue.service.ts:119`)에서 판정한다. 즉 **"서버가 판정하는 테넌트 엔타이틀먼트" 패턴 자체는 이미 있고, 메뉴로 일반화되어 있지 않을 뿐이다.**
- 어드민 테넌트 관리 화면(`TenantsPage.tsx`)의 행 액션은 `사용자 관리` / `정지`·`활성` 3개뿐이다.

### 1.5 `roles_permissions` 는 스키마에만 있는 죽은 테이블이다

- 엔티티 `apps/api/src/domain/user/entity/role-permission.entity.ts` 는 존재하나 **코드 어디에서도 참조되지 않는다**(레포 전체 grep 결과 정의부 1건).
- 원 설계 의도는 주석대로 "DB가 기본 매트릭스를 테넌트별로 오버라이드" 였는데, 정작 **`tenant_id` 컬럼이 없어** 테넌트별 오버라이드가 구조적으로 불가능하다. §6 알려진 갭(테이블 tenant_id 누락)의 사례다.

### 1.6 서버 차단은 행위 단위로만 존재한다

- `AuthorizationGuard` 가 `@RequireRank` / `@RequireCapability` / `@AdminOnly` 를 평가한다(deny-by-default).
- 화면(메뉴) 단위 차단은 없다. 사이드바에서 숨겨도 **URL 직접 입력이나 API 직접 호출로 우회 가능**하다.

## 2. TO-BE

### 2.1 2계층 권한 모델

```
① 플랫폼 어드민 : 테넌트별 "제공 메뉴"      → 이 테넌트가 살 수 있는 메뉴의 상한선
② 테넌트 마스터 : 팀원별 "접근 가능 메뉴"   → 상한선 안에서 누구에게 열어줄지
```

②는 ①을 절대 초과할 수 없다. 미제공 메뉴는 테넌트 설정 화면에 **비활성 + "미제공" 배지**로 보인다(존재를 숨기지 않는다 — 업셀 지점이자, 마스터가 "왜 안 보이지"로 헤매지 않게 한다).

## 3. 권한 판정 규칙 (확정)

```
provided(tenant, menu)
  = tenantOverride[menu]              (있으면: on=제공 / off=차단)
  ?? planPreset[tenant.plan][menu]    (플랜 프리셋)
  ?? true                             (plan NULL/미지의 값 → 전체 제공)

effective(user, menu)
  1. provided == false                       → false      (상한선, 예외 없음)
  2. user.rank == 'master'                   → true       (자기잠금 방지, NFR-3)
  3. userOverride[user][menu] 존재            → 그 값       (마스터의 명시적 의사)
  4. roleMatrix[user.rank][menu]             → AND
     labelRule(menu, user.labels)            → AND        (기존 라벨 게이팅 유지)
```

- **3 > 4**: 사용자 예외는 직급 매트릭스와 라벨 규칙을 모두 이긴다. 마스터가 "이 사람에게 이력 화면을 열어준다"고 명시했으면 라벨이 없어도 열린다(대신 그 화면의 *행위*는 여전히 기존 capability/label 가드가 판정 — 메뉴 권한은 화면 접근이지 행위 허가가 아니다).
- **1이 모든 것을 이긴다**: 어드민이 차단한 메뉴는 마스터에게도 안 보인다.
- 이슈 보드는 여기에 더해 기존 `workflow_mode` 판정이 그대로 AND 된다(제공했어도 `base` 테넌트는 안내 화면).

### 3.1 기본값(행 부재 시) — 현행 동작을 그대로 재현

- `roleMatrix` 기본값 = 현 `apps/web/src/lib/rbac.ts` 의 `RANK_EXTRA`
- `labelRule` = 현 `LABEL_CAPS` (consult → 실시간/이력, operations → 주문·고객·캠페인·리뷰·지식, accounting → 제휴)
- 즉 **1단계 배포 직후 화면상 변화는 0** 이어야 한다. 이것이 이 요구사항의 회귀 판정 기준이다.

## 4. 사용자 흐름

### 4.1 어드민 — 테넌트 제공 메뉴

```
/admin/tenants  →  [제공 메뉴] 버튼(행 액션)
   → 모달: 플랜 배지 + 메뉴 16행 × (플랜 기본 / 이 테넌트 3상태 셀렉트)
   → 저장 → 토스트 → 해당 테넌트 사용자들에게 즉시 반영(캐시 무효화)
```

### 4.2 테넌트 마스터 — 팀원 접근권한

```
/settings  →  "메뉴 접근권한" 섹션
   ├ 탭 1 · 역할 기본값 : 직급(4) × 메뉴(제공된 것만) 체크 매트릭스
   └ 탭 2 · 사용자 예외 : 팀원 목록 → [예외 편집] → 메뉴별 (기본/허용/차단)
   → 저장 → 토스트 → 해당 사용자 다음 화면 전환 시 반영
```

### 4.3 차단된 사용자

```
사이드바에 없음 → URL 직접 입력 → "이 메뉴에 접근할 수 없습니다" 안내 + 대시보드 링크
                              → (그 화면의 API를 직접 호출해도 403 E5030)
```

## 6. 비범위 (이번에 하지 않는 것)

- 어드민 콘솔 자체의 메뉴 제공 관리(플랫폼 메뉴 4개는 계속 admin level로만 판정)
- 위젯(고객용) 메뉴/탭 노출 제어
- 플랜 프리셋을 화면에서 편집하는 기능(상수로 관리, 변경 시 배포)
- 행위 단위 capability 매트릭스의 테넌트 편집(메뉴 접근과 별개 층)
- `roles_permissions` 죽은 테이블 DROP (별도 정리 건)
- 메뉴별 읽기/쓰기 구분(이번엔 접근 가능/불가 2상태)
