# FIX-260819-Cafe24-Mall-Tenant-Binding

Cafe24 몰이 엉뚱한 테넌트에 연결되는 것을 막는 가드.

- 작성일: 2026-08-19
- 선행: `docs/analysis/REQ-260819-Cafe24-Login-Amoebaorder.md` (PR #313)
- 사용자 확인: **tenant 2(annehearts) 정상, tenant 3(amoebaorder)만 잘못됨** — 재발 방지 코드 승인

## 1. 무엇이 잘못됐나

tenant 3 `amoebaorder`의 Cafe24 자격증명에 저장된 몰이 `annehearts`였다. 결과는 둘.

1. **로그인 불가** — 로그인 시작이 "스토어프론트 호스트 → 몰 ID → 그 몰의 테넌트"로
   찾는데 `amoebaorder`를 가진 자격증명이 없어 매칭 실패.
2. **주문 오염** — 동기화는 자격증명만 보고 테넌트를 안 본다. tenant 3에 annehearts
   주문 **65건**이 캐시됐고 그중 **17건이 tenant 3 고객 16명에게 바인딩**됐다.

코드가 잘못 매핑한 게 아니라 **잘못된 입력을 아무도 막지 않았다.**

## 2. 고친 것

### G-1. 설치 시 몰↔테넌트 대조 (`createInstall`)
테넌트의 `shop_domain`/`storefront_url`이 `*.cafe24.com`이면 거기서 몰 ID를 읽어
요청된 몰과 대조하고, 다르면 **거부**(E5045).

⚠️ **커스텀 도메인은 거부하지 않는다.** `shop.example.com`에서는 몰 ID를 읽을 수 없으므로
"검증 불가"이고, 오타를 잡겠다고 정상 설치를 막는 것은 잘못된 거래다. 대신 경고를 남긴다.
이번 건은 `amoebaorder.cafe24.com`이라 이 규칙에 걸린다.

### G-2. 한 몰은 한 테넌트 (`createInstall`)
이미 다른 테넌트가 연결한 몰이면 **거부**(E5046). 같은 테넌트의 재연결은 허용.

### G-3. 모호한 조회는 거절 (`findTenantIdByMallId`)
같은 몰을 두 테넌트가 들고 있으면 예전에는 **스캔 순서상 첫 행**을 반환했다. 즉 annehearts
쇼핑객이 tenant 2가 아니라 tenant 3 세션에 묶일 수 있었다. 이제 모호하면 `null` + `error`
로그. **로그인이 시끄럽게 실패하는 편이 엉뚱한 상점으로 성공하는 것보다 낫다.**

> 이건 지금 스테이징의 실제 상태다. 데이터를 정정하기 전까지 annehearts 로그인도
> 안전하지 않았다.

### G-4. 남의 몰은 동기화하지 않는다 (`syncOrders`)
검증 가능한 `*.cafe24.com` 도메인과 자격증명의 몰이 다르면 **아무것도 가져오지 않고**
`ok:false` + `error` 로그. 경고만으로는 오염이 계속 쌓인다.

### G-5. 200 뒤에 숨은 실패를 기록 (`start`/`callback` catch)
`start`는 성공하면 302, 실패하면 200(되돌아가기 HTML)이라 **접근 로그에서 실패가 성공처럼
보였다.** 스테이징에 남은 실제 시도 3건이 전부 `-> 200`이었고, 원인을 알아내려면 저장된
자격증명을 복호화해야 했다. 이제 각 catch가 사유를 `warn`으로 남긴다. 쇼핑객 경험은 그대로다.

### G-6. 몰 ID 파싱 일원화 (`cafe24-mall.ts` 신규)
같은 파싱이 세 곳(customer-auth·install·sync)에 복사돼 있었다. 이번 사고가 **그 비교가
어디서나 같아야** 성립하는 문제라 한 곳으로 합쳤다.

## 5. 예방 패턴

**외부 시스템 식별자는 테넌트가 이미 아는 사실과 대조하라.** 운영자 입력을 그대로 믿으면
한 글자 차이가 다른 상점의 데이터를 끌어온다. 대조할 근거가 없을 때만(커스텀 도메인)
통과시키고, 그 사실을 로그에 남긴다.

**"조회 결과가 여러 개면 첫 번째"는 멀티테넌트에서 버그다.** 모호함은 임의 선택이 아니라
거절로 끝나야 한다.

**실패를 성공과 같은 상태 코드로 응답한다면 반드시 로그를 남겨라.** 사용자 경험상
조용히 되돌리는 게 맞더라도, 운영자에게는 사유가 필요하다. 이 사건의 진단 비용 대부분이
여기서 나왔다.

## 6. 코드리뷰(CodeRabbit, PR #314) 반영 — 4건 전부

| # | 지적 | 조치 |
|---|---|---|
| R-1 | **`findTenantIdByMallId`가 미소유와 다중소유를 둘 다 `null`로 답한다** → 이미 두 테넌트가 물고 있는 몰이 "주인 없음"으로 읽혀 세 번째 테넌트가 연결 가능 | ⭐ **내가 만든 회귀.** G-3에서 모호를 `null`로 만들면서 G-2가 그걸 자유로 해석하게 됐다. 소유자 목록을 그대로 주는 `findMallOwners`를 분리하고, 설치 가드는 이쪽을 쓴다 |
| R-2 | `shop_domain`과 `storefront_url`이 **서로 다른 몰**을 가리켜도 첫 값만 쓴다 | `tenantMall()`이 `known`/`unknown`/**`ambiguous`** 3상태를 반환. 모호하면 설치도 동기화도 거부 — 깨진 테넌트 레코드 위에 "검증됨"을 발급할 수 없다 |
| R-3 | 설치 입력 정규화가 공용 파서와 달라 `https://mall.cafe24.com/path`를 거부 | `mallIdFromHost` 공용 사용. 로그인 경로가 받는 형식을 설치도 받는다 |
| R-4 | 공개 `shop` 파라미터·예외 메시지를 **원문 로깅** → CR/LF 로그 위조, PII 유출 가능 | `logSafe()`(개행·제어문자 제거 + 200자 제한) 공용화. `start`는 원문 대신 **파싱된 mall id**를 기록 |

R-1과 관련해 설치 **콜백 저장 직전에도** 소유권을 재확인한다. 두 테넌트가 동시에 설치를
시작하면 시작 시점엔 둘 다 "주인 없음"을 통과하기 때문이다.

⚠️ 완전한 원자성은 **정규화된 mall id에 대한 영속 unique 제약**이 있어야 한다. 지금 mall id는
암호화된 블롭 안에 있어 컬럼이 없고, 이는 **스키마 변경**이라 이번 범위에서 뺐다(§7).

신규 테스트 4건 추가 — 다중 claim 몰 거부, 테넌트 레코드 자체가 모호한 경우, 전체 URL 형식
입력 허용, 로그 위조 문자열 제거. 전체 **1,471건 통과**.

## 8. 이 PR이 하지 않는 것

**데이터는 건드리지 않았다.** 다음 둘은 사용자 결정·운영자 작업이 필요하다.

1. tenant 3을 `amoebaorder` 몰로 **재연결**(콘솔에서 OAuth 재수행).
   ⚠️ G-1이 이제 잘못된 재연결을 막아주지만, **기존에 저장된 잘못된 자격증명은 그대로다.**
2. tenant 3에 오염된 주문 **65건**(고객 바인딩 17건) 정리 — 삭제할지 바인딩만 끊을지 미결.

G-4 덕분에 **배포 즉시 추가 오염은 멈춘다**(tenant 3 동기화가 거부됨). 이미 들어온 65건은
남아 있으므로, 정리 전까지 amoebaorder 고객에게 다른 몰 주문이 보일 수 있다.
