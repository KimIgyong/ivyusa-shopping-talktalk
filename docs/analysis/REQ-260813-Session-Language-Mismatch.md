## 0. 결론 먼저

**AI는 고객 언어를 따라가는데, 시스템 문구는 따라가지 않습니다.** 그래서 한 대화 안에서 언어가 섞입니다.

### 실측 (스테이징 tenant 1)

세션 언어가 `EN`인데 고객이 한국어로 쓴 대화 **27건**에서, 그 대화에 오간 메시지를 언어별로 세면:

| 발신 | 한국어 | 영어 |
|---|---|---|
| **AI** | **28** | 43 |
| **시스템** | **0** | **23** |

AI는 절반가량을 한국어로 답했지만, **시스템 문구는 23건 전부 영어**였습니다.

실제 대화(208번):

```
고객:   뉴욕 날씨 알려주시오
시스템: We're outside our support hours right now. I've passed your message to …
```

### 왜 이렇게 되는가

| 주체 | 언어 결정 방식 |
|---|---|
| **AI 답변** | 응답 규칙 8번 *"고객의 언어와 격식을 맞출 것"* → **매 턴 고객 문장을 보고 맞춤** |
| **시스템 문구** | `session.language` 한 값으로 결정 → **세션 생성 시점에 고정** |

즉 문제는 "번역이 없다"가 아니라 **판단 시점이 다르다**는 것입니다.

---

## 1. AS-IS

### 1-1. 세션 언어가 정해지는 경로

| 시점 | 값 |
|---|---|
| 위젯 최초 진입 | 스토어 기본값 **`'en'`** (하드코딩) → `POST /session/ensure`의 `locale`로 전달 |
| 서버 해석 | `resolveLanguage(locale, tenant.timezone)` — 명시적 `es`/`ko`면 존중, 아니면 테넌트 타임존 기본값, 그다음 영어 |
| 이후 변경 | 고객이 위젯 언어 선택기를 **직접** 누를 때만(`POST /session/language`) |

**위젯은 브라우저 언어를 보지 않습니다.** 한국어 사용자가 언어 선택기를 건드리지 않으면 세션은 `EN`으로 시작하고, 그 뒤 한국어로 쓰든 말든 바뀌지 않습니다.

> 서버 쪽에는 이미 유사 문제를 겪은 흔적이 있습니다 — 외부 메신저 채널은 `languageForChannel()`로 **플랫폼 힌트 → 테넌트 기본값** 순으로 해석합니다(PLN-260812 S3). *"릴레이 채널이 locale을 아예 보내지 않아 한국어 카카오톡 방에 영어 안내가 나갔다"* 는 주석이 그대로 남아 있습니다. **위젯에서 같은 일이 일어나고 있습니다.**

### 1-2. `session.language`가 지배하는 것

- 이관·오프아워·재위임·방치 확인/종료 등 **모든 시스템 문구**
- 오프아워 **이메일 회신 문구**
- RAG 호출 시 답변 언어 지시(다만 페르소나 규칙이 고객 문장을 우선하므로 실제로는 고객 언어를 따라감)
- 위젯 UI 언어(수동 변경 이력이 없을 때만 서버 값을 따름)

### 1-3. 위젯의 동기화 규칙

위젯은 `ensure` 응답의 `language`로 UI 언어를 맞추되 **사용자가 직접 고른 이력이 있으면 존중**합니다(`localStorage`). 즉 서버가 세션 언어를 바꾸면 UI도 따라오지만, **수동 선택자는 보호**됩니다 — 이 규칙은 그대로 두는 것이 맞습니다.

| G3 | AI와 시스템의 언어 판단 시점이 다름 | **한 대화 안에서 언어가 섞임**(가장 눈에 띄는 증상) |
| G4 | 언어 감지 로직 자체가 없음 | 판단 근거가 없음 |

## 3. TO-BE

```
위젯 진입      브라우저 언어(navigator.language) → locale 힌트로 전달
                   └ 지원 언어(en/es/ko)일 때만, 수동 선택 이력이 있으면 그것을 우선

대화 중        고객 메시지의 언어가 세션 언어와 다르면 → 세션 언어 갱신
                   └ 갱신 이후의 시스템 문구·이메일 회신이 그 언어로 나감
                   └ 수동 선택 이력이 있으면 갱신하지 않음(고객의 명시적 선택이 우선)
```

핵심은 **G1(시작값)과 G2(갱신)** 이며, 둘 다 있어야 G3이 사라집니다. G1만 고치면 브라우저가 영어인 한국인이 여전히 어긋나고, G2만 고치면 첫 한 턴은 어긋난 채 나갑니다.

## 4. 리스크

| # | 리스크 | 비고 |
|---|---|---|
| **R1** | **언어가 왔다 갔다 함** — 한국어 대화 중 `ok`, `thanks` 한 마디에 영어로 뒤집힘 | 가장 큰 위험. 짧은 메시지·감지 신뢰도 기준이 필요 |
| R2 | 고객이 언어 선택기로 고른 값을 시스템이 덮어씀 | 수동 선택 이력이 있으면 자동 갱신 금지 |
| R3 | 동의 고지를 A 언어로 받고 이후 B 언어로 바뀜 | 동의 자체는 유효하나, 고지 언어와 대화 언어가 달라짐 — 법무 관점 확인 필요 |
| R4 | 오프아워 이메일이 이미 A 언어로 나간 뒤 대화 언어가 바뀜 | 후속 회신부터 적용 |
| R5 | 감지 비용 | 문자 범위 기반이면 비용 0. 모델 호출은 불필요 |
