## 0. 한 줄 요약

이관 트리거에 **네 번째 조건**을 넣습니다 — *고객이 사람을 요청했다*. 나머지는 그 조건이 실패했을 때 고객을 오도하지 않게 하는 장치입니다.

```
고객 메시지
   │
   ├─ ① 정책 키워드(denyRules)        ─┐
   ├─ ★ 상담원 요청  ← 신설            ├─ 기존 handoff() 경로 재사용
   ├─ ② 모더레이션 차단                │   (라우팅·오프아워·알림·이슈 전부 그대로)
   └─ ③ 저신뢰(< 0.45)                ─┘
```

---

## 1. 단계별 계획

### P1 — 상담원 요청을 이관 조건으로 (핵심)

| 항목 | 설계 |
|---|---|
| 위치 | `chat.service` — 의도 분류 **직후**, 정책 deny 판정 **다음**. RAG 호출 **이전**이라 쓰지 않을 답변에 모델 호출을 낭비하지 않음 |
| 1차 신호 | `classifyIntent().intent === 'agent_request'` **AND** `confidence >= 0.6` **AND** `!fallback` |
| 2차 신호 | 내장 문구 목록(EN/ES/KO) 일치 — 의도 분류가 놓치거나 실패했을 때의 보완 |
| 이관 실행 | 기존 `handoff(conversationId, session, tenantId, 'user_request', text)` — **`user_request`는 이미 정의된 사유**(위젯 버튼이 쓰는 값)라 새 개념이 없음 |
| 응답 | `escalate: true` + 이관 안내(`system`) — 기존 세 분기와 동일 형태(D3) |
| 대기 중 가드 | `queued`(이미 `waiting`)면 **조용히 무응답** — 기존 분기와 동일, 중복 알림 없음 |
| 사람이 잡은 대화 | 상위의 `humanOwnsThread` 조기 반환에서 이미 걸러짐 |

**분류기 프롬프트 확장**: 현재 `{"intent":string,...}`은 자유 문자열이라 `agent_request`가 안정적으로 나오지 않습니다. 프롬프트에 **닫힌 집합**을 명시합니다.

```
intent ∈ order_status | delivery | cancel_refund | product_inquiry
        | agent_request | other
```

> 파싱 실패 시 폴백은 지금처럼 `product_inquiry` + `fallback: true`이며, **폴백은 이관 신호로 쓰지 않습니다.** 분류 실패를 사람 요청으로 읽으면 큐가 오염됩니다.

**내장 문구 목록(2차 신호)** — 짧게 유지하고, 테넌트 정책이 아니라 제품 동작으로 둡니다.
```
EN  talk to a (person|human|agent) · speak to (someone|a human) · real person · live agent
ES  hablar con (una persona|un agente|alguien)
KO  상담원 · 상담사 · 사람과 (통화|대화) · 담당자와 (통화|연결)
```

### P2 — 모델이 연결을 약속하지 못하게 (2차 방어)

응답 규칙 **5번을 수정**합니다(D4, 규칙 수 유지).

> 현행: *"…고객의 질문 자체가 미해결일 때만 상담원 연결을 제안하세요."*
> 추가: *"연결 여부는 시스템이 결정합니다. '연결해 드리겠습니다', '잠시만 기다려 주세요'처럼 **연결을 확정하거나 대기를 요구하는 표현은 쓰지 마세요.** 상담원이 필요해 보이면 '원하시면 상담원 연결을 도와드릴 수 있어요'처럼 **제안**만 하세요."*

P1이 동작하면 이 규칙이 발동할 일이 거의 없지만, **P1이 놓친 경우에 고객이 오지 않을 것을 기다리지 않게** 합니다.

### P3 — 계측 (승인 전제)

과잉 이관이 최대 리스크이므로 **판단 근거를 남깁니다.**

- `handoff()` 감사/로그에 이미 `reason`이 들어가므로, 배포 후 **사유별 이관 건수**를 비교(`user_request` 증가분이 곧 이 기능의 영향)
- 의도가 `agent_request`인데 **신뢰도 미달로 이관하지 않은 건**을 `logger.log`로 남겨, 임계 0.6이 적절한지 실데이터로 판단

## 2. 화면 설계

**UI 변경 없음.** 고객에게는 기존 이관 안내가 그대로 보이고, 상담원 콘솔에는 기존 대기열·알림이 그대로 뜹니다.

```
고객: 상담원 연결해 주세요
       ↓  (기존과 동일한 시스템 안내)
system: 상담원에게 연결해 드릴게요. 잠시만 기다려 주세요.       ← 실제로 대기열에 올라감
   또는 (오프아워)
system: 지금은 상담 가능 시간이 아니에요. 회신받으실 이메일을…   ← 기존 오프아워 라우팅
```

> **지금과 문구는 비슷하지만 결정적으로 다릅니다.** 지금은 AI가 같은 말을 하고 아무 일도 일어나지 않고, 이후에는 시스템이 말하며 실제로 큐에 올립니다.

## 3. 영향 범위

| 영역 | 영향 | 조치 |
|---|---|---|
| **고객질문 통계** | 의도 렌즈에 `agent_request` 버킷 신설 | 의도 값이 닫힌 집합이 되어 오히려 정돈됨. 과거 데이터는 기존 값 유지 |
| **상담 큐** | 이관 건수 증가(의도한 변화) | P3로 계측, 임계 조정 여지 |
| **오프아워 이메일** | 오프아워 요청도 이관 경로를 타므로 회신 요청 증가 | 기존 라우팅이 그대로 처리 |
| **이슈 워크플로우** | `user_request` 사유로 이슈 생성 | 위젯 버튼과 동일 경로라 신규 배선 없음 |
| **모더레이션** | 변화 없음 | 이관 안내는 시스템 문구 |
| **AnswerReuse / 초안 모드** | 이관 시 RAG를 호출하지 않으므로 재사용·초안 경로를 타지 않음 | 의도된 동작 |

## 5. 리스크와 대응

| # | 리스크 | 대응 |
|---|---|---|
| R1 | **과잉 이관** — "상담원분이 친절하시네요"가 요청으로 분류 | 신뢰도 **0.6** 임계 + 닫힌 집합 프롬프트 + 문구 목록을 좁게 유지. 배포 후 사유별 건수 계측(P3) |
| R2 | 분류 실패(`fallback`)를 요청으로 오독 | **폴백은 신호로 쓰지 않음**(명시적 가드 + 테스트) |
| R3 | 문구 목록이 오탐 유발("상담원이 몇 명인가요?") | 목록은 **요청 형태**만 담고 명사 단독은 배제. 의도 분류가 본선이고 목록은 보완 |
| R4 | 오프아워 큐 증가 | 기존 이메일 라우팅으로 흡수. 총량은 계측 대상 |
| R5 | 프롬프트 변경이 기존 의도 분포를 바꿈 | 통계는 스냅샷 기반이라 과거 값은 보존. 신규 분포만 달라짐 |

## 6. 검증 계획

| # | 항목 | 기준 |
|---|---|---|
| V1 | **재현 3건** | REQ §0의 세 문장(`Can I talk to a real person?` · `그래도 상담원과 직접 통화하고 싶어요` · `상담원 바꿔주세요`) → **다음 메시지가 `system` 이관 안내**, `escalate: true` |
| V2 | 상태 전이 | 대화가 `waiting`으로 가고 상담원 알림이 발생 |
| V3 | **과잉 이관 회귀** | 일반 질문 10종(배송비·반품·상품추천 등)이 **이관되지 않음** |
| V4 | 오탐 방어 | "상담원이 몇 명인가요?", "상담원분 친절하시네요" → 이관되지 않음 |
| V5 | 임계 | 의도가 `agent_request`이나 신뢰도 0.6 미만이면 이관하지 않고 로그만 남김 |
| V6 | 폴백 가드 | 분류 실패(`fallback: true`)는 이관 신호가 되지 않음 |
| V7 | 대기 중 중복 | 이미 `waiting`인 대화에서 재요청 → 중복 알림 없이 조용히 무응답 |
| V8 | 오프아워 | 오프아워 요청 → 이메일 안내 + 주소 수집 흐름(기존) |
| V9 | 약속 금지 | 페르소나 수정 후, 이관되지 않는 상황에서 AI가 "연결해 드리겠습니다"라고 말하지 않음 |

## 7. 구현 순서

```
P1 트리거(+프롬프트 닫힌 집합)  →  P2 페르소나 규칙  →  P3 계측 확인
        │                              │                    │
   스키마 없음                    설정 데이터 변경        배포 후 실측
   단독 PR                        (콘솔에서 즉시 반영)     사유별 건수 비교
```

- P1·P2는 한 PR로 묶습니다(둘 다 없으면 반쪽입니다)
- 배포 후 **V1·V3를 즉시 측정**하고, 과잉 이관이 보이면 임계를 먼저 올립니다

## 8. 승인 요청

위 계획대로 진행할지 확인 부탁드립니다. 구현 전 짚어둘 것 하나입니다.

**이 변경은 상담 큐를 늘립니다.** 지금까지 사람을 찾던 고객 일부가 AI 답변으로 흡수되고 있었고, 그것이 O1의 실체입니다. 정상화되면 **실제로 사람이 응대해야 할 건수가 늘어납니다** — 특히 오프아워에는 이메일 회신 부담으로 나타납니다. 기능 자체의 문제는 아니지만 운영 부하가 함께 움직인다는 점을 미리 알려드립니다.
