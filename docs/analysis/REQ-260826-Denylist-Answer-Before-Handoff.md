# REQ-260826-Denylist-Answer-Before-Handoff

콘솔 지식조회는 답하는데 위젯은 상담원에게 넘기는 문제 — 원인과 개선안

- 작성일: 2026-08-26
- 관찰: https://shoptalk.amoeba.site/live-chat?c=417 (tenant 3 amoebaorder)
- 근거: 스테이징 DB 실조회 + 코드 실측

## 1. 원인 — 결함이 아니라 **설정대로 동작한 것**

tenant 3의 핸드오프 설정에 **정책 deny-list**가 있습니다.

```json
denyRules: [{ "type": "refund", "label": "accounting",
              "keywords": ["환불계좌", "계좌변경"] }]
```

고객 질문은 `환불계좌 바꾸고 싶어` — 키워드에 정확히 걸립니다.

`chat.service.ts:619`의 deny 분기는 **검색보다 먼저** 실행되고 주석 그대로
*"a matched topic goes to a human no matter how confident the AI would be — the LLM is not
even asked"* 입니다. 그래서:

| | deny-list 검사 | 결과 |
|---|---|---|
| 위젯(고객) `POST /chat/message` | **있음** | 검색·LLM을 건너뛰고 즉시 인계 |
| 콘솔 지식조회 `POST /knowledge/ask` | **없음** | 정상적으로 검색해 답변 |

`denyMatch` 호출부는 코드 전체에서 `chat.service.ts` 한 곳뿐입니다. 두 화면의 답이 다른 이유는
지식이나 검색 품질 차이가 아니라 **경로가 다른 것**입니다.

**측정된 증거**

- 대화 417의 인계 시스템 메시지는 고객 발화 **290ms 뒤**에 기록됐습니다(10420 19:49:09.192 →
  10421 19:49:09.482). LLM 호출이 있었다면 나올 수 없는 간격입니다.
- tenant 3의 최근 7일 인계 9건 중 **3건이 이 키워드**(대화 416, 417×2). 나머지는 릴레이
  잡음·저신뢰입니다.
- 고객은 답을 받기까지 **약 2분** 기다렸습니다(19:46:16 인계 → 19:48:00 상담원 답변).

## 2. 아이러니 — 지식은 이미 있고, 심지어 이 대화에서 배웠습니다

tenant 3 KB에 이 질문에 답하는 문서가 **6건** 있습니다.

```
2098 policy_return 환불계좌 변경
2104 faq          환불계좌 변경하고 싶습니다
2376 faq          환불계좌 변경가능한가요?
2377 faq          환불계좌를 바꾸고 싶어요      ← 상담원 답변에서 승격
2378 faq          환불계좌 바꾸고 싶어          ← 대화 417의 상담원 답변 그대로
 376 policy_return 환불규정
```

2377·2378은 **바로 이 대화들에서 사람이 쓴 답을 지식으로 승격시킨 것**입니다. 지식 폐루프가
답을 학습했는데, deny-list가 그 답이 절대 쓰이지 않도록 보장하고 있습니다.

## 3. 판단

deny-list의 목적은 **"이 주제는 사람이 처리한다"** 이지 **"고객에게 아무것도 말하지 말라"** 가
아닙니다. 지금은 후자로 동작합니다 — 시스템이 이미 가진 답을 쥐고 고객을 2분 기다리게 합니다.

다만 모든 deny 주제에 자동 답변이 안전한 것도 아닙니다(법적 분쟁, 지불거절, 의료 표현 등은
자동 응답 자체가 위험). 그래서 **주제마다 운영자가 고르게** 하는 것이 맞습니다.

## 4. 선택지

| 안 | 내용 | 코드 | 부작용 |
|---|---|---|---|
| **A** | 콘솔에서 `환불계좌`·`계좌변경` 키워드를 뺀다 | 없음(운영 10초) | 이 주제가 **사람에게 안 간다.** 신뢰도가 낮을 때만 인계 |
| **B** | deny 매칭 시 **답변 먼저 하고 그 다음 인계** — 전 주제 일괄 | 소 | 기존 테넌트의 민감 주제 동작이 **말없이** 바뀜 |
| **C(권장)** | deny 규칙마다 `mode` 추가: `silent`(현행·기본) / `answer_then_handoff` | 소~중 | 없음. 기존 규칙은 그대로 두고 운영자가 주제별로 켠다 |

**C를 권장합니다.** 기본값을 현행으로 두면 어떤 테넌트도 모르는 사이에 민감 주제를 자동 응답하지
않게 되고, 이번 건은 운영자가 `refund` 규칙 하나를 `answer_then_handoff`로 바꾸면 해결됩니다.
"고객에게 답은 주되 사람도 붙는다"는 상태가 이 주제에서 실제로 원하는 그림입니다.

C에서 위젯 동작:

```
고객: 환불계좌 바꾸고 싶어
  ↓ deny 매칭(refund) · mode=answer_then_handoff
AI  : (KB 근거 답변 — 모더레이션 통과분)
시스템: 정확한 처리를 위해 상담원에게도 전달했습니다. 잠시만 기다려 주세요.
  ↓ 상담원 배정 · 이슈 생성 (지금과 동일)
```

인계·이슈 생성·SLA는 **하나도 바뀌지 않습니다.** 고객이 기다리는 동안 답을 받을 뿐입니다.

## 6. side-impact (C 기준)

- `handoff_config.denyRules[].mode` 추가 — JSON 필드라 **스키마 변경 없음**
- 값이 없으면 `silent` → 기존 테넌트 동작 무변화
- 모더레이션 게이트는 그대로(자동 답변도 반드시 통과)
- 이슈 워크플로우(type/label/SLA) 무변화
- 콘솔 `/ai-setting` 핸드오프 카드에 규칙별 선택 UI 1개 추가 + 6개 언어
- 저신뢰·차단 시 기존 인계 경로로 자연 복귀
