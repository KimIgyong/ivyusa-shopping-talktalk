## 0. 결론 먼저

| # | 요구 | 현행 | 판정 |
|---|---|---|---|
| ① | 상담원 → **AI 재위임** | 상태는 `ai_active·waiting·agent·ended` 4종. **`agent`에서 빠져나오는 길은 `end`(대화 종료)뿐** | **미구현 — 전이 자체가 없음** |
| ② | **지식 조회** 버튼 | `/knowledge/ask`는 있으나 권한이 `knowledge_source.manage`(MASTER·DIRECTOR). 상담사(MANAGER·STAFF)는 `conversation.handle`만 보유 | **미구현 + 권한 격차** |
| ③ | **AI 초안 전달** | 브리핑(요약·의도·감정·권장조치)만 생성. **고객에게 보낼 문장을 만드는 기능이 없음** | **미구현** |
| ③-b | 채택분의 **확정 지식화** | `KnowledgeCaptureModal`(PR #131)로 수동 작성·저장은 가능 | **부분 존재 — 전달과 연결 안 됨** |

> **①은 개선이 아니라 결손입니다.** 상담원이 대화를 잡는 순간 봇은 영구히 침묵하고, 되돌릴 방법이 없습니다.

### 실측 피해 (스테이징 tenant 1, 2026-08-10)

| 지표 | 값 |
|---|---|
| `agent` 상태 대화 | **7건** |
| 그중 최근 24시간 내 상담원 메시지가 있는 대화 | **0건** |
| **상담원 마지막 답변 이후 아무도 답하지 않은 고객 메시지** | **10건** (대화 5번 3건 · 37번 2건 · 42번 5건) |

대화 42번은 고객이 5번 더 말을 걸었고 **AI도 사람도 답하지 않았습니다.** 봇 침묵은 의도된 설계(`chat.service.ts:314`)지만, 되돌리는 문이 없어서 방치가 곧 영구 무응답이 됩니다.

## 1. AS-IS

### 1-1. 대화 상태와 봇 침묵 (요구 ①)

```
ai_active ──고객이 상담원 요청/저신뢰──▶ waiting ──상담원 수락──▶ agent ──end──▶ ended
    ▲                                                              │
    └──────────────────── 없음 ─────────────────────────────────────┘
```

- 봇 침묵 조건(`chat.service.ts:314`): `status === agent` **또는** `waiting && agentId != null`
- `waiting`은 큐일 뿐이라 수락 전까지 AI가 계속 답합니다(FIX-260806에서 정정된 동작)
- **`agent` → `ai_active` 전이는 서비스·컨트롤러 어디에도 없습니다.** `AgentService.end()`만 존재하며 이는 대화를 **종료**시킵니다(`endedAt` 기록, 배정 해제, 이슈 종결)
- 즉 상담원이 "이건 AI가 이어받아도 되겠다"고 판단해도 **대화를 끊는 것 외에 선택지가 없습니다**

### 1-2. 지식 조회 (요구 ②)

| 항목 | 현행 |
|---|---|
| API | `POST /knowledge/ask` — 질문·언어·그룹 → RAG 답변 + 근거 문서 목록 |
| 권한 | `KNOWLEDGE_SOURCE_MANAGE` |
| 보유 랭크 | **MASTER · DIRECTOR만** (`permission-matrix.ts`) |
| 상담사 랭크 | MANAGER·STAFF는 `CONVERSATION_HANDLE` 보유, 지식 권한 없음 |
| 상담 화면 진입점 | **없음** — `/knowledge` 화면에만 존재 |

상담사가 "이 질문 우리 지식에 있나?"를 확인하려면 **화면을 떠나 지식 메뉴로 가야 하고, 대부분의 상담사는 그 화면 자체에 접근 권한이 없습니다.**

### 1-3. AI 답변 생성 (요구 ③)

- RAG(`rag.service.answer`)는 **고객 턴에서만** 호출됩니다. 상담원이 임의 시점에 초안을 요청하는 경로가 없습니다.
- 상담원 콘솔의 AI는 **브리핑 한 종류뿐**입니다(`agent.service.ts:341`, `assist` 기능) — "요약·의도·감정·권장 조치"를 문장으로 돌려주며, **고객에게 그대로 보낼 답변이 아닙니다**.
- 상담원 발신 메시지는 이미 모더레이션을 통과합니다(scope `both`) — 초안을 보낼 때도 같은 관문을 지나야 합니다.

### 1-4. 확정 지식화 (요구 ③-b)

PR #131의 `KnowledgeCaptureModal`이 있습니다.

| 있는 것 | 없는 것 |
|---|---|
| 질문/답변을 골라 모범답안을 작성 → KB 문서 생성 + 즉시 임베딩 | **전달한 답변을 그대로 채택**하는 흐름 |
| 출처로 대화 링크 기록(`source_url`) | 저장 권한이 **MASTER·DIRECTOR** — 정작 답변한 상담사가 저장 불가 |
| 분류 기본값 `faq` | 확정 답변임을 나타내는 표식·우선순위 없음 |

## 3. TO-BE (요구별)

### ① AI 재위임
```
[대화 헤더]  … [AI에게 넘기기]  [상담 종료]
      │
      ├─ conversations.status: agent → ai_active
      ├─ 배정 해제(released) — 이후 새 에스컬레이션은 정상 동작
      ├─ 시스템 메시지 1건 기록 + 고객 안내 문구(3개 언어)
      └─ 감사 기록 agent.handed_back
```
- 재위임 직후 고객 메시지부터 AI가 다시 응답
- 다시 상담원이 필요하면 기존 에스컬레이션 경로가 그대로 다시 태움

### ② 지식 조회
```
[대화창 우측]  이 질문, 지식에 있나?
   질문 [ 고객 마지막 메시지 자동 채움 (편집 가능) ]  [조회]
   → 답변 미리보기 + 근거 문서 N건(제목·유사도·열람 링크)
   → 근거 없음이면 그 사실을 명시 (지식 공백 신호)
```
- **읽기 전용**입니다. 상담사가 쓸 수 있어야 하므로 권한 설계가 §4 D2.

### ③ AI 초안 전달 + 확정
```
[초안 만들기] → AI 답변 초안 + 근거 문서 표시 (고객에게는 아직 안 보임)
   → 상담원이 편집 가능
   → [고객에게 전달]  → 모더레이션 통과 후 상담원 메시지로 발송
   → 전달 후 [이 답변을 확정 지식으로]  → 질문+확정답변이 KB 문서로 저장·임베딩
                                        → 다음 유사 질문에서 이 문서가 근거로 사용됨
```

> **"저장된 대화내용에서 확정된 내용으로 답변"의 해석**: 대화 로그를 그대로 재생하는 방식은 채택하지 않는 것을 권장합니다. 로그는 그 고객의 주문·맥락에 묶여 있어 다른 고객에게 그대로 쓰면 틀립니다. **질문–확정답변 쌍을 지식 문서로 승격**하면 기존 RAG가 맥락에 맞게 인용하며, 이미 검증된 경로입니다(§4 D4).

## 4. 결정 필요 사항 (PLN 착수 전)

| # | 항목 | 선택지 | 분석 의견 |
|---|---|---|---|
| **D1** | 재위임 시 고객 안내 | 안내 문구 노출 / 조용히 전환 | **안내 권장** — 담당이 바뀐 사실은 고객이 알아야 하고, 문구는 핸드오프 설정처럼 3개 언어 편집형 |
| **D2** | 상담사의 지식 조회 권한 | ㄱ. 상담 콘솔 전용 **읽기 라우트** 신설(권장) / ㄴ. `KNOWLEDGE_SOURCE_MANAGE`를 MANAGER·STAFF에 부여 | **ㄱ** — ㄴ은 문서 생성·삭제까지 열립니다. 조회만 필요한데 쓰기 권한을 주는 건 과합니다 |
| **D3** | 확정 지식 저장 권한 | ㄱ. 상담사는 **제안**, 관리자가 승인 / ㄴ. 상담사가 바로 저장 | **ㄱ 권장** — 코칭 제안(PR #99)에서 이미 쓰는 승인형 패턴. 다만 운영 부담이 늘어 사용자 판단 필요 |
| **D4** | "확정 지식"의 형태 | ㄱ. **KB 문서로 승격**(권장) / ㄴ. 대화 로그 재사용 | **ㄱ** — ㄴ은 고객별 맥락(주문번호·이름)이 섞여 오답 위험 |
| **D5** | 확정 문서의 우선순위 | 일반 문서와 동일 / 검색 가산점 부여 | 1차는 **동일**로 두고 계측 후 판단(GROUP_BONUS 선례대로 근거 없이 손대지 않음) |
| **D6** | 초안 생성에 쓸 AI 기능 | `rag`(고객 답변과 동일 파이프라인, 권장) / `assist` | **rag** — 고객에게 나갈 문장이므로 페르소나·응답규칙·지식이 동일하게 적용돼야 함 |

## 5. 리스크

| # | 리스크 | 대응 |
|---|---|---|
| R1 | 재위임 ↔ 에스컬레이션 왕복(핑퐁) | 재위임 후 일정 시간 내 재에스컬레이션은 **같은 상담원에게 우선 배정**하거나 카운트를 이력에 남겨 가시화 |
| R2 | 초안이 고객에게 실수로 즉시 발송 | 초안은 **별도 영역**에 표시, 전달은 명시적 2차 클릭. 초안 상태는 대화에 저장하지 않음 |
| R3 | 확정 지식이 기존 문서와 상충 | 기존 **지식 충돌 검출**이 상담 그룹을 이미 스캔하므로 자동 검출됨(상품 그룹만 제외 상태) |
| R4 | 상담사 권한 확대로 인한 지식 오염 | D3에서 승인형을 택하면 해소 |
| R5 | 초안 생성 지연(현재 RAG 8초) | 진행 표시 + 취소 가능. 상담원은 대기 중에도 직접 입력 가능해야 함 |
