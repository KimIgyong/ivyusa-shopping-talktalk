# REQ-260824-Tenant-AI-Engines

테넌트별 AI 엔진 모델 설정 — 요구사항 분석

- 요청일: 2026-08-24
- 요청 요지:
  - **현재**: 어드민에서 설정한 AI 엔진 모델을 전체 테넌트가 사용한다.
  - **개선**: 테넌트 설정에 개별 AI 엔진 모델 설정 기능을 추가하고, 테넌트가 별도 지정한
    엔진이 있으면 그것을 사용한다. 테넌트도 **복수 개**의 엔진을 지정할 수 있다.
- 선행: FR-070(멀티엔진 게이트웨이), `PLN-260804`(기능별 라우팅), [[ai-settings-console]]

## 0. 먼저 — 요청의 절반은 이미 동작합니다

코드를 읽고 확인한 사실입니다.

**① 라우팅은 이미 테넌트를 우선합니다.** `AiGatewayService.resolveRouting()`
(`ai-gateway.service.ts:143`)의 순서:

```
1. EXPLICIT          tenant_ai_settings(tenant, function) → engine_id
2. INHERITED         같은 테넌트의 다른 기능에서 상속(FUNCTION_INHERITS)
3. TENANT_DEFAULT    ai_engines WHERE tenant_id = <나> AND is_default = 1
4. PLATFORM_DEFAULT  ai_engines WHERE is_default = 1
5. NONE
```

**② 스키마도 이미 테넌트를 압니다.** `ai_engines.tenant_id`(nullable)가 존재하고,
한 테넌트가 여러 행을 가질 수 있으므로 **복수 엔진도 이미 표현 가능**합니다.
기능(chat/rag/summary/assist/moderation/coach)마다 다른 엔진을 붙이는 것도 이미 됩니다.

**③ 교차 테넌트 할당은 이미 막혀 있습니다.** `AiSettingService.upsert()`
(`ai-setting.service.ts:88`)가 `engine.tenantId != null && engine.tenantId !== tenantId`이면
거부합니다.

> **따라서 이 요구사항의 실제 내용은 "라우팅을 만드는 것"이 아니라
> "테넌트가 자기 엔진을 등록할 수 있게 하는 것"입니다.** 지금은 그 문이 없습니다.

## 1. AS-IS

### 1.1 엔진을 만들 수 있는 사람은 어드민뿐입니다

`ai-engine.controller.ts`의 4개 라우트가 전부 `@AdminOnly()` + `AI_ENGINE_MANAGE`입니다.

| 라우트 | 권한 |
|---|---|
| `GET/POST /ai-engines`, `PATCH/DELETE /ai-engines/:id` | **어드민 전용** |
| `GET /ai-settings`, `PUT /ai-settings/:function` | 테넌트(`AI_SETTINGS_MANAGE`) |

테넌트는 **이미 있는 엔진에 기능을 연결**만 할 수 있습니다. 자기 모델·자기 키로 엔진을
만들려면 어드민이 `tenant_id`를 넣어 대신 만들어 줘야 합니다.

### 1.2 스테이징 실측 (2026-08-24)

```
ai_engines
 id  tenant_id  provider   name             model            is_default  has_key
  1  NULL       stub       Built-in Stub    stub-1                    1        0
  2  NULL       anthropic  Anthropic Claude claude-opus-4-8           0        1
  3  NULL       openai     chatGPT          gpt-5                     0        1
```

**테넌트 소유 엔진은 0건입니다** — 세 개 모두 플랫폼(`tenant_id = NULL`).
그리고 6개 테넌트 전부가 모든 기능을 **엔진 2번 하나**에 붙여 두었습니다
(tenant 2만 6개 중 4개 기능 설정 — 나머지는 폴백).

즉 "전체 테넌트가 같은 모델을 쓴다"는 현상은 **라우팅의 한계가 아니라 데이터의 상태**입니다.
테넌트가 다른 걸 고를 수단이 없어서 그렇게 된 것입니다.

### 1.3 결함 2건 — 이 기능을 켜는 순간 문제가 됩니다 ⚠️

**D-1. 다른 테넌트의 엔진 목록이 그대로 노출됩니다.**
`GET /ai-settings`가 `aiEngineService.listEnabled()`를 그대로 `availableEngines`로 내려주는데
(`ai-setting.controller.ts:35`), 그 쿼리에는 **테넌트 필터가 없습니다**
(`ai-engine.service.ts:25` — `find({ where: { status: 'enabled' } })`).

지금은 플랫폼 엔진 3개뿐이라 드러나지 않습니다. 테넌트가 자기 엔진을 만들기 시작하면
**테넌트 A의 선택 목록에 테넌트 B의 엔진 이름·프로바이더·모델이 보입니다.** 고르면 400으로
막히긴 하지만(§0-③), 목록에 뜨는 것 자체가 노출이고 UX도 깨집니다.

**D-2. 플랫폼 기본값이 남의 테넌트 엔진을 집을 수 있습니다.**
폴백 4단계의 쿼리가 `where: { isDefault: 1, status: 'enabled' }`뿐입니다
(`ai-gateway.service.ts:158`) — **`tenant_id IS NULL` 조건이 없습니다.**

어떤 테넌트가 자기 엔진에 `is_default = 1`을 걸면, 아무 설정이 없는 **다른 테넌트의 요청이
그 엔진으로 갈 수 있습니다.** 그 엔진에 붙은 **API 키까지 함께 쓰입니다.** 지금은 테넌트 소유
엔진이 0건이라 발생하지 않지만, **이번 기능이 정확히 그 조건을 만듭니다.**

## 2. TO-BE

1. 테넌트가 **자기 AI 엔진을 등록·수정·비활성**할 수 있다(프로바이더·모델·엔드포인트·API 키).
2. 테넌트는 **여러 엔진**을 가질 수 있고, 기능별로 다르게 붙일 수 있다(이미 되는 부분).
3. 테넌트 엔진이 있으면 **그것이 플랫폼 엔진보다 우선**한다(이미 되는 부분 — 명시적 검증 필요).
4. 테넌트 하나를 **자기 기본값**으로 지정할 수 있다(`is_default`의 테넌트 스코프).
5. **다른 테넌트의 엔진은 보이지도, 쓰이지도 않는다**(D-1·D-2 해소).
6. 어드민은 여전히 플랫폼 엔진을 관리하고, **테넌트가 무엇을 쓰는지 볼 수 있다**.

### 범위 제외
- 새 프로바이더 어댑터 추가 — 현재 어댑터(anthropic/openai/voyage/stub) 범위 내에서.
- 사용량·과금 분리(테넌트 키로 호출하면 청구가 테넌트로 감) — **정책 결정 필요, §6 D3**.
- 모델별 파라미터 튜닝 — 이미 `tenant_ai_settings.params_json`에 있음.

| # | 갭 | 대응 방향 |
|---|---|---|
| **G1** | 테넌트가 엔진을 만들 수 없음 | 테넌트 스코프 엔진 CRUD 라우트(+capability). 서비스가 `tenant_id`를 **호출자에서** 강제 |
| **G2** | `listEnabled()`에 테넌트 필터 없음 (D-1) | `내 것 + 플랫폼(NULL)`만 반환 |
| **G3** | 플랫폼 기본값이 테넌트 엔진을 집음 (D-2) | 4단계 쿼리에 `tenantId IS NULL` 추가 |
| **G4** | `is_default`가 전역 유일성 가정 | 테넌트 스코프로 해석 — 한 테넌트에 기본값 1개 |
| **G5** | API 키 입력·회전 UI 없음 | 저장은 AES-GCM 기존 경로 재사용. **마스킹 표시**, 평문 재조회 금지 |
| **G6** | 어드민이 테넌트 엔진을 못 봄 | 어드민 목록에 소유 테넌트 표시 |
| **G7** | 키 유효성 확인 수단 없음 | 연결 테스트(1회 최소 호출) — 저장 전 확인 |

**스키마 변경 없음** — `ai_engines.tenant_id`가 이미 존재합니다. 마이그레이션 불필요.

## 4. 사용자 흐름

1. 테넌트 운영자가 **설정 → AI 엔진**을 연다. 목록에 **플랫폼 제공 엔진**(읽기 전용)과
   **내 엔진**이 구분되어 보인다.
2. **엔진 추가** — 프로바이더 선택, 모델명, (선택)엔드포인트, API 키 입력.
3. **연결 테스트** — 키가 유효한지 저장 전에 확인한다.
4. 저장하면 내 엔진 목록에 들어가고, **기본값으로 지정**할 수 있다.
5. **AI 설정** 화면에서 기능별로 엔진을 고른다 — 선택지는 이제 *내 엔진 + 플랫폼 엔진*뿐이다.
6. 아무것도 지정하지 않은 기능은 **내 기본값 → 플랫폼 기본값** 순으로 폴백하며,
   화면은 지금처럼 그 근거(`source`)를 표시한다.

## 5. 제약·전제

- **C1.** 라우팅 순서는 **이미 구현돼 있습니다**. 이번 작업은 그 위에 등록 경로를 여는 것이며,
  라우팅을 재작성하지 않습니다. 대신 **D-2를 고치지 않으면 3단계와 4단계가 뒤섞입니다.**
- **C2.** API 키는 `ai_engines.api_key_encrypted`(varbinary 2048, AES-256-GCM)에 저장됩니다.
  기존 경로를 그대로 쓰되 **읽기는 게이트웨이 내부로 한정**하고 콘솔에는 마스킹만 내려야 합니다.
- **C3.** `is_default`는 현재 전역 컬럼입니다. 테넌트 스코프로 해석하면 **플랫폼 기본값과
  테넌트 기본값이 같은 컬럼을 공유**하므로, 조회마다 `tenant_id` 조건이 빠지면 D-2가 재발합니다.
- **C4.** 테넌트가 자기 키를 넣으면 **호출 비용이 테넌트에게 청구**됩니다. 플랫폼 키를 계속
  쓰는 테넌트와 과금 주체가 갈립니다 → D3.
- **C5.** 잘못된 모델명·만료된 키는 **런타임에야 드러납니다.** 저장 전에 확인할 수단이 없으면
  "설정은 됐는데 대화만 조용히 stub으로 떨어지는" 상태가 됩니다([[invisible-fallback-trap]],
  [[staging-ai-stub-blockers]]에서 이미 한 번 겪음).
- **C6.** 기능은 6종(chat/rag/summary/assist/moderation/coach)이며 상속 규칙이 있습니다.
  엔진을 늘리면 조합이 늘어나므로 화면이 "지금 무엇이 실제로 쓰이는지"를 계속 보여줘야 합니다.

## 7. 결론

요청의 **라우팅 부분은 이미 있습니다**(§0). 실제로 없는 것은 **테넌트가 자기 엔진을 등록할
경로**이며, 그래서 스테이징의 테넌트 소유 엔진이 0건이고 6개 테넌트가 같은 엔진을 씁니다.

가장 주의할 것은 **결함 2건이 이번 기능으로 활성화된다는 점**입니다.

- **D-1**: 지금은 플랫폼 엔진뿐이라 안 보이는 목록 노출이, 테넌트 엔진이 생기는 순간 드러납니다.
- **D-2**: 플랫폼 기본값 폴백에 `tenant_id IS NULL`이 없어, 테넌트가 자기 엔진을 기본값으로
  지정하는 순간 **다른 테넌트가 그 엔진과 그 API 키로 응답할 수 있습니다.**

둘 다 지금은 발생하지 않습니다. 이 기능이 정확히 그 전제 조건을 만듭니다(D5).
