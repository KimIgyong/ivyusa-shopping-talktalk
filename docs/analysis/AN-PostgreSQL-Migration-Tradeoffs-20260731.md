# AN — MySQL → PostgreSQL 전환 장단점 분석

- 작성일: 2026-07-31
- 선행 문서: `AN-KB-Retrieval-FulltextVsVector-20260731.md`, `AN-VectorDB-Selection-20260731.md`
- 목적: ShopTalk의 DB를 MySQL 8.0에서 PostgreSQL(+pgvector)로 변경할 경우의 장단점·전환 비용·권고

---

## 1. 전제: 현재 MySQL 종속 지점 (코드 스캔 결과)

| 종속 지점 | 규모 | 전환 시 작업 |
|---|---|---|
| TypeORM 드라이버 | `type: 'mysql'` + `mysql2` | `type: 'postgres'` + `pg` 교체 — 설정 2곳 |
| 엔티티 컬럼 타입 | 40개 엔티티 중 **`datetime` ~20곳, `tinyint` ~13곳, `longtext` 2곳**은 PG에 없는 타입 → DDL 에러 | `timestamp`/`boolean`(또는 `smallint`)/`text`로 일괄 치환. `bigint·varchar·text·json·decimal`은 호환 |
| FULLTEXT 검색 | `rag.service.ts:60-61` `MATCH…AGAINST` 2곳 + `ft_kb_title_content` ngram 인덱스 | **PG에 직접 대응물 없음** — 한국어 검색 대체 설계 필요(§3) |
| 원시 SQL | `.query()` 4곳 (`?` 플레이스홀더) | PG는 `$1` 방식 → 4곳 수정 (경미) |
| DDL 스크립트 | `sql/01-schema.sql` + 마이그레이션 2본 (MySQL 방언: AUTO_INCREMENT, ENGINE, backtick 등) | PG 방언으로 재작성. dev는 `synchronize: true`라 TypeORM이 생성 — 스테이징/운영용만 재작성 |
| 인프라 | `mysql:8.0` 컨테이너(dev/staging/prod), 스테이징 실데이터 | 이미지 교체 + 데이터 이관(pgloader 등) |
| 기타 | bcrypt/AES-GCM 암호화는 앱 레벨 → 무관. 예약어 backtick(`` `rank` ``) → 쌍따옴표 | 경미 |

전체적으로 종속은 **잘 격리되어 있는 편**이다(레포지토리 패턴, ORM 중심). 최대 난제는 데이터 이관이 아니라 **한국어 전문검색 대체**와 **전량 회귀 검증**이다(현재 자동화 테스트 0건 — 감사 보고서 기준).

## 2. 장점 (PostgreSQL 전환 시 얻는 것)

1. **pgvector로 벡터·키워드·메타데이터 단일 저장소** — 별도 벡터 스토어(Qdrant 등) 없이 HNSW ANN,
   `tenant_id` 필터, 원문 조인을 한 쿼리로 처리. 동기화 파이프라인·정합성 문제 원천 제거.
   RAG 관점에서 전환의 가장 큰 실익.
2. **Row-Level Security(RLS)** — `tenant_id` 격리를 앱 코드가 아닌 DB 정책으로 강제 가능.
   감사 보고서의 최우선 갭("full tenant_id coverage + tenant-scope guard")을 구조적으로 해결하는
   수단. MySQL에는 대응 기능 없음.
3. **jsonb** — 현 `json` 컬럼(config_json 등)에 인덱스·연산자 지원, 부분 인덱스/표현식 인덱스 등
   인덱싱 유연성 전반 우위.
4. **트랜잭셔널 DDL** — 마이그레이션 실패 시 자동 롤백. 무중단 배포 운영 안정성.
5. 성숙한 확장 생태계(pg_trgm, pg_partman, PostGIS…), 정교한 쿼리 플래너, 표준 SQL 준수.
6. 라이선스 명확(PostgreSQL License) — MySQL의 Oracle 이중 라이선스 고려사항 제거.

## 3. 단점·리스크 (잃는 것과 비용)

1. **한국어 전문검색 하향** — 최대 기술 리스크. MySQL ngram FULLTEXT는 CJK를 기본 지원하지만
   PG 기본 tsvector는 한국어 형태소를 다루지 못한다. 대안:
   - `pg_trgm`(trigram) 유사도 검색 — 설치 간단, 한국어 실용 수준이나 ngram 대비 recall 특성 상이
   - `pg_bigm`(bigram) — CJK 특화, 별도 확장 설치 필요(관리형 PG에선 미지원인 곳 많음)
   - textsearch_ko/mecab — 품질 최고이나 운영 복잡도 높음
   → 어떤 안이든 **검색 품질 재검증 필수**. (단, 벡터 하이브리드로 가면 키워드 레그의 비중이
   줄어 리스크가 완화되는 측면도 있음)
2. **전환 공수와 회귀 리스크** — 엔티티 타입 치환(~35곳), DDL 재작성, 데이터 이관, 전 도메인
   동작 검증. **자동화 테스트가 0건**이라 회귀를 수동 검증해야 하는 것이 실질적 최대 비용.
   Nest 메이저/락파일 재생성류 부수 작업 포함 추정 공수 1~2주 + 안정화 기간.
3. **운영 전환 비용** — 백업/복구 절차, 모니터링, 계정 관리 재정립. 스테이징·운영 데이터
   이관 시 다운타임 창 필요. 팀의 MySQL 운영 경험 대비 PG 숙련도 확인 필요.
4. 세부 동작 차이 — 대소문자 구분(기본 collation), `GROUP BY` 엄격성, upsert 문법
   (`ON DUPLICATE KEY` → `ON CONFLICT`), 0000-00-00 류 관용 동작 부재 등 잠복 이슈.

## 4. 판단 프레임

| 전환 동기 | 판정 |
|---|---|
| "벡터 검색 때문에" | **비권장** — MySQL 유지 + (Phase 1) JSON 컬럼 브루트포스 → (Phase 2) Qdrant 추가가 공수 1/5 이하로 같은 효과. 벡터만으로는 전환 ROI가 나오지 않음 |
| "벡터 + RLS 테넌트 격리 + 단일 저장소 전략" | **검토 가치 있음** — 전환의 진짜 실익은 pgvector 단독이 아니라 RLS(멀티테넌트 보안 갭 해소)와 저장소 통합의 결합 효익 |
| 전환한다면 시점은 | **지금이 최저 비용** — 운영 데이터가 적고(스테이징 단계), 스키마가 계속 진화 중이며, 테스트 부재로 어차피 검증 체계를 세워야 하는 시점. 정식 런칭·데이터 축적 후에는 비용이 배수로 증가 |

## 5. 권고

1. **기본 권고(현 계획 유지)**: MySQL 유지 + 단계별 벡터 도입(선행 문서 로드맵). 정책 KB 등록과
   AI 품질 개선이 당면 목표라면 DB 전환은 그 목표를 지연시키는 우회로다.
2. **조건부 전환**: RLS 기반 테넌트 격리를 보안 로드맵의 필수 요건으로 채택하고, 상품 지식·외부
   소스 확장으로 벡터 규모가 커질 것이 확정적이라면 — **정식 런칭 전인 지금 전환**하는 것이
   유일하게 합리적인 창구다. 이 경우:
   - 선행 조건: 핵심 플로우(E2E) 테스트 최소 세트 구축 → 전환 → 동일 테스트로 검증
   - 한국어 검색은 pg_trgm으로 시작하되 하이브리드(pgvector)로 조기 전환해 키워드 레그 의존 축소
   - 데이터 이관은 pgloader + 검증 스크립트(행 수·체크섬), 스테이징에서 리허설 후 운영 적용
3. 어느 쪽이든 **"벡터 때문에 두 RDBMS(MySQL+PG) 병행"은 금지** — 이중 운영 비용이 모든 대안 중 최악.

## 6. 한 줄 요약
> pgvector·RLS·jsonb는 실제 매력적이지만, 전환의 손익은 "벡터"가 아니라 "RLS 테넌트 격리 + 단일
> 저장소"에서 갈린다. 벡터만 필요하면 MySQL+Qdrant, 보안·통합까지 원하면 런칭 전인 지금 전환 —
> 단 한국어 전문검색 대체와 무(無)테스트 상태의 회귀 검증이 실질 비용의 대부분이다.
