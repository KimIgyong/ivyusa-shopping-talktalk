## 2-1. 실 LLM 검증 (2026-08-13 스테이징 배포 후 실행) — B-07/B-08 통과

tenant 1, coach 엔진 Anthropic, `provider=anthropic`. **제안은 하나도 승인하지 않았고**
전후 rules·scenarioOverrides 동일 확인. 스레드는 보관, 제안 3건은 `rejected` 처리.

**B-07 — 사실 피드백이 지식으로 간다. 2단계로 통과했다.**

1차 입력: "반품 배송비 — 불량·오배송은 회사 부담, 단순 변심은 고객이 왕복 6,000원 부담"
→ **제안 0건.** 대신 기존 문서 `docId=40`이 **$6.95**로 되어 있어 금액도 통화도 다르다고 지적하고,
사유별 구분이 신규 추가가 맞는지 되물었다. (프롬프트의 "문서와 모순되면 먼저 확인하고 조용히
덮어쓰지 말라"가 그대로 동작)

2차 입력(모순 해소): "$6.95가 맞다. 사유별 구분은 신규 추가다. docId=40을 수정해라"
→ **`kb_upsert` 제안 생성**:

| 필드 | 값 |
|---|---|
| `docId` | **40** — 새 문서를 만들지 않고 **기존 문서를 개정** |
| `docCategory` | `policy_return` — 컨텍스트의 실제 카테고리 중에서 선택 |
| `docContent` | 사유별 부담 구분 + **$6.95**(관리자가 확정한 값), 상담원 지시문이 아닌 **고객에게 답할 수 있는 산문** |

즉 W1에서 "지식 문서가 필요하다"고 **막기만** 하던 것이, 이제 **올바른 문서를 지목해 개정 제안**까지 간다.
`docId` 주입이 없었다면 모델은 새 문서만 제안할 수 있었고 KB는 스스로 모순됐을 것이다.

**B-08 — `scenario_override` 제안 생성.** `scenarioAction: cancel_refund`(라벨이 아닌 **action 키**),
언어별 reply 맵. 공감 문장으로 시작하도록 재작성됨.

### 이 검증이 찾아낸 결함 2건 (같은 PR에서 수정)

**D-1. 같은 대상의 pending 제안이 서로를 무효화하지 않았다.**
`scenario_override` 제안 2건(#4, #6)이 같은 `cancel_refund`를 겨냥했는데 둘 다 pending으로 남았다.
`supersedePeers`가 persona와 `targetRule`만 알고 있어서, W3에서 타입을 추가하며 확장하지 않은 탓이다.
→ 대상 판정을 `sharesTargetWith`로 분리하고 타입별로 명시했다(persona=전체, rule=targetRule,
scenario=action, kb=docId). **신규 문서 제안 2건은 서로 무관하므로 무효화하지 않는다.** 테스트 2건 추가.

**D-2. 시나리오 현재 문구가 컨텍스트에 없었다.**
모델이 *"현재 스크립트 원문이 제게 표시되지 않아 새로 작성했습니다"* 라고 말했다 — 고치라고 한 문구를
**처음부터 새로 쓴** 것이다. 컨텍스트에 action 목록과 "편집 있음" 표시만 있고 본문이 없었다.
→ 테넌트 편집 본문을 컨텍스트에 포함시켰다. ⚠️ **한계**: 편집이 없는 버튼의 내장 스크립트 원문은
`ScenarioService`(코드)에 있어 여전히 보이지 않는다. 그 경우 "내장 스크립트(본문 비공개)"로 명시한다.

화면에서 사라지던 문제) 수정이 실제 화면에서 동작함을 확인했다.

### 실측에서 관측된 것 2건 (결함 아님, 후속 판단 필요)

**O-1. 적용한 규칙의 효과가 재실행 답변에 드러나지 않았다.**
"배송 답변 첫 문장에 기다리게 해서 미안하다는 공감을 넣어라"는 규칙을 적용하고 같은 질문을
재실행했으나, 새 답변은 여전히 "안녕하세요! 배송 소요 기간 안내해 드릴게요"로 시작했다(문구는
조금 바뀌고 conf 0.66→0.69). 제안 카드가 이미 **기존 규칙 5번("Never open with a disclaimer")과
충돌 가능**을 경고했고, 질문이 "배송이 얼마나 걸리나요?"라는 일반 문의라 "기다림에 대한 공감"이
적용 대상이 아니라고 모델이 판단했을 수도 있다. **B-05가 검증하는 것은 전환·재실행 동작이며 그것은
통과**했다. 규칙이 실제로 답변을 바꾸는지는 별도 판단이 필요하다 — **W4 회귀 검증이 정확히 이 질문을
자동화하려는 것**이다.

**O-2. 내장 스크립트 원문은 여전히 보이지 않는다 — 그리고 모델이 그렇게 말한다.**
배송 관련 코칭에서 모델이 *"배송 상태 안내는 built-in 스크립트(delivery_status 버튼)가 담당합니다.
현재 원문 텍스트가 보이지 않아 전체 문안을 새로 작성해야 합니다"* 라고 명시하고, 규칙으로 처리할지
`scenario_override`로 갈지 되물었다. #266에서 테넌트 편집 본문은 넣었지만 내장 스크립트는 코드에
있어 여전히 비공개인 상태가 **의도대로 드러난 것**이다 — 조용히 새로 쓰지 않는다.

## 3-1. 원래 계획했던 확인 항목 (참고)

패널 간 연동은 서버가 아니라 화면 상태라 자동화 범위 밖이다.

| # | 항목 | 확인 방법 |
|---|---|---|
| B-01 | 시뮬레이션 AI 버블 hover 시 **[코칭하기]** 노출 | 시나리오 스크립트 답변에는 **안 보여야** 함(영속 id 없음) |
| B-02 | [코칭하기] → 코칭 탭 전환 + 첨부 칩 표시 | 칩에 그 답변이 보이고 `×`로 해제 가능 |
| B-03 | 첨부 상태로 전송 → 답변에 **참조 턴 블록** 렌더 | conf/인용 배지가 저장값으로 표시 |
| B-04 | 탭 왕복 시 **프리뷰 세션 유지** | 대화가 초기화되지 않아야 함(패널을 unmount하지 않음) |
| B-05 | 제안 적용 후 **[시뮬레이션에서 확인]** | 프리뷰 탭 전환 + 같은 질문 자동 재실행 |
| B-06 | `kb_upsert` 카드에 되돌리기 버튼 **없음** + 이력 안내 문구 | E4016을 부를 버튼을 애초에 노출하지 않음 |
| B-07 | 실 LLM에서 사실 피드백 → **`kb_upsert` 제안 생성** | W1에서 "지식 문서가 필요하다"고 안내만 하던 것이 이제 제안이 되는지 |
| B-08 | 카테고리 없는 신규 문서 제안이 나오지 않는지 | 컨텍스트의 `EXISTING_CATEGORIES` 중에서 고르는지 |

**B-07이 W3의 실질 목표다.** U-02에서 확인된 "사실은 규칙이 아니다"가 이제 **막는 데 그치지 않고
올바른 곳으로 보내는지**를 봐야 한다.
