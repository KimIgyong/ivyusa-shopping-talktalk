# REQ-260824-Knowledge-Taxonomy-Per-Tenant

지식 분류 체계의 테넌트화 — Usage guides 유형 + 문서 카테고리 관리

- 요청일: 2026-08-24
- 요청 요지:
  1. `https://shoptalk.amoeba.site/knowledge`의 **Usage guides**가 IVY USA에만 맞춰져 있다.
     각 테넌트가 자기 Usage guides를 작성할 수 있어야 한다.
  2. **카테고리 관리 기능**도 함께 구현한다.
- 선행: `PLN-260807` P2(사용법 가이드), `PLN-260804` D2(doc_group/category 2단 분류)

## 0. 두 요청의 관계 — 같은 병, 다른 증상

둘 다 `/knowledge` 한 화면의 분류 체계이고, 둘 다 IVY USA 기준으로 고정돼 있습니다.
다만 **고장 난 방식이 정반대**라 대응도 달라집니다.

| | Usage guide 유형 | 문서 카테고리 |
|---|---|---|
| 저장 | 코드 상수 `USAGE_TYPES` 10종 | `kb_documents.category` **자유 문자열** varchar(64) |
| 테넌트가 새로 만들 수 있나 | **불가** — `upsert()`가 목록 대조 후 400 | **가능** — 아무 값이나 타이핑 |
| 실제 문제 | **닫힌 게이트** — 자기 유형을 만들 수 없다 | **관리 부재** — 만들 수만 있고 이름변경·병합·삭제·정렬이 없다 |
| 본문/문서의 테넌트 격리 | 이미 됨(`tenant_id`) | 이미 됨(`tenant_id`) |

> **먼저 짚을 것**: 가이드 **본문**은 이미 테넌트별입니다. `list()`·`upsert()`가 `tenantId`로
> 스코프되고 `kb_documents`에도 `tenant_id`가 있습니다(`usage-guide.service.ts:50,68,93`).
> 테넌트별이 아닌 것은 **"쓸 수 있는 유형 목록"**입니다. 본문 저장·격리는 재구현하지 않습니다.

# A. Usage guide 유형

## A-1. AS-IS

```
USAGE_TYPES (코드 하드코딩, 10종)      ← 테넌트 공용. 여기가 문제
  └ key + keywords[]
       │ classifyUsageType(title+category+tags) 첫 매치 우선
       ▼
products_cache (tenant_id)  ──▶ 유형별 "상품 N개" 집계
       │
kb_documents (tenant_id, category='How to Use',
              external_key='usage:{key}')          ← 본문. 이미 테넌트별
       ▼
RAG 검색 시 상품 문서 옆에 인용
```

10종은 IVY USA의 K-뷰티 카탈로그에 맞춘 것입니다 — 속눈썹 접착제·붙임 손톱·헤어컬러·가발 등
(`usage-guide.types.ts:22`). 콘솔은 이 10행을 그대로 보여주고(`KnowledgePage.tsx:663-702`),
라벨은 i18n 키 `usageType_{key}`로 렌더합니다(`:670`).

## A-2. 실측 — 스테이징 2026-08-24

하드코딩된 10종 분류표를 각 테넌트 카탈로그에 실제로 돌린 결과:

| 테넌트 | 활성 상품 | 분류된 상품 | 비율 | **작성된 가이드** |
|---|---:|---:|---:|---:|
| 1 ivyusa | 2,260 | 1,482 | **65%** | **0** |
| 2 annehearts (여성 의류) | 144 | **0** | **0%** | **0** |
| 3 amoebaorder | 23 | **0** | **0%** | **0** |
| 4 go2joy | 0 | — | — | **0** |
| 5 skyliving / 6 gif2box | 0 | — | — | **0** |

**① 비뷰티 테넌트에서 이 기능은 죽어 있습니다.** annehearts 운영자가 보는 화면은
"속눈썹 접착제 — 상품 0개"가 10줄 이어진 표입니다. 정작 필요한 세탁·소재·사이즈 안내를
만들 칸은 없습니다.

**② ivyusa조차 한 건도 쓰지 않았습니다.** 유형이 맞는 테넌트에서도 사용된 적이 없습니다.
유형을 열어주는 것이 필요조건이지만 충분조건은 아닐 수 있습니다(§D-5).

## A-3. 유형 라벨이 i18n 키에 묶여 있습니다 ⚠️

라벨은 번역 파일에 있습니다 — `usageType_lashes`, `usageType_press_on_nails` … **10종 × 6개 언어**.
**테넌트가 만든 유형은 이 키가 없습니다.** i18next는 키가 없으면 키 문자열을 그대로 출력하므로
`usageType_laundry_care` 같은 날문자열이 화면에 찍힙니다.

유형을 데이터로 옮기는 순간 **라벨도 데이터여야 하고**, 그때 6언어 정책을 정해야 합니다(D1).
A축에서 가장 구조적인 제약입니다.

## A-4. 그 외 하드코딩

- `USAGE_GUIDE_CATEGORY = 'How to Use'` — 영어 고정이며 문서 `category`로 저장됩니다(`:13`).
- 분류는 **첫 매치 우선**이라 배열 순서가 곧 우선순위입니다(`lash_adhesive`가 `lashes`보다 앞).
- `external_key='usage:{key}'`(`:80`)가 문서의 안정 키입니다. 유형 키가 바뀌면 문서가 고아가 됩니다.

# B. 문서 카테고리

## B-1. AS-IS — 만들 수만 있고 정리할 수 없습니다

`kb_documents.category`는 **자유 문자열**(varchar(64), nullable)이고 테넌트별로 격리돼 있습니다.
따라서 테넌트는 이미 아무 카테고리나 만들 수 있습니다. 없는 것은 **관리**입니다.

콘솔의 제안 목록은 이렇게 만들어집니다(`KnowledgePage.tsx:155-161`):

```
categorySuggestions = (이 테넌트가 실제 쓰는 카테고리) ∪ (하드코딩 19종)
                                                        ↑ IVY USA 정책 태그
   policy_beautizen · policy_roundtable · policy_b2b · policy_professional …
```

이름변경·병합·삭제·정렬·숨김 기능은 **하나도 없습니다.**

## B-2. 실측 — 스테이징 2026-08-24

**하드코딩 19종 중 각 테넌트가 실제로 쓰는 것:**

| 테넌트 | 19종 중 사용 |
|---|---:|
| 1 ivyusa | **18** |
| 2 annehearts | **1** |
| 3 amoebaorder | 5 |
| 4 go2joy | 3 |
| 5, 6 | 0 |

annehearts 운영자는 **19개 제안 중 1개만 자기 것**인 목록에서 고릅니다. 나머지 18개는
다른 테넌트의 정책 태그입니다.

**각 테넌트가 실제로 쓰는 카테고리:**

| 테넌트 | 문서 | 서로 다른 카테고리 | 실제 값 |
|---|---:|---:|---|
| 1 ivyusa | 2,071 | **63** | `knowledge_store` 39종 + `product_catalog` 26종이 **한 목록에 섞임** |
| 2 annehearts | 238 | 8 | `All`(134) · `Artist / Journal`(8) · `SHOP`(7) · `26SS Collection 1st Lookbook`(2) · `faq`(1) … |
| 3 amoebaorder | 34 | 11 | `립` `아이` `페이스` `향수` `소품` `기타` + `policy_return` `policy_cancellation` … |
| 4 go2joy | 16 | 3 | `faq`(13) · `policy`(2) · `policy_payment`(1) |

두 가지가 보입니다.

**① 사람이 만든 분류와 카탈로그가 자동 생성한 분류가 구분 없이 섞입니다.** ivyusa의 63종 중
26종은 상품 동기화가 만든 것(`product_catalog`)이고 39종은 사람이 만든 것(`knowledge_store`)인데,
콘솔에는 한 줄로 나열됩니다. annehearts의 `All`(134건)·`26 Summer Lookbook`도 카탈로그 파생입니다.

**② 정리할 수단이 없습니다.** 오타나 표기 흔들림이 생기면 조용한 중복이 되고 되돌릴 방법이
없습니다. *현재 대소문자·공백만 다른 중복은 0건입니다* — 아직 문제가 나타나지 않았을 뿐,
방어 수단이 없다는 사실은 그대로입니다.

## B-3. 이름을 바꾸면 어디까지 건드려야 하나

카테고리 변경의 실제 비용을 코드로 확인했습니다.

- **임베딩 벡터는 재생성 불필요** — 임베딩 입력은 `title\ncontent`뿐입니다
  (`knowledge.service.ts:583`). 카테고리는 벡터에 들어가지 않습니다.
- **MySQL 일괄 UPDATE가 본체입니다** — RAG는 Qdrant 히트의 id로 **MySQL에서 문서를 다시 읽고**
  (`rag.service.ts:207`) 인용 라벨에 `doc.category`를 씁니다(`:228`). 즉 표시되는 카테고리의
  출처는 DB입니다.
- **Qdrant 페이로드에도 사본이 있지만 현재 아무도 읽지 않습니다** — 페이로드에 `category`가
  저장되고(`knowledge.service.ts:596`) keyword 인덱스도 걸려 있지만(`qdrant.service.ts:65`),
  `search()`의 필터는 `active`와 `tenant_id`뿐입니다(`qdrant.service.ts:110-115`).
  검색·표시 어느 쪽도 이 값을 쓰지 않습니다.
- **그리고 페이로드만 고치는 경로가 없습니다** — `QdrantService`에는 `upsert`/`setActive`/`delete`만
  있고 `setPayload`가 없습니다.

**정리하면**: 이름 변경의 정확성은 MySQL 갱신만으로 확보됩니다. Qdrant 사본은 낡은 채로 남지만
**오늘은 아무 동작도 바꾸지 않습니다.** 다만 나중에 카테고리 필터링을 붙이는 사람에게는
조용한 지뢰가 되므로, 지금 정리할지 기록만 할지 정해야 합니다 → D9.

### ⚠️ 카탈로그 파생 카테고리는 되살아납니다 (코드 확인)

`catalog-sync.service.ts:319`가 문서 카테고리를 `rep.vendor ?? rep.category`로 채우고,
`:345`에서 `(doc.category ?? null) === next.category`로 무변경을 판정합니다.
**운영자가 이름을 바꾸면 다음 동기화가 차이를 감지해 원래 이름으로 되돌려 씁니다.**
ivyusa의 카탈로그 파생 26종은 사실상 **브랜드명**입니다. D8의 근거입니다.

## 2. TO-BE

### A축 — Usage guide 유형
1. 유형 목록이 **테넌트별 데이터**가 된다. 추가·수정·비활성 가능.
2. 유형은 **라벨과 키워드를 함께** 가진다. 키워드가 자기 카탈로그에 맞아야 "상품 N개"가 의미를 갖는다.
3. 신규 테넌트에 **기본 세트 시딩** — 직무 라벨 선례(`tenant.service.ts:166` `seedDefaultJobLabels`).
4. 기존 IVY USA 10종은 **ivyusa 테넌트의 데이터로 이관**(무회귀).
5. 본문 작성·저장·인용 흐름은 **그대로**.

### B축 — 카테고리 관리
6. `/knowledge`에 **카테고리 관리** 화면. 테넌트가 쓰는 카테고리를 문서 수와 함께 보여준다.
7. **이름 변경 · 병합 · 삭제(미사용에 한함) · 정렬 · 숨김**을 제공한다.
8. 제안 목록에서 **다른 테넌트의 정책 태그를 걷어낸다** — 제안은 자기 테넌트 것 + 자기 기본 세트.
9. **출처를 구분해 보여준다** — 사람이 만든 것과 카탈로그 파생을 섞지 않는다.
10. 이름 변경 시 **MySQL과 Qdrant 페이로드를 함께** 갱신한다(B-3).

### 범위 제외
- **가이드 본문 자동 생성(LLM)** — 화장품 사용법을 지어내는 것은 콘텐츠 갭이 아니라 안전 문제입니다.
  기존 코드가 명시적으로 내린 판단이며(`usage-guide.service.ts:31-32`) 유지합니다.
- **`doc_group` 변경** — 상위 분류(닫힌 집합)는 이번 범위가 아닙니다. 카테고리만 다룹니다.
- 가이드/문서 **본문의 다국어 버전** — KB 전체의 별도 주제.
- 카탈로그 파생 카테고리의 자동 생성 규칙 변경 — 이번엔 **표시와 정리**만.

## 4. 사용자 흐름

**A. 유형을 만들고 가이드를 쓴다**
1. `/knowledge` → **Usage guides** 카드. 자기 테넌트 유형 목록이 보인다(신규는 기본 세트).
2. **유형 추가** — 라벨("세탁·소재 관리")과 키워드(`cotton`, `linen`, `wool`) 입력.
3. 저장하면 자기 카탈로그에서 **몇 개 상품에 걸리는지 즉시 개수로 확인**된다.
   0이면 키워드가 틀린 것이므로 그 자리에서 고친다.
4. **작성**을 눌러 본문(단계·주의사항)을 쓴다 — 기존 흐름 그대로.
5. 맞지 않는 기본 유형은 **비활성**(삭제 아님 — 이미 쓴 본문을 지키기 위해).

**B. 카테고리를 정리한다**
6. `/knowledge` → **카테고리 관리**. 자기 카테고리가 문서 수·출처와 함께 나열된다.
7. 오타를 발견하면 **이름 변경** — 해당 문서 전체와 검색 필터가 함께 따라온다.
8. 사실상 같은 두 카테고리를 **병합** — 문서가 한쪽으로 옮겨지고 빈 쪽은 사라진다.
9. 문서가 0건인 카테고리는 **삭제**, 쓰지 않지만 남길 것은 **숨김**.

## 5. 제약·전제

- **C1.** 테넌트가 입력한 라벨은 사전 번역할 수 없습니다. 시스템 언어는 6종이지만
  ([[i18n-six-languages]]) 운영자에게 6언어 입력을 요구하는 것은 과합니다 → D1.
- **C2.** A축 분류는 첫 매치 우선이므로 **순서가 데이터**여야 합니다(G7).
- **C3.** `external_key='usage:{key}'`가 문서의 안정 키입니다. 이관 시 키를 바꾸면 기존 가이드가
  고아가 됩니다. 현재 0건이라 위험은 낮지만 규칙은 지킵니다.
- **C4.** 스키마 변경이 있으므로 **SQL을 스테이징 DB에 먼저 적용한 뒤 코드를 배포**합니다
  (staging `DB_SYNCHRONIZE=false`).
- **C5.** 상품 0개 테넌트(go2joy·skyliving·gif2box)에서는 유형을 만들어도 "상품 0개"입니다 → D3.
- **C6.** 키워드 편집은 운영자에게 **분류 규칙을 편집하게 하는 일**입니다. 잘못 넣으면 조용히
  0개가 되거나 엉뚱한 상품이 묶입니다. A-4단계의 즉시 개수 확인이 이 위험의 방어선입니다.
- **C7.** 카테고리 이름 변경의 정확성은 **MySQL 갱신만으로** 확보됩니다(B-3) — 표시·검색 어디서도
  Qdrant의 카테고리 사본을 읽지 않습니다. 벡터 재생성도 불필요합니다.
- **C8.** `category`는 varchar(64)입니다. 라벨을 길게 쓰면 잘립니다.
- **C9.** 카탈로그 파생 카테고리는 **다음 동기화에서 되살아납니다.** 이름을 바꿔도 상품 동기화가
  원래 이름으로 다시 만들 수 있습니다 → D8.

## 7. 결론

두 요청 모두 **IVY USA 기준으로 고정된 분류 체계를 테넌트의 것으로 만드는 일**입니다.
문서·본문의 테넌트 격리는 이미 되어 있으므로 손대지 않습니다.

축마다 성격이 다릅니다. **A축은 닫힌 게이트를 여는 일**이고(만들 수 없던 것을 만들 수 있게),
**B축은 열린 채 방치된 것을 정리하는 일**입니다(만들 수만 있던 것을 관리할 수 있게).

가장 주의할 두 지점:
- **A축**: 라벨이 i18n 키에 묶여 있어(§A-3), 데이터로 옮기는 순간 6언어 정책을 정해야 합니다(D1).
- **B축**: 카탈로그 파생 카테고리는 **이름을 바꿔도 다음 동기화가 되돌려 씁니다**(§B-3, `catalog-sync.service.ts:345`).
  이걸 모르고 편집을 열어주면 운영자는 "고쳤는데 다시 돌아온다"를 겪습니다.

그리고 숫자 하나를 기록해 둡니다 — **작성된 가이드는 전 테넌트 통틀어 0건입니다**(D5).
