## 0. 요약 (결론 먼저)

| # | 요구 | 현행 | 판정 |

| 2 | 상담원별 대화 보기 | `conversations.agent_id` 컬럼 존재, **조회 필터·화면 없음** | **미구현(기반은 있음)** |

**가장 중요한 발견 4가지** *(v1.0.1에서 B1 관련 서술 정정 — 상단 정정 이력 참조)*
1. **과거 AI 답변이 어떤 지식을 썼는지 이미 로그에 남아 있습니다** — `messages.retrieval_trace`에
   citations(문서 id·제목·출처)와 confidence가 JSON으로 저장되어 `JSON_EXTRACT`로 집계 가능
   (실측: 저장된 12건 모두 citations·confidence 보유). ④와 ⑤의 데이터 기반이 이미 확보돼 있습니다.
2. **대화 로그는 365일 후 하드 삭제됩니다**(`retention.service.purgeExpired()`, messages→
   conversations→cjm→notifications 순 `DELETE`). 통계를 원본 로그에서만 계산하면 **퍼지 시점에
   과거 수치가 영구 소실**됩니다 → 집계 스냅샷 설계가 필수 전제입니다.
3. **`agent_daily_stats` 테이블이 이미 존재하지만 쓰는 코드가 없어 0건입니다**(읽기 API만 존재).
   ③·④는 "새로 만들기"가 아니라 **"설계된 빈 껍데기를 채우는" 작업**에 가깝습니다.
4. **현재 감사 로그를 볼 수 있는 사용자가 아무도 없습니다** — 화면은 시스템 관리자 라우트에 있는데
   API는 테넌트 권한을 요구해 **관리자는 403**, 권한이 있는 테넌트 마스터에게는 **메뉴가 없습니다**.
   ③은 기능 추가 이전에 이 불일치 해소가 선행되어야 합니다(§5-1 B4).

## 1. 고객 대화 로그 보기

### 현행
- 화면 `apps/web/src/domain/history/HistoryPage.tsx` — 목록 컬럼: id(8자리)·고객명·상태·이관여부·
  메시지 수·시작일. 필터 2종(상태/이관), 페이지네이션 있음.
- 상세: 클릭 시 모달이 열리지만 **id·고객·상태·요약·시작/종료 시각만** 표시.
- API: `GET /analytics/conversations`(목록). 대화 내용 조회는 **상담원 콘솔** 경로에만 존재
  (`GET /agent/conversations/:id`, `CONVERSATION_HANDLE` 권한, 조회 시 PII 감사 기록).

### 갭
- **대화 원문을 이력 화면에서 볼 수 없음** — 요구의 핵심. 전체 대화를 읽는 유일한 경로는
  상담원 콘솔(`CONVERSATION_HANDLE`)이며, 그마저 **대기/진행 중 대화 큐만** 보여주므로
  **종료된 대화는 콘솔에서 도달할 수 없습니다**(딥링크 `?c=<id>` 예외).
- 메시지 본문 검색 없음, 기간 필터 없음, 채널(`preview` 포함) 구분 표시 없음, 정렬 불가.
- AI 답변의 근거·confidence가 저장돼 있으나 **어떤 읽기 경로에서도 반환하지 않음**
  (`ChatMapper`/`agent.mapper` 모두 `retrieval_trace`를 버림).

### ⚠️ 조사 중 발견한 기존 결함 (전체 목록은 §5-1)
| 결함 | 내용 |
|---|---|
| **상세 API 부재(404)** | `history.service.detail()`이 `GET /analytics/conversations/:id`를 호출하나 **해당 라우트가 없음** — 죽은 코드 |
| **3개 컬럼이 항상 `—`** | 화면은 `customerName`·`summary`·`startedAt`을 렌더링하지만 `searchConversations`는 `{id,status,escalated,messageCount,createdAt,endedAt}`만 반환 |
| ~~메시지 tenant_id 미기록~~ **(정정됨)** | 세 곳의 메시지 쓰기 경로(`chat`/`scenario`/`agent.service`)가 `tenantId`를 명시하지 않는 것은 사실이나, `TenantSubscriber.beforeInsert`가 요청 컨텍스트에서 **자동 스탬프**합니다. 실측 40건 전부 `tenant_id` 보유 → **통계는 정상 동작**. 잔존 위험은 §5-1 B1 참조 |
| 감사 누락 | `/analytics/conversations` 경로에는 PII 열람 감사가 없음(상담원 경로에만 존재) |

### 고려사항
- 상담원 콘솔의 대화 조회는 **PII 접근 감사(PRV-H4)** 를 남깁니다. 이력 화면에서도 원문을 열면
  **동일한 감사 기록이 필요**합니다(권한·감사 일관성).
- `sessions.channel='preview'`(관리자 미리보기) 대화가 섞이므로 **배지 구분 또는 기본 제외** 필요.

## 2. 상담원별 대화 보기

### 현행
- `conversations.agent_id` 컬럼 **존재**(수락 시 기록, `idx_conv_agent` 인덱스까지 있음).
- **`assignments` 테이블도 존재**: conversation_id, agent_id, assigned_by, type(auto/manual),
  status(active/transferred/released), assigned_at, released_at — 담당 이력을 담을 구조가 이미 있음.
- 상담원 큐 조회 `GET /agent/sessions`는 대기/진행 대화만 반환하며 **agent 필터 인자가 없습니다**.

### 갭
- 상담원 기준 필터/그룹 조회 API·화면 부재. 종료된 대화까지 포함한 "이 상담원이 처리한 대화" 목록 없음.
- **`agentId`가 큐 응답에 직렬화조차 되지 않음**(`toSessionResponse`에서 누락) — 화면이 담당자를
  표시할 방법이 없음. 웹의 `ConversationDetail.assignedTo` 필드는 **API가 채워주지 않는 유령 필드**.
- **`assignments`는 쓰기만 하고 읽는 코드가 전혀 없음**. 이관(transfer) 기능은 미구현이라
  `status='transferred'`가 기록되는 곳이 없고, `CAPABILITY.CONVERSATION_ASSIGN`은 **어떤 라우트도
  보호하지 않는 미사용 권한**입니다.

### 고려사항
- **가시성 정책(POL-019 ACL)** 과 충돌 여지: 상담원이 **타인의 대화**를 볼 수 있는지 결정 필요.
  기본안 = 마스터/디렉터는 전체, 일반 상담원은 본인 것만.

## 3. 상담원 작업로그

### 현행
- `audit_logs`(tenant_id, actor_type, actor_id, action, target, created_at, ip, request_id,
  result, metadata JSON) — 인프라 완비.
- 실제 기록 중인 action(실측): `auth.login`, `retention.purge`, `dsar.*`, `ccpa.opt_out`,
  `gdpr.*`, `campaign.dispatched`, `user.invited`, **`agent.conversation_viewed`**, …
- 상담원 행위 엔드포인트는 존재: accept / message / end / link-customer / create-customer /
  alerts ack.

### 갭
- **수락·답변·종료·고객연결·알람확인이 감사에 기록되지 않음**(조회만 기록).
- **조회 API는 있으나(`GET /audit`, `TENANT_AUDIT_READ`) 필터가 `action`/`actor_type`뿐** —
  **"상담원 X가 무엇을 했는지"를 질의할 수 없습니다**(actor_id·기간 필터 부재).
- **화면과 권한이 어긋나 있어 현재 아무도 볼 수 없습니다**: `AuditPage`는 `/admin/audit`
  (시스템 관리자 전용 라우트)에만 걸려 있는데, 관리자에게 부여된 권한은 `PLATFORM_AUDIT_READ`이고
  API가 요구하는 것은 `TENANT_AUDIT_READ` → **관리자 요청은 403**. 반대로 이 권한을 가진
  테넌트 마스터/디렉터에게는 **메뉴·라우트 자체가 없습니다**.
- `AuditPage`의 `actor` 컬럼도 API가 `actorType`/`actorId`만 반환해 항상 `—`로 표시됩니다.

### 고려사항
- 감사 로그는 보존기간 정책상 대화 로그(365일)와 **다른 수명**을 가질 수 있습니다 — 확인 필요.
- 작업로그는 인사평가로 오인될 소지가 있어 **열람 권한을 마스터/디렉터로 제한**하는 것이 안전합니다.

## 4. 고객질문 통계

### 현행
- `GET /analytics/dashboard` → `DashboardKpis`: activeChats, todayNotifications,
  aiResolutionRate, **popularQuestions**, unresolvedTopN, totalConversations, totalOrders.
- ⚠️ `popularQuestions` 실제 구현(`analytics.service.ts:107-111`)은 **최근 메시지 body를 중복
  제거해 5개 담는 것** — 빈도 집계·정규화·기간 개념이 없습니다.
- `agent_daily_stats`(handled/avg_first_response_sec/avg_handle_sec/resolved/escalated/
  csat_avg/online_sec/blocked_msgs) — **행 0건, 쓰는 코드 없음**.
- `cjm_events`(stage/event_type/payload) 존재.

### 갭
- 질문 **빈도·주제·기간별 추이·미해결(이관) 비율** 집계 전무. **어떤 분석 API에도 기간(from/to)
  파라미터가 없고**, 콘솔에는 차트·기간 선택기가 하나도 없습니다.
- 지식 활용 통계(어떤 문서가 자주 근거로 쓰였는지, 어떤 질문이 근거를 못 찾았는지) 전무.
- **의도 분류 결과가 저장되지 않습니다** — `rag.classifyIntent()`가 메시지마다 의도를 계산하지만
  `needsOrderData` 판단에만 쓰고 **버립니다**. 의도 기준 통계를 하려면 적재부터 시작해야 합니다.
- 이관 사유(`low_confidence`/`moderation_blocked`/`user_request`)는 `agent_alerts.reason`과
  `retrieval_trace`에 남지만 **집계하는 코드가 없습니다**. `unresolvedTopN`은 "미해결 질문 상위 N"이
  아니라 **단순 대기 건수**입니다(이름과 실제가 불일치).
- CSAT는 컬럼(`csat_avg`)만 있고 **수집 경로 자체가 없습니다**.
- `cjm_events`는 이벤트 원본만 나열(`GROUP BY` 없음)하고 **웹에서 호출조차 하지 않습니다**.
- ~~`messages.tenant_id` 미기록으로 인기 질문 쿼리가 항상 빈 결과~~ → **정정**: `TenantSubscriber`가
  자동 스탬프하므로 테넌트 필터는 정상 동작합니다(실측 확인). 통계 작업의 선행조건이 아닙니다.

### 고려사항 (설계 난이도의 핵심)
- **"질문 통계"의 정의부터 결정해야 합니다.** 원문 그대로 세면 표현이 달라 집계가 무의미합니다.
  선택지: ①의도 분류 라벨(`rag.classifyIntent` 결과) 기준 ②근거 문서/카테고리 기준
  ③임베딩 클러스터링 ④키워드 정규화. **②는 이미 저장된 데이터로 즉시 가능**하고 지식 개선과
  직결되어 비용 대비 효과가 가장 좋습니다(①은 의도 라벨을 로그에 남기는 작업 추가 필요).
- **retention 퍼지(365일)** 때문에 원본 기반 집계는 과거를 잃습니다 → **일/주 단위 스냅샷 테이블**
  적재가 전제. `agent_daily_stats`와 같은 패턴을 질문 통계에도 적용하는 것이 일관적입니다.
- 통계는 **개인 식별이 되지 않도록** 집계 단위를 유지해야 합니다(개인정보 최소화 원칙).

## 5. 지식 충돌 · 출처 표기 · 오래된 지식 관리

### 현행
- **출처 표기**: `POST /knowledge/ask`가 답변별 근거 문서(id·제목·카테고리·유사도·발췌)를 반환하고
  콘솔 QA 패널이 표시합니다(PR #84). **과거 답변**도 `messages.retrieval_trace.citations`로 보존.
- **문서 메타**: source(`knowledge_store`/`google_drive`), source_id, category, active, status,
  updated_at, embedding_model, embedded_at.
- Qdrant `search(tenantId, vector, limit)` 보유 → **문서 간 유사도 탐색 가능**.

### 갭
| 요구 요소 | 현행 | 필요 |
|---|---|---|
| 충돌 탐지 | 없음 | 유사도 높은 문서쌍(중복/상충 후보) 탐지 |
| 어떤 지식을 반영할지 표시 | `active`(노출/숨김) 뿐 | 상충 그룹 내 **채택본 지정**(우선순위) |
| 출처 표기 | 문서 제목 수준 | 원문 출처(문서명·URL·담당자·기준일) 필드 부재 |
| 오래된 지식 판정 | **`updated_at` 뿐** | 유효기간/검토주기/최종검토자 등 |
| 이력 | **없음**(버전·변경이력 테이블 부재, `created_at`·`updated_by`조차 없음) | 변경 이력 최소 1단계 |

**추가 확인 사항**
- 현재 존재하는 유일한 "출처 우선순위" 장치는 `knowledge_store`를 `google_drive`보다 앞세우는
  RRF 보너스(POL-013)뿐입니다. 문서 간 우열을 지정할 수단은 없습니다.
- **답변 프롬프트는 검색된 문서를 라벨 없는 한 덩어리로 합칩니다**(`- [category] title: snippet`).
  두 문서가 상충할 때 어느 쪽을 따르라는 지시가 없고, 생성된 답변에 **인라인 출처 표시도 없습니다**
  → 상충 시 AI가 어느 쪽을 썼는지 사후 판별이 어렵습니다.
- 검색 단계의 중복 제거는 **문서 id 기준**뿐이라, 내용이 모순되는 두 문서는 그대로 함께 투입됩니다.
- 콘솔 문서 목록에 **`source` 컬럼이 렌더링되지 않아** 관리자가 지식저장소/Drive 출처를 구분할 수 없습니다
  (타입 정의에는 존재).
- `status`는 임베딩 상태(`pending`/`embedded`)일 뿐 **승인·발행 워크플로가 아닙니다**.
- QA 패널(PR #84)의 소스 목록은 **유사도 순 평면 목록**입니다 — 상충 표시, 출처 유형 라벨,
  최신성 표시가 없어 "어느 쪽을 믿어야 하는지"를 화면만 보고는 알 수 없습니다.

### 고려사항
- **"충돌"은 자동 판정이 어렵습니다.** 임베딩 유사도는 *중복 후보*는 잘 찾지만 *내용이 상반되는지*는
  판별하지 못합니다(예: "무료배송 $29.99" vs "무료배송 $19.99"는 유사도가 높고 서로 모순).
  현실적 설계: **①유사도로 후보군 추림 → ②LLM으로 상충 여부 판정(수치·조건 비교) → ③사람이 채택본 결정**
  의 3단 구조. ②는 비용이 들지만 후보군에만 적용하므로 제한적입니다.
- **오래된 지식 판정 신호가 부족합니다** — 현재는 `updated_at`뿐이고 문서 생성 시점(`created_at`)도
  없습니다. 정책 문서(§KB 224건)는 원문에 시행일이 있으므로 **문서 메타에 기준일/검토주기 필드 추가**가
  실효적입니다.
- 채택본 지정은 **검색 단계에 반영되어야 실효**가 있습니다(단순 표시로는 답변이 안 바뀜):
  숨김(`active=0`) 또는 우선순위 가중치로 RAG에 반영하는 설계가 필요합니다.

## 5-1. 조사 중 발견한 기존 결함 (요구와 별개, 선행 수정 권고)

이번 요구를 구현하려면 어차피 건드리게 되는 영역에서, **지금도 잘못 동작 중인 것들**입니다.
요구사항 작업과 묶어 처리하는 편이 경제적입니다.

| # | 결함 | 영향 | 선행도 |
|---|---|---|---|
| B1 | 메시지 쓰기 경로가 `tenant_id`를 명시하지 않고 `TenantSubscriber` 자동 스탬프에 전적으로 의존 | 평시에는 정상. 단 **테넌트 2개 이상 + 세션 토큰 미해석 위젯 요청**, 그리고 **HTTP 요청 밖(이벤트 핸들러·배치)** 의 쓰기는 `tenant_id`가 null로 남음 | 낮음 — 방어 코드 + 회귀 테스트 |
| B2 | `GET /analytics/conversations/:id` 라우트 없음(웹은 호출 중) | 이력 상세 404 — 죽은 코드 | ①에서 함께 해소 |
| B3 | 이력 목록이 `customerName`·`summary`·`startedAt`을 반환하지 않음 | 3개 컬럼 항상 `—` | ①에서 함께 해소 |
| B4 | 감사 화면 권한 불일치(`/admin/audit` ↔ `TENANT_AUDIT_READ`) | **현재 감사 로그를 볼 수 있는 사용자가 없음** | ③의 **필수 선행** |
| B5 | 감사 목록 `actor` 컬럼이 항상 `—` | 누가 한 행위인지 화면에서 식별 불가 | ③에서 함께 해소 |
| B6 | `EVENTS.CONVERSATION_LOG` 구독자 없음 | 이벤트만 발행되고 아무도 처리하지 않음(사실상 미사용) | 정리 대상 |

## 6. 공통 관찰

1. **데이터는 있는데 보여줄 화면이 없는 항목이 많습니다**(①③⑤). 신규 수집보다 **노출·집계·권한**
   작업 비중이 큽니다.
2. **감사·권한 일관성**이 반복 쟁점입니다 — 대화 원문·작업로그·통계는 모두 PII 또는 인사 민감
   정보에 접근하므로, 열람 권한과 감사 기록을 한 번에 정리하는 편이 낫습니다.
3. **보존기간(365일)** 이 ①④⑤ 모두에 영향을 미칩니다. 특히 통계는 스냅샷 없이는 무의미해집니다.

## 9. 권고 진행 순서

1. **§7의 D1~D8 결정** (특히 D2·D5는 설계 방향을 좌우)
2. **B군 선행 수정(1d)** — 특히 **B4(감사 권한)는 ③의 전제조건**이라 본 작업보다 먼저 처리해야
   합니다. 나머지 B군은 ①③ 작업 중 자연스럽게 함께 해소됩니다.
3. 결정 반영해 **PLN 작성** — ①②③(로그·권한 묶음) → ④(통계) → ⑤(지식 충돌) 3단계 분할 권고.
   ①②③은 서로 권한·감사 설계를 공유하므로 한 묶음이 효율적이고, ④는 스냅샷 잡이 선행되어야 하며,
   ⑤는 독립성이 높아 마지막에 배치해도 무방합니다.
4. 단계별 PR + CI 게이트 + 스테이징 검증(기존 절차 동일).

> **범위에 대한 제안**: ⑤(지식 충돌)는 요구 중 유일하게 *새로운 판단 로직*(LLM 상충 판정)이
> 필요하고 데이터 모델 확장도 가장 큽니다. ①②③은 대부분 "있는 데이터를 보여주고 권한을 정리하는"
> 작업이라 위험이 낮습니다. 빠른 효용을 원하시면 **①②③ 먼저 → ④ → ⑤** 순서를 권합니다.
