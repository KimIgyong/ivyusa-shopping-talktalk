# PLN-260817-Widget-Header-Prefs-Cleanup

헤더 사용자명 표시 + 위젯 알림채널 설정을 콘솔로 이관하는 구현 계획.

- 작성일: 2026-08-17
- 선행: `docs/analysis/REQ-260817-Widget-Header-Prefs-Cleanup.md`
- **UI 변경 있음** → ASCII 와이어프레임 §3

## 0. 확정 전제 (REQ §확정)

| 항목 | 결정 |
|---|---|
| 로그인 시 헤더 | `{이름}님` (en `Hi, {name}`) |
| 미로그인 헤더 | **현행 유지** — 테넌트 표시명 → `알림센터` |
| 채널 설정 | **콘솔로 이관** — 테넌트가 채널×카테고리 on/off |
| 요구 2 (탭 노출 설정) | **확인 완료 · 조치 없음** (REQ 참조) |

## 1. 목표 / 비목표

**목표**
1. 로그인한 고객의 이름을 헤더에 띄운다(프레임 34).
2. 위젯에서 채널 매트릭스를 걷어내고, 같은 결정을 **테넌트 단위**로 콘솔에 만든다.
3. 이미 배포된 모바일/PWA의 **푸시 토글은 계속 동작**해야 한다.

**비목표**
- CCPA 옵트아웃 · 동의 철회 · DSAR 제거 — 정책상 불가(FR-069/POL-020). 위젯에 그대로 둔다.
- `/notifications/prefs` API 제거 — 모바일·PWA가 `push` 채널로 쓰고 있다.
- 디자인 변경 — 헤더 형태는 프레임 34 그대로.

## 2. 설계

### 2.1 헤더 (요구 1)

```ts
customerName ? t('header.greeting', { name })     // "{이름}님" / "Hi, {name}"
             : displayName || t('notificationCenter')
```
`customerName`은 이미 스토어에 있다(`session/ensure`). **새 API 없음.**

### 2.2 채널 설정 이관 (요구 3) — 2계층 판정

지금 억제 판정은 `isSuppressed()` **한 곳**이다(`notification.service.ts:191`).
여기에 테넌트 정책을 **상한(ceiling)** 으로 얹는다.

```
발송 여부 = 테넌트가 그 채널×카테고리를 허용   AND   고객이 끄지 않음
             └ 신규: 콘솔 설정                    └ 기존: notification_prefs 행
```

이 순서가 중요한 이유:
- 테넌트가 SMS를 끄면 **고객 pref와 무관하게** 안 나간다 — 상점의 정책이 이긴다.
- 테넌트가 허용한 채널 안에서는 **기존 고객 pref가 그대로 존중된다** —
  모바일/PWA가 쓰는 `push` 토글이 살아 있는 이유가 이것이다.

### 2.3 저장

| 컬럼 | 타입 | 기본 | 의미 |
|---|---|---|---|
| `tenants.notification_channels` | `json NULL` | `NULL` | `{ [category]: string[] }` — 카테고리별 허용 채널. **NULL = 미설정 = 현행 동작 그대로** |

`widget_tabs`와 같은 NULL 규약. 백필 없음 → 기존 4개 테넌트의 발송 동작이 **한 건도 바뀌지 않는다.**

## 4. 단계별 계획

### S1 — 헤더 (요구 1, 독립)
- `WidgetPanel.tsx` 헤더 분기 + i18n 키 `header.greeting` **6개 언어**
  (ko `{{name}}님` · en `Hi, {{name}}` · es `Hola, {{name}}` · vi `Chào {{name}}` · ja `{{name}}さん` · zh `{{name}} 您好`)
- `npm run i18n:check`

### S2 — 스키마 + 판정
- `sql/migration_notification_channels.sql` — `tenants.notification_channels json NULL` (객체별 멱등 가드)
- `tenant.entity.ts` — nullable 컬럼은 `type` 명시
- `packages/types` — `NotificationChannelPolicy` + `channelAllowed(policy, category, channel)` 순수 함수 **+ 단위 테스트**
- `notification.service.isSuppressed()` — 고객 pref 확인 **전에** 테넌트 상한을 먼저 본다.
  ⚠️ `isSuppressed`는 현재 `customerId`만 받는다 → `tenantId` 전달 경로 필요(`notify()`가 이미 `input.tenantId`를 안다)

### S3 — 콘솔 UI
- `/settings`에 **알림 채널** 카드 신설 (`WidgetBehaviorCard` 옆)
- 저장은 기존 `PATCH /tenants/widget-settings`가 아니라 **별도 엔드포인트**
  (`PATCH /tenants/notification-channels`) — 위젯 동작과 성격이 다르고, dirty 판정을 섞지 않는다
- 저장 성공/실패 토스트(dev-kit §4.3), `AuditService.write`
- i18n 6개 언어

### S4 — 위젯 정리
- `PreferencesPanel`에서 매트릭스 + `CHANNELS`/`CATEGORIES` 상수 + `usePrefs`/`useSetPref` 사용 제거
- **동의·CCPA·DSAR 블록은 그대로**
- `prefs.channels.*` / `prefs.categories.*` i18n 키 정리(모바일/PWA가 쓰는 키는 그 앱 번들이라 무관 — 확인 후 제거)

### S5 — 회귀
- 모바일/PWA 푸시 토글이 여전히 저장·반영되는지
- 미설정 테넌트의 발송 동작 무변화(가장 중요)
- 위젯 설정 패널의 동의 철회·옵트아웃·DSAR 정상

## 6. 마이그레이션

```sql
-- sql/migration_notification_channels.sql
ALTER TABLE `tenants` ADD COLUMN `notification_channels` json NULL AFTER `widget_tab_position`;
```
- **백필 없음** — NULL = 현행 동작.
- 롤백: 컬럼 DROP(구코드는 읽지 않음).
- 순서: 스테이징 DB 선적용 → 코드 배포. `pre-deploy-check` 사용.

## 7. 승인 요청

**PLN 승인 전 구현 착수하지 않습니다.**

특히 확인이 필요한 것:
- **SI-1** — 채널 설정을 테넌트로 올리면 고객은 "주문 알림 문자 그만 받기"를 스스로 할 수 없게 됩니다.
  마케팅은 원래 default-deny라 무관하지만, **거래성 SMS·이메일**은 영향을 받습니다.
  이대로 진행할지, 아니면 위젯에 "마케팅 수신 거부" 토글 하나만 남길지 확인 부탁드립니다.
- **§2.3** — `notification_channels`를 NULL 허용 json으로 두는 방식(백필 회피, `widget_tabs`와 동일 규약).
- **W-3** 카드의 카테고리 5종 · 채널 5종 구성이 맞는지(앱푸시 `push` 포함).
