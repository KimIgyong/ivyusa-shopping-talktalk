# REQ-260819-Widget-Theming-Embed-SDK

테넌트별 위젯 **테마/스킨 확장**과 고객사 솔루션 임베드용 **SDK** 구현 가능성 검토.

- 작성일: 2026-08-19
- 원 요구:
  1. 테넌트별 프론트엔드 챗위젯을 각 테넌트별로 **디자인도 변경 가능**하게 테마/스킨 수정 기능 구현 가능한지 검토
  2. 고객사 솔루션에 **임베드 세팅 가능하도록 SDK** 기능 구현 검토
- 전제(사용자 제시): **아메바는 샵톡 기능을 제공하고, 고객 대화와 데이터는 모두 고객사 소유
  스토리지 또는 클라우드에 저장한다.**
- 코드 기준: `origin/main` `9c3404d`

---

## 0. 결론 먼저

| 요구 | 판정 | 근거 |
|---|---|---|
| 1. 테마/스킨 확장 | **가능 — 토대는 이미 있음** | PR #308이 CSS 변수 기반을 깔았다. 남은 건 토큰 추가이지 구조 변경이 아니다 |
| 2. 임베드 SDK | **가능 — 단, 선행 조건 2개** | `embed.js`가 이미 로더 역할을 한다. **오리진 검증 부재**와 **플랫폼 하드코딩 신원 연동**을 먼저 풀어야 SDK라 부를 수 있다 |
| 3. 데이터 주권(전제) | **코드는 이미 준비됨 · 비용은 운영에 있음** | 스택이 자기완결적 compose라 고객사 클라우드에 통째로 올릴 수 있다. 문제는 N배가 되는 배포·업그레이드·마이그레이션과, **LLM 호출은 여전히 외부로 나간다**는 점 |

**가장 중요한 발견**: 4개 고객사의 요구는 실은 **두 가지 다른 제품 형태**다 —
전용 배포(ivyusa·skyliving·go2joy)와 멀티테넌트 SaaS(Cafe24 몰 다수). 지금 코드는 후자를
이미 하고 있고, 전자는 "**테넌트가 1개인 배포**"이므로 코드 변경이 거의 없다. 이 두 형태를
하나의 코드베이스로 함께 지탱할 수 있느냐가 이 검토의 실제 질문이며, **답은 가능**이다.

## 1. AS-IS

### 1.1 테마 — 어디까지 되어 있나 (PR #308, 2026-08-18 스테이징 배포)

| 축 | 현황 | 근거 |
|---|---|---|
| 브랜드 색 | 테넌트가 **색 1개** 입력 → 9단 램프 + 전경색 **산출** | `packages/types/src/common/widget-theme.ts` |
| 적용 방식 | Tailwind 토큰을 **CSS 변수**로 내림(채널 삼중값, 알파 표기 보존) | `apps/widget/src/lib/theme.ts`, `tailwind.config.js` |
| 헤더 | `white` / `brand` 선택 | `widget_theme.headerStyle` |
| 전경색 | 입력 불가 — 명도에서 산출(흰색 기준, 3:1 미만이면 잉크) | 동상 |
| 저장 | `tenants.widget_theme` JSON, **NULL = 미설정**(마이그레이션 불필요) | `tenant.entity.ts:113` |
| 문구 | `widget_copy` JSON — 표시명·환영·로그인 인사, **언어별** | `tenant.entity.ts:77` |
| 탭 | `widget_tabs`(순서·구성) + `widget_tab_position`(top/bottom) | `tenant.entity.ts:88,92` |
| 번들 | **전 테넌트 공용 1개** — 변수만 갈아끼운다 | 설계 의도 |

**확인 결과**: 산출 전경색 토큰 `text-on-primary`는 위젯 컴포넌트 **12곳에서 실제로 소비**되고
있다. 남아 있는 `text-white`(10파일)는 상태 배지·라이트박스 오버레이 등 **브랜드 배경이 아닌
표면**이라 테마 대상이 아니다 — 과거 "만든 토큰을 아무도 안 쓴다" 결함은 해소된 상태다.

### 1.2 테마가 아직 못 바꾸는 것

| 항목 | 현황 |
|---|---|
| 로고·아바타 | **없음**. 브랜드 이미지를 넣을 컬럼도, 업로드 경로도 없다 |
| 런처 버튼 | 위치·크기·아이콘이 **하드코딩**: `fixed bottom-5 right-5`, `h-14 w-14`, `MessageCircle` (`Widget.tsx:125`) |
| 패널 크기 | 로더에 하드코딩: 열림 `min(444px,100vw) × min(680px,100vh)`, 닫힘 96px (`embed.js`) |
| 서체 | 시스템 폰트 고정. 웹폰트 주입 경로 없음 |
| 모서리·간격·그림자 | Tailwind 클래스에 고정, 토큰 아님 |
| 다크 모드 | 없음 |
| 커스텀 CSS | 없음(의도적 — 임의 CSS는 업그레이드마다 깨진다) |
| 상태색 4종 | 테마에서 **의도적으로 제외**(성공/경고/오류/정보는 의미색) |

### 1.3 임베드 — `embed.js`가 이미 하고 있는 일

`apps/widget/public/embed.js` (의존성 0, 바닐라)는 이미 로더다:

- 스토어 테마와 격리된 **iframe 주입** + `sandbox` 속성 최소 권한
- **postMessage 프로토콜**: `ivy:ready` / `ivy:resize` / `ivy:session` / `ivy:identity` /
  `ivy:login` / `ivy:login-cancelled` / `ivy:cafe24-ticket`
- **로그인 중개**: redirect·popup 2모드, 복귀 후 위젯 자동 재오픈(1회용 플래그)
- **플랫폼 자동 감지**: Shopify(App Proxy `/apps/ivy/identity`) / Cafe24(`*.cafe24.com` 호스트 →
  customer-auth 티켓 교환)
- **유입 출처 캡처**: UTM 5종 + referrer + landing을 iframe src로 전달
- GA4 측정 ID 전달, 멱등 마운트

즉 **"SDK가 없다"가 아니라 "로더는 있는데 공개 API·범용 신원·오리진 검증이 없다"**가 정확한 현황이다.

### 1.4 임베드가 아직 못 하는 것

| # | 갭 | 왜 문제인가 |
|---|---|---|
| G-1 | **오리진 검증 없음** | `session/ensure`는 `shop_domain` 문자열만으로 테넌트를 해석한다(`session.service.ts:92-97`). 도메인 값만 알면 **아무 사이트에서나 남의 테넌트 위젯을 띄우고 세션을 열 수 있다.** 고객사가 4곳일 땐 드러나지 않지만 SDK로 배포 대상이 늘면 정면으로 문제가 된다 |
| G-2 | **신원 연동이 플랫폼 하드코딩** | Shopify App Proxy와 Cafe24 티켓 **두 경로뿐**이다. skyliving(Odoo)·go2joy(자체 시스템)는 **로그인한 고객을 위젯에 알려줄 방법이 아예 없다** |
| G-3 | 공개 JS API 없음 | 호스트 페이지가 위젯을 열고/닫고/사용자를 알려주고/이벤트를 받을 수단이 없다. go2joy 웹처럼 자체 UI에서 "문의하기"를 누르는 흐름을 만들 수 없다 |
| G-4 | **API 주소가 빌드타임에 굳는다** | `VITE_API_BASE_URL`이 번들에 인라인된다(`api-client.ts:4`). 고객사마다 **별도 빌드**가 필요하다 |
| G-5 | 모바일 없음 | `apps/mobile`은 아메바가 만든 **자체 앱**이지, go2joy 앱에 넣을 SDK가 아니다 |
| G-6 | 버전·배포 정책 없음 | `embed.js`는 위젯 오리진에서 그대로 서빙된다. 버전 고정·캐시·롤백 전략이 없다 |
| G-7 | 설정 전달이 전역 변수 | `window.IVY_WIDGET_CONFIG` 하나. `data-*` 속성도, npm 패키지도, 타입 정의도 없다 |

### 1.5 배포 — 현재는 단일 배포 · 멀티테넌트

| 축 | 현황 |
|---|---|
| 배포 단위 | compose 1벌: **api · web · mysql · redis · rabbitmq · qdrant · nginx** (+ staging은 widget·pwa) |
| 상태 저장 | 명명 볼륨 4개 + **업로드 볼륨**(`UPLOAD_DIR=/data/uploads`, 첨부 파일) |
| 테넌트 격리 | 애플리케이션 레벨 `tenant_id` — **한 DB에 4개 고객사가 함께** 있다 |
| 스키마 변경 | 스테이징 `DB_SYNCHRONIZE=false` → **수동 SQL 선적용**이 원칙 |
| 배포 방법 | 서버에서 `git pull && deploy-staging.sh` — **수동** |
| 외부 의존 | Anthropic/OpenAI(LLM), Voyage(임베딩), Shopify·Cafe24 API, GA4, Web Push |

## 4. 갭 분석

### 4.1 요구 1 — 난이도 낮음, 구조 변경 없음

PR #308이 깐 CSS 변수 기반이 **정확히 이 확장을 위한 토대**다. 색 토큰이 이미 변수로
내려가 있으므로 반경·간격·치수도 같은 방식으로 추가하면 된다.

| 항목 | 작업 |
|---|---|
| 저장 | `widget_theme` JSON 확장 — **컬럼 추가 불필요**(NULL 폴백 규약 그대로) |
| 이미지 | 저장·서명URL·썸네일 **기계는 재사용 가능**하나, `message_attachments`는 대화·메시지에 묶여 있다 — 대화에 속하지 않는 **테넌트 자산** 경로가 새로 필요하다 |
| 런처/패널 | 하드코딩된 3곳(`Widget.tsx`, `embed.js` CLOSED/OPEN)을 변수화 — **로더가 테마를 알아야 한다**(현재는 모름) |
| 미리보기 | 콘솔에 위젯을 iframe으로 띄우고 테마만 주입 |

**주의 지점 하나**: 런처 크기·위치는 **iframe 바깥**(로더)에 있다. 지금 로더는 테마를 전혀
모르므로, 테마를 로더까지 전달하는 경로(부트스트랩 응답 또는 `init()` 설정)가 새로 필요하다.
이것이 요구 1과 요구 2가 만나는 지점이다.

### 4.2 요구 2 — 난이도 중, 그러나 **선행 2건이 진짜 작업**

| 갭 | 해소 방향 | 크기 |
|---|---|---|
| G-1 오리진 검증 | 테넌트별 허용목록(구현은 `tenants.embed_origins` **JSON 컬럼** — 조회가 항상 '테넌트 확정 후 대조'라 테이블·인덱스가 불필요) + `session/ensure`에서 대조. **위반은 로그로 남긴다**(4xx는 기본 미로깅) | S |
| G-2 범용 신원 | 테넌트별 시크릿 발급 → 고객사 서버가 `user_hash` 생성 → SDK `identify()` → 서버 검증 후 고객 바인딩. Shopify/Cafe24 기존 경로는 **그대로 둔다**(회귀 금지) | M |
| G-3 공개 API | 로더에 `window.ShopTalk` 네임스페이스 + 이벤트 버스. postMessage 프로토콜은 이미 있으므로 **표면만 씌우면 된다** | S |
| G-4 런타임 설정 | `api-client.ts`의 빌드타임 상수를 부트스트랩 주입으로 교체 | S |
| G-5 모바일 | WebView 래퍼 + 서명 신원. 네이티브 UI 재구현은 비범위 | M |
| G-6 버전 | 경로 버저닝 + 캐시 헤더 | S |
| G-7 배포 형태 | npm 패키지 + `.d.ts` | S |

### 4.3 전제 — 코드가 아니라 **운영**이 비용이다

좋은 소식: 스택이 이미 자기완결적이고 테넌트 스코프가 코드 전반에 적용돼 있어,
**"테넌트 1개짜리 배포"는 새 아키텍처가 아니라 현재 아키텍처의 특수한 경우**다.

나쁜 소식 4가지:

1. **운영이 N배가 된다.** 지금도 배포는 서버에서 수동이고, 스키마 변경은 **수동 SQL 선적용**이
   원칙이다. 인스턴스가 4개(이후 더)가 되면 자동화 없이는 유지 불가능하다.
2. **LLM 호출은 고객사 클라우드를 벗어난다.** 인프라를 고객사로 옮겨도 **대화 본문은
   Anthropic·Voyage로 전송된다.** "데이터는 모두 고객사 소유 스토리지에 저장한다"는 전제와
   충돌할 수 있는 지점이며, **저장(storage)과 처리(processing)를 구분해 명문화**해야 한다.
3. **Cafe24 몰에는 '고객사 클라우드'가 없다.** amoebaorder처럼 몰들에 제공하는 형태에서는
   전용 배포가 성립하지 않는다 → **§6 Q-2 결정 필요**.
4. **스테이트풀 4종은 소형 고객에 과하다.** MySQL·Redis·RabbitMQ·Qdrant를 몰 하나마다 세우는
   것은 비용·운영 모두 부담이다.

## 5. 사용자 흐름 (TO-BE)

**흐름 A — 고객사 개발자가 위젯을 붙인다(go2joy 웹)**
1. 콘솔 → 설치 안내에서 스니펫 복사(테넌트 키 포함) 및 임베드 허용 도메인 등록
2. 자체 페이지에 스크립트 추가 → `ShopTalk.init({ key, apiBase })`
3. 로그인 사용자에 대해 서버가 `user_hash` 생성 → `ShopTalk.identify({ userId, name, email, hash })`
4. 자체 "문의하기" 버튼에서 `ShopTalk.open('chat')`
5. 콘솔 설치 진단에서 "설치됨 · 신원 서명 정상" 확인

**흐름 B — 브랜드 담당자가 디자인을 바꾼다**
1. 콘솔 → 위젯 테마: 브랜드 색·헤더·로고 업로드·런처 위치/아이콘·모서리 선택
2. 오른쪽 미리보기가 **저장 전에** 즉시 반영
3. 저장 → 다음 위젯 로드부터 적용(캐시된 테마는 첫 페인트 전에 덮인다)

**흐름 C — 고객사 인프라에 배포한다(ivyusa AWS)**
1. 고객사 AWS에 compose 스택 기동, `talk.ivyusa.com` TLS 종단
2. 스키마 SQL 선적용 → 컨테이너 기동 → 부팅 로그·라우트 상태코드 확인
3. `www.ivyusa.com`에 스니펫 설치, 허용 도메인 등록
4. 대화·첨부·백업이 전부 고객사 계정 안에 남는지 확인

## 7. 배포 모델 3안 (Q-1)

| 안 | 형태 | 장점 | 비용 |
|---|---|---|---|
| **A. 전면 전용 배포** | 고객사마다 스택 1벌 | 데이터 주권 완전 충족, 격리 확실 | 운영 N배, 소형 고객 수용 불가 |
| **B. 전면 SaaS(현행 유지)** | 아메바 운영 멀티테넌트 | 운영 단순, 지금 그대로 | **전제 위배** — ivyusa AWS 요구를 못 맞춘다 |
| **C. 혼합(권고)** | 대형·규제 고객은 전용 배포, 소형 몰은 리전별 아메바 운영 SaaS | 4사 요구를 **있는 그대로** 수용, 코드 1벌 유지 | 배포 자동화와 버전 관리가 필수 전제 |

**결정: C** (2026-08-19). 근거는 두 가지다 — (1) ivyusa·skyliving·go2joy는 인프라가 이미 정해져 있고,
(2) amoebaorder는 몰 다수 대상이라 전용 배포가 성립하지 않는다. 코드는 이미 두 형태를 모두
지탱할 수 있으므로, 새로 만들 것은 **아키텍처가 아니라 배포·업그레이드 자동화**다.
