## 1. AS-IS

### 1.1 HEIC는 4중 게이트 전부에서 막힌다

첨부 파이프라인 자체는 완성돼 있고, HEIC만 **정책상 목록에 없어서** 거절된다.

| 게이트 | 현황 | 근거 |
|---|---|---|
| 위젯 파일 선택창 | `accept=".jpg,.jpeg,.png,.gif,.webp,.pdf,.txt,.csv,.docx,.xlsx"` — `.heic` 없음 | `apps/widget/src/components/chat/ChatTab.tsx:553` |
| 위젯 클라이언트 검증 | `IMAGE_EXT = ['jpg','jpeg','png','gif','webp']` → 업로드 시도 **전에** `chat.attachment.typeNotAllowed` 토스트 | `apps/widget/src/hooks/useAttachmentUpload.ts:10,42` |
| 콘솔(상담원) | 동일한 목록·동일한 `accept` | `apps/web/src/domain/live-chat/useAgentUpload.ts:9`, `LiveChatPage.tsx:650` |
| 서버 타입 정책 | `SPECS`에 heic/heif 스펙 없음 → `resolveType()` = null → **E5036 400** | `apps/api/src/domain/attachment/file-type.util.ts` (SPECS), `attachment.service.ts` `store()` |
| 외부 메신저 인바운드 | `store()`가 던진 예외를 삼키고 `inbound attachment dropped` **warn 한 줄** — 고객·상담원 누구에게도 표시 없음 | `messenger-ingest.service.ts:237,254` |

마지막 줄이 이번 요구의 실질적 위험이다. 위젯 경로는 최소한 고객에게 "이 형식은 안 됩니다"라고
말하지만, **Gmail·텔레그램(문서 전송)·허브로 들어온 HEIC는 조용히 사라진다** — 고객은 사진을
보냈다고 믿고 상담원 화면엔 아무것도 없는, PLN-260814가 없애려던 바로 그 실패 형태다.

### 1.2 "확장자만 열어주면 된다"가 아닌 이유 — 디코더가 없다 (실측)

스테이징 API 컨테이너에서 직접 확인(2026-08-17):

| 항목 | 실측값 |
|---|---|
| 런타임 | `node:20-alpine` / Alpine **3.23.4** / x86_64 (musl) |
| sharp | **0.33.5**, 내장 libvips **8.15.3** (`@img/sharp-libvips-linuxmusl-x64`) |
| `sharp.format.heif.input.fileSuffix` | **`['.avif']`** — HEIF 컨테이너 중 **AVIF만** 입력 가능 |
| libvips-cpp.so.42 심볼 | AOM(AV1) 인코더/디코더만 존재. **`de265` 심볼 0건** |

즉 sharp의 prebuilt libheif는 **AV1 코덱만** 물고 있고, 아이폰이 만드는 **HEVC 코딩 HEIC는
디코드할 수 없다**(sharp 공식 정책 — HEVC는 특허 문제로 prebuilt에서 제외).

여기서 파생되는 결과가 셋이다.

1. **미리보기가 안 된다.** `processImage()`는 디코드 실패를 `logger.warn` 후 삼키고 "원본 저장,
   썸네일 없음"으로 넘어간다(`attachment.service.ts` processImage 예외 처리). 확장자만 허용하면
   업로드는 성공하는데 콘솔에는 썸네일이 없는 상태가 된다.
2. **브라우저가 대신 그려주지도 않는다.** HEIC를 네이티브 렌더하는 건 Safari 계열뿐이고,
   상담원 콘솔이 실제로 도는 Chrome/Edge/Firefox는 못 그린다 → 현재 UI에서는 `onError` 폴백인
   "이미지 없음" 자리표시로 떨어진다(`MessageAttachments.tsx` broken 상태).
3. **EXIF가 남는다.** 지금 EXIF(GPS·기기·시각) 제거는 별도 스크러버가 아니라 **재인코딩의
   부산물**이다(PLN-260814 SI-10). 디코드가 안 되면 재인코딩도 없고, **촬영 위치가 박힌 원본이
   그대로 저장·서빙된다** — 기능 결함이 아니라 프라이버시 회귀다.

> 결론: 이 요구는 "화이트리스트에 heic 추가"가 아니라 **서버 측 디코드·변환 경로 추가**다.

### 1.3 얼마나 자주 발생하는지 — 지금은 셀 수 없다

| 축 | 현황 |
|---|---|
| 위젯 거절 | 클라이언트에서 먼저 막으므로 **서버에 흔적이 남지 않는다** |
| 서버 거절(E5036) | 4xx는 기본적으로 서버 로그에 남지 않는다(CLAUDE.md §2 주의) |
| 인바운드 드롭 | `inbound attachment dropped` warn만 — 스테이징 로그 실측 **0건**(실트래픽 부재) |
| 프로덕션 | 미배포 상태라 관측 데이터 자체가 없다 |

iOS는 카메라 설정이 '고효율'이면 HEIF/HEVC로 촬영하고(기본값), '높은 호환성'이면 JPEG다.
다만 **Safari가 사진 라이브러리에서 업로드할 때는 JPEG로 변환해 주는 경로가 있어서**, 실제
실패는 파일 앱 경유·인앱 브라우저·타 브라우저·메일 첨부 등 **일부 경로에 몰릴 가능성**이 크다.
"얼마나 아픈가"를 추정으로 결정하지 않기 위해 **경로별 실측**(§6 T-1)과 **거절 계측**(FR-6)을
요구에 포함한다.

## 3. 갭 분석

### 3.1 구현 후보 비교

| 안 | 방식 | 장점 | 비용·위험 |
|---|---|---|---|
| **A. WASM 디코더** | `libheif-js`(1.19.8, 의존성 0) 또는 `heic-decode`/`heic-convert`로 RGBA 디코드 → 기존 sharp로 JPEG/webp 재인코딩 | **Docker 이미지·배포 파이프라인 무변경**, npm 의존만 추가, 알파인/musl 무관, 롤백은 화이트리스트 되돌리기 | 순수 WASM이라 느리다(12MP 기준 수백 ms~수 초), 디코드 중 메모리(12MP RGBA ≈ 48MB), 이벤트 루프 블로킹 대책 필요 |
| **B. 시스템 libvips** | Alpine 3.23 `vips-heif`(8.17.3) + `libde265`(1.0.16) 설치 후 sharp를 글로벌 libvips에 링크 | 네이티브 속도, 코드 변경 최소 | Dockerfile 2개(staging/prod) 변경, sharp 0.33.5(빌드 기준 libvips 8.15.3) ↔ 시스템 8.17.3 **ABI/버전 정합 미검증**, 실패 시 sharp가 통째로 죽으면 썸네일 전체가 사라짐(현재는 lazy-load fail-open), 이미지 크기 증가 |
| **C. 클라이언트 변환** | 위젯/콘솔에서 `heic2any` 등으로 업로드 전 변환 | 서버 무변경 | 위젯 번들 +1MB급(위젯은 스토어프론트 임베드), **인바운드 채널을 전혀 해결 못 함** → 부분해 |
| **D. 수용만, 미리보기 없음** | 다운로드 전용 파일로 취급 | 최소 변경 | 요구(미리보기) 미충족 + EXIF 잔존(§1.2-3) → **채택 불가** |

**권고: A로 PLN 진행**, 성능 실측이 목표치를 못 맞출 때만 B로 승격.
근거는 두 가지다 — (1) 이 기능의 트래픽은 "상담 중 사진 몇 장"이지 배치 변환이 아니다,
(2) B는 배포·이미지 리스크를 상시로 떠안는 반면 A의 위험은 요청 하나에 국한된다(적정기술 원칙).

### 3.2 손대야 하는 지점

| 축 | 현재 | 필요 |
|---|---|---|
| 서버 타입 정책 | `SPECS`에 heic 없음 | heic/heif 스펙 추가 + **magic byte 판별**: offset 4의 `ftyp` + brand(`heic/heix/hevc/hevx/heim/heis/mif1/msf1`). 현재 sniff 유틸(`startsWith`/`ascii`)로 표현 가능 |
| 저장 형식 일관성 | `store()`가 `{uuid}.{입력ext}`로 저장하고 `mime`도 입력 기준 | 변환 후에는 **저장 ext/mime이 입력과 달라진다**(heic → jpg). `storagePath`·`mime`·`size`·`checksum`이 변환 결과 기준이 되도록 정리 필요(표시용 `filename`은 원본 유지 여부 = Q2) |

| i18n | `attachment.*` 키 존재 | 변환 실패/미지원 문구 en·es·ko × (widget locales, web `livechat.json`) |
| 인바운드 | 실패를 warn으로 삼킴 | FR-5 자리표시 메시지 |

| 문서 | 사용자 매뉴얼의 첨부 항목 | 지원 형식 목록 갱신 |

## 4. 사용자 흐름 (TO-BE)

**흐름 1 — 아이폰 고객이 위젯에서 사진 첨부**
1. 첨부 버튼 → 사진 선택(파일 앱 경유라 `IMG_0001.HEIC` 원본이 올라옴)
2. 클라이언트: `.heic` 허용 → 업로드 진행바 (변환은 서버가 하므로 위젯 번들 변화 없음)
3. 서버: ftyp brand 확인 → HEIC 디코드 → JPEG 재인코딩(EXIF 제거·회전 보정) → 320px webp 썸네일
4. 위젯 말풍선에 즉시 썸네일, 탭하면 확대 — JPEG를 보고 있으므로 안드로이드·PC에서도 동일
5. 콘솔 대화방에 썸네일 → 클릭 시 라이트박스(기존 경로 그대로)

**흐름 2 — Gmail/텔레그램으로 들어온 HEIC**
1. 인바운드 어댑터가 첨부 다운로드 → `store()` → 흐름 1의 3단계와 동일 변환
2. 상담원 화면에 사진이 뜬다 (지금은 아무것도 안 뜬다)

**흐름 3 — 디코드 실패(손상 파일·미지원 코덱)**
1. 위젯: "이 사진은 처리할 수 없습니다. JPEG로 다시 보내주세요" 오류 토스트(재시도 가능)
2. 인바운드: 대화에 자리표시 메시지 + 서버 warn 계측 → 상담원이 고객에게 재요청할 수 있음
3. 어느 경우에도 **EXIF가 남은 원본이 그대로 저장되지 않는다**

## 5. 제약 · 정책

| ID | 제약 |
|---|---|
| C-1 | **런타임 고정**: alpine musl / x86_64 / sharp 0.33.5(libvips 8.15.3 내장, HEVC 디코더 없음) — §1.2 실측 |
| C-2 | **HEVC 특허**: HEIC 디코딩은 HEVC 특허 풀 대상 기술이다. libde265/libheif는 오픈소스지만 상용 서비스에서의 라이선스 노출은 별도 판단 사항 — **디코드 전용(인코드 없음)**임을 전제로 진행하고, 프로덕션 전 법무 확인 항목으로 남긴다 |
| C-3 | **성능**: 변환은 요청 경로 안에서 일어난다. 이벤트 루프 블로킹을 피할 방법(worker_threads / 큐 / 동시 실행 제한)을 PLN에서 정한다 |
| C-4 | **메모리**: 디코드 결과는 압축이 풀린 픽셀 버퍼다. 12MP ≈ 48MB, 5장 동시 = 240MB → FR-7 상한이 없으면 API 컨테이너가 OOM으로 죽는다 |
| C-5 | **업로드 상한**: nginx `client_max_body_size 25m`, 이미지 10MB(`ATTACHMENT_MAX_IMAGE_MB`) 유지 |
| C-6 | **저장 원칙 유지**: "저장된 원본 = 재인코딩본"(PLN-260814 SI-10)을 HEIC에도 동일 적용 |
| C-7 | **배포**: 스키마 변경이 생기면 SQL을 대상 DB에 **먼저** 적용(kit 04 §3, `DB_SYNCHRONIZE=false`). 배포 확인은 exit code가 아니라 부팅 로그·컨테이너 나이·라우트 상태코드로 |
| C-8 | **롤백 가능성**: 화이트리스트 되돌리기만으로 기능이 꺼져야 한다(안 A가 이 조건을 만족) |
