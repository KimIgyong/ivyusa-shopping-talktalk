# FIX-260903 — 일괄등록: 공백 낀 제목이 재업로드마다 중복 문서 생성

- 발견: PLN-260903 스테이징 스모크 (PR #465 배포 직후, counsel 240행 라운드트립에서
  `created=1` 발생 — 기대는 전행 skip)
- 심각도: 중간 (데이터 중복 생성, 라운드트립 계약 위반)

## 근본 원인
`bulk-import.service.ts`의 제목 업서트 맵이 **저장된 제목 원문**을 키로 썼다:
`byTitle = new Map(existing.map(d => [d.title, d]))`. 반면 업로드 행은 CSV/XLSX 파서가
셀 단위 `trim()`을 적용한다. 스테이징 ivyusa에 제목이 `"아시아 배송 "`(트레일링 공백,
id 2345)인 문서가 있었고, export는 원문을 그대로 내보내지만 재업로드 행은
`"아시아 배송"`으로 트림되어 맵 미스 → **자기 자신의 행을 못 찾고 새 문서(id 2672)를
생성**했다. 재업로드할 때마다 반복될 구조.

MySQL로는 안 보이는 함정: utf8mb4 PAD SPACE 콜레이션에서는 `'아시아 배송 ' = '아시아 배송'`
이 참이라 `title != TRIM(title)` 같은 점검 쿼리도 이 행을 잡지 못한다(진단은
`LENGTH(title) != LENGTH(TRIM(title))`로 해야 함).

## 수정 (최소 변경)
- `byTitle` 키를 양쪽 모두 트림 기준으로: `d.title.trim()` (생성 후 `byTitle.set`도 동일).
- 결과: 패딩 제목 문서는 자기 행과 매칭되어 **1회성 제목 정규화 update**로 수렴하고,
  이후 라운드트립은 전행 skip.
- 회귀 테스트 추가: 패딩 제목 기존 문서 + 트림 행 → `created=0, updated=1`.

## 스테이징 정리
- 오생성 중복 id 2672 → `DELETE /knowledge/documents/2672` (벡터 정리 포함 API 삭제).
- 원본 id 2345는 수정 배포 후 재업로드에서 제목이 정규화됨.
- 같은 스모크의 `updated=1`(id 2099)은 내용 공백/개행 정규화 1회성 update로 정상 동작.

## 예방 패턴
- **업서트 키는 정규화 함수를 한 곳에 두고 양쪽(기존 데이터·입력 행)에 동일 적용**한다.
  한쪽만 정규화하면 "자기 자신을 못 찾는" 중복이 생기고, 성공 카운터(created)에 섞여
  들키지 않는다. 라운드트립 검증(전행 skip 기대)이 이런 결함을 유일하게 드러낸다.
- MySQL 문자열 비교는 PAD SPACE 때문에 트레일링 공백을 숨긴다 — 진단은 LENGTH로.
