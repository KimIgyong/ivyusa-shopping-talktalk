# Claude 메모리 운영 가이드

> **버전**: 1.0 (2026-07-30)
> AMA 프로젝트에서 60+ 메모리 파일로 운영 검증된 방식. 세션 간 작업 연속성과 함정 재발 방지의 핵심 장치다.

---

## 1. 왜 메모리인가

Claude Code 세션은 컨텍스트가 초기화된다. 메모리가 없으면:
- 같은 함정(배포 검증, heredoc, TypeORM 타입 등)을 세션마다 다시 밟는다.
- "이미 구현·머지되어 배포만 남은 기능"을 재구현하는 사고가 난다 (AMA 실사례 — 메모리에 "재구현 금지, 배포만" 명시로 방지).
- 배포 상태(어디까지 나갔는지, 마이그레이션 적용 여부)를 매번 재조사한다.

## 2. 파일 구조

```
{memory-root}/
├── MEMORY.md                 # 인덱스 — 세션마다 로드됨. 한 줄/메모리, 내용 금지
├── project_*.md              # 진행 중/완료 작업 현황
├── debug_*.md                # 디버깅 함정
├── deploy_*.md               # 배포/운영 함정
├── incident_*.md             # 장애 기록
├── feedback_*.md             # 사용자가 확정한 작업 방식/규칙
└── manual_*.md               # 매뉴얼 정본 위치 포인터
```

### 메모리 파일 형식

```markdown
---
name: <kebab-case-slug>
description: <한 줄 요약 — 회상(recall) 판단에 사용됨>
metadata:
  type: user | feedback | project | reference
---

<사실 본문. feedback/project는 **Why:** 와 **How to apply:** 를 포함>
관련 메모리는 [[다른-메모리-name]] 으로 링크.
```

### MEMORY.md 인덱스 규칙
- `- [제목](파일명.md) — 훅(핵심 요약)` 한 줄씩. **메모리 내용을 인덱스에 넣지 않는다.**
- 인덱스 한 줄만 보고 "이 메모리를 열어야 하는가"를 판단할 수 있게 훅을 구체적으로: 결론·상태·핵심 키워드 포함.
  - 나쁨: `웹메일 작업 기록`
  - 좋음: `IMAP 폴더 하드코딩 Sent/Trash→실서버 불일치로 동기화 실패 19000회→special-use 해석으로 수정, 배포완료(2026-07-22)`

## 3. 무엇을 저장하는가 (AMA 검증 기준)

| 타입 | 저장 대상 | 예시 |
|------|----------|------|
| `project` | 작업 현황: 무엇이 어디까지 갔는가 — **PR 번호, 커밋 SHA, 배포 상태(스테이징/프로덕션), 마이그레이션 적용 여부, 미완료 항목** | "REQ-260729. #715→main cfb350b3, #716→prod b3cd3c01, 마이그 3환경 선적용, 수동 UI 시나리오 미실시" |
| `feedback` | 사용자가 확정한 규칙·작업 방식 (why 포함) | "모든 저장 후 완료 모달 필수 — 조용한 성공 처리 금지 (REQ-260713 사용자 확정)" |
| `debug`/`deploy`/`incident` (project 또는 feedback 타입) | 함정·장애: 증상 → 원인 → 재발 방지 | "heredoc은 docker exec -i 필수, 없으면 조용히 무실행" |
| `reference` | 외부 리소스 포인터 | 매뉴얼 정본 경로, 대시보드 URL |

**저장하지 않는 것**: 코드 구조·git 이력 등 레포에서 파생 가능한 사실, 이번 대화에만 유효한 내용.

## 4. 작성 규칙 (AMA 운영에서 확립)

1. **상대 날짜 금지** — "어제"가 아니라 "2026-07-29". 세션이 언제 열릴지 모른다.
2. **배포 상태는 명시적으로** — "배포완료(날짜, PR#, 커밋SHA, 검증 방법)"까지. "머지됨"과 "배포됨"은 다르다(AMA에서 머지≠배포 혼동이 재구현 사고로 이어짐).
3. **미완료 항목을 남긴다** — "수동 UI 시나리오 미실시", "Phase2 미착수" 등. 다음 세션의 시작점.
4. **틀린 메모리는 즉시 정정** — 상태가 바뀌면 "⚠️정정(날짜): ... 위 내용은 무효" 방식으로 갱신하거나 삭제. AMA는 프로덕션 메일엔진 전환 후 옛 기술이 남아 정정 주석으로 해소.
5. **중복 생성 금지** — 저장 전 기존 파일 확인, 있으면 그 파일을 갱신.
6. **링크로 그물 만들기** — 관련 함정끼리 `[[...]]` 연결 (배포 검증 ↔ 헬스체크 false-negative ↔ 마이그레이션).
7. **함정은 일반화 시점에 표준으로 승격** — 2회 이상 재발하거나 프로젝트 무관하게 유효하면 dev-kit 표준 문서(01~05)에 반영하고 메모리는 사례 포인터로 유지.
