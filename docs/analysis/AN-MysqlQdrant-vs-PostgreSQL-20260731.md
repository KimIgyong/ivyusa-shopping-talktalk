# AN — MySQL+Qdrant vs PostgreSQL 비교 검토 (다국어 KO/EN/ES 전제)

- 작성일: 2026-07-31
- 선행 문서: `AN-VectorDB-Selection-20260731.md`, `AN-PostgreSQL-Migration-Tradeoffs-20260731.md`
- 요구사항: 두 아키텍처 비교. **MySQL+Qdrant로 얻을 수 있는 부분 집중 검토**. 한국어/영어/스페인어 지원 필수.

---

## 1. 비교 대상 정의

| | A안: MySQL 8 유지 + Qdrant 추가 | B안: PostgreSQL(+pgvector) 전환 |
|---|---|---|
| 원문·트랜잭션 | MySQL (현행 그대로) | PostgreSQL (전량 이관) |
| 키워드 검색 | MySQL FULLTEXT ngram (현행) | pg tsvector(EN/ES) + pg_trgm/pg_bigm(KO) |
| 벡터 검색 | Qdrant (HNSW, payload 필터) | pgvector (HNSW) |
| 하이브리드 병합 | 앱 RRF(또는 Qdrant 내부 dense+sparse) | SQL 내 병합 |

## 2. MySQL+Qdrant로 얻는 것 (집중 검토)

### 2.1 무전환 — 회귀 리스크 0
- 기존 40개 엔티티·전 도메인 코드·스테이징 데이터·백업 절차를 **한 줄도 건드리지 않는다**.
  자동화 테스트 0건인 현 상태에서 이것이 가장 큰 실익 — B안의 최대 비용(전량 수동 회귀 검증)을
  통째로 회피한다.
- 다운타임 없음: Qdrant는 신규 컨테이너 1개 추가이며 기존 서비스 경로에 영향이 없다.

### 2.2 한국어 검색 자산 유지 — 다국어 요구의 핵심 우위
- MySQL ngram FULLTEXT는 **한국어를 무설정으로 지원**하며 이미 동작 중이다. B안은 이 부분이
  다운그레이드(pg_trgm/pg_bigm/mecab 중 택일 + 품질 재검증)라서, **KO 지원 필수라는 요구가
  A안의 손을 들어준다**.
- EN/ES도 ngram으로 검색 가능(라틴 문자에서 어간 추출은 없지만, 이 갭은 벡터 레그가 흡수 — §4).

### 2.3 검색 실패가 서비스 실패가 되지 않는 구조 (역할 분리)
- **MySQL = 소스 오브 트루스**(원문·트랜잭션·백업), **Qdrant = 파생 검색 인덱스**.
- Qdrant 데이터는 언제든 MySQL에서 재색인으로 복원 가능 → 벡터 저장소의 백업·HA 요건이 낮아지고,
  Qdrant 장애 시 FULLTEXT 폴백으로 챗봇이 계속 동작한다(현행 `retrieveLike` 폴백 패턴의 연장).
- **가역성**: 도입이 기대에 못 미치면 Qdrant 컨테이너를 제거하면 끝. B안(DB 전환)은 사실상 비가역.

### 2.4 벡터 전용 엔진의 기능 우위 (pgvector 대비)
| 기능 | Qdrant | pgvector | ShopTalk 관점 의미 |
|---|---|---|---|
| 필터-인식 HNSW | **지원** — `tenant_id` 필터를 그래프 탐색에 통합 | 필터는 post/pre-filter 성격, 선택도 높은 필터에서 recall/성능 저하 가능 | 모든 질의가 tenant 필터 동반 — 멀티테넌트 SaaS에 직접적 이점 |
| 네임드/멀티 벡터 | **지원** — 한 포인트에 여러 벡터(예: 언어별·모델별) | 컬럼 추가로 우회 | 임베딩 모델 교체/AB 테스트, 언어별 벡터 실험 용이 |
| dense+sparse 하이브리드 | **엔진 내장** (Query API RRF 융합) | SQL로 직접 조립 | 장기적으로 키워드 레그까지 Qdrant로 통합 가능한 경로 |
| 양자화(int8/binary) | 내장 — 메모리 1/4~1/32 | 미지원(halfvec 정도) | 상품 지식 확장 시 단일 서버 메모리 절약 |
| 스냅샷/컬렉션 관리 | 내장 API | pg 백업에 포함 | 재색인·롤백 운영 단순 |
| 관리형 이전 경로 | Qdrant Cloud | 관리형 PG 선택지 다수 | 동급 |
- 벡터 검색 성능 자체도 전용 엔진이 유리하지만, **현 규모에서 체감 차이는 필터-인식 인덱스와
  운영 기능에서 난다**.

### 2.5 조직·일정 관점
- 당면 목표(정책 KB 등록 → AI 답변 품질)와 병행 가능: Qdrant 도입은 KB 파이프라인에 국한된
  증분 작업(어댑터 `embed()` + 동기화 + 검색 경로)이라 **다른 도메인 개발을 멈추지 않는다**.
- 팀의 MySQL 운영 경험 유지 — 새로 배우는 것은 Qdrant API 하나로 한정.

## 3. PostgreSQL이 앞서는 부분 (공정 비교)

1. **RLS(Row-Level Security)** — 테넌트 격리를 DB 정책으로 강제. A안에서는 앱 레벨 가드로 보완해야
   함(§6). *B안의 가장 실질적인 고유 가치.*
2. **단일 저장소 정합성** — 원문과 벡터가 한 트랜잭션. A안은 MySQL↔Qdrant 동기화 지연/유실
   가능성이 존재(§6에서 완화책).
3. **EN/ES 형태소 검색** — tsvector의 english/spanish 스테머(활용형 매칭: "shipped"→"ship",
   "envíos"→"envío")는 ngram에 없는 기능. 단, 이 갭은 다국어 임베딩이 대부분 흡수한다(§4).
4. 운영 대상 DB가 1종(단, RabbitMQ·Redis는 어차피 존재하므로 "단일 인프라"는 아님).

## 4. 다국어(KO/EN/ES) 관점 상세 비교

핵심 통찰: **다국어 검색 품질은 DB가 아니라 임베딩 레이어에서 결정된다.**
Voyage `voyage-4` 같은 다국어 임베딩은 KO/EN/ES 질의·문서를 같은 벡터 공간에 놓으므로
(교차언어 검색), 벡터 레그는 **A안·B안 모두 동일 품질**이다. 차이는 키워드 레그에만 남는다.

| 언어 × 레그 | A안 (MySQL ngram + Qdrant) | B안 (PG + pgvector) |
|---|---|---|
| KO 키워드 | **기본 지원, 현행 동작** | 확장 설치·검증 필요 (품질 리스크) |
| EN 키워드 | 지원 (스테밍 없음) | **스테머 내장 (우위)** |
| ES 키워드 | 지원 (스테밍·악센트 정규화는 collation 의존) | **스테머 내장 (우위)** |
| KO/EN/ES 벡터(의미) | voyage-4 교차언어 — 동일 | voyage-4 교차언어 — 동일 |
| 교차언어 질의 (KO 질의→EN 문서) | 벡터 레그가 처리 — 동일 | 동일 |
| ES 원문 없는 상태의 ES 지원 | 벡터 교차언어 + AI 현지화로 가능 | 동일 |

- 하이브리드에서 키워드 레그의 역할은 "수치·코드·고유명사 정확 매칭"으로 좁혀지는데, 이 용도에는
  스테밍이 필요 없다($29.99, 쿠폰코드, "Beautizen"은 어형 변화가 없다). **활용형·유의어 매칭은
  벡터 레그의 일**이므로, B안의 EN/ES 스테머 우위는 하이브리드 구조에서 실효가 작다.
- 반면 KO 키워드 검색의 하향(B안)은 수치·고유명사 매칭에도 영향을 주는 실질 리스크다.
- **결론: 3개 언어 동시 지원 요구는 A안(MySQL+Qdrant)에 유리하게 작용한다.**

## 5. 종합 판정

| 평가 축 | 우위 | 비고 |
|---|---|---|
| 전환 비용·회귀 리스크 | **A안 압승** | 무전환 vs 1~2주+무테스트 회귀 검증 |
| 한국어 검색 | **A안** | 현행 유지 vs 다운그레이드 후 재구축 |
| EN/ES 키워드 스테밍 | B안 (실효 작음) | 하이브리드에선 벡터가 흡수 |
| 다국어 의미 검색 | 동률 | 임베딩 레이어 소관 |
| 멀티테넌트 벡터 필터 | **A안** | Qdrant 필터-인식 HNSW |
| 테넌트 격리 강제(RLS) | B안 | A안은 앱 레벨 보완 필요 |
| 데이터 정합성(원문↔벡터) | B안 | A안은 동기화 설계로 완화 |
| 벡터 운영 기능(양자화·멀티벡터·스냅샷) | **A안** | |
| 가역성·점진 도입 | **A안** | Qdrant는 파생 인덱스, 제거 가능 |

**권고: A안(MySQL + Qdrant).** 한국어 필수 요건, 무테스트 상태의 회귀 리스크, 당면 일정(KB 등록·
AI 품질)을 모두 고려하면 A안이 명확히 우세하다. B안의 고유 가치는 RLS 하나로 수렴하는데, 이는
DB 전환 없이도 앱 레벨 가드 강화(§6)로 상당 부분 커버되며, RLS를 필수 요건으로 격상할 경우에만
전환을 재검토한다(그 경우에도 시점은 런칭 전 — 선행 문서 참조).

## 6. A안 채택 시 보완 과제 (B안 대비 약점 메우기)

1. **동기화 정합성**: KB 쓰기 경로에서 MySQL 커밋 후 Qdrant upsert, 실패 시 재시도 큐(기존
   RabbitMQ 활용) + 주기 재색인 배치(MySQL `updated_at` 기준 diff)로 최종 일관성 보장.
   벡터 누락 시에도 FULLTEXT 폴백이 있어 서비스 영향은 "의미 검색 일시 저하"에 그침.
2. **테넌트 격리(RLS 대체)**: Qdrant 질의 빌더에 `tenant_id` payload 필터를 **필수 파라미터**로
   강제(필터 없는 질의가 컴파일되지 않는 시그니처), MySQL 측은 기존 로드맵(tenant-scope guard)
   대로 진행. 침투 테스트 항목에 교차 테넌트 검색 케이스 추가.
3. **EN/ES 키워드 보강(선택)**: 필요 시 Qdrant sparse 벡터(BM25 계열)를 언어별 토크나이저로
   추가해 키워드 레그까지 Qdrant 내부 하이브리드로 통합 — ngram의 라틴어 한계를 장기적으로 해소.
4. **백업 정책 문서화**: "Qdrant는 재색인으로 복원(백업 불요), MySQL만 백업"을 운영 문서에 명시.

## 7. 한 줄 요약
> 다국어(KO/EN/ES) 요구에서 의미 검색은 임베딩이 해결하므로 DB 선택과 무관하고, 남는 차이는
> "한국어 키워드"인데 이건 MySQL이 이미 이긴 게임이다. MySQL+Qdrant는 그 자산을 지키면서
> 전환 비용 0, 필터-인식 벡터 검색, 가역적 도입을 얻는다 — PostgreSQL의 고유 가치는 RLS 하나로
> 수렴하며, 그것만으로 전량 이관을 정당화하기 어렵다.
