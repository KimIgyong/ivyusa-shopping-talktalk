## 2. 설계에서 의도적으로 선택한 것

**이미 있는 신호를 주웠습니다.** `classifyIntent`는 매 턴 호출돼 `messages.intent`에 저장되고 있었지만, 주문 데이터 조회와 상품 그룹 선호에만 쓰였습니다. 새 모델 호출 없이 분기 하나가 늘었습니다. 이 저장소에서 같은 일을 한 전례가 있습니다 — 고객질문 통계(PLN-260804)도 버려지던 `classifyIntent` 결과를 주워 만들었습니다.

**의도 집합을 닫았습니다.** 자유 문자열일 때 같은 문장에 `agent_request`·`human_handoff`·`talk_to_agent`가 섞여 나와 분기 조건으로 쓸 수 없었습니다. 실측 신뢰도는 요청 3건 모두 **0.97~0.98**입니다.

**분류 실패는 신호가 아닙니다.** 폴백 라벨이 "자신 있는 `product_inquiry`"라, 파싱이 한 번 실패했다고 고객을 대기열에 넣을 수는 없습니다. 명시적 가드 + 테스트로 고정했습니다.

**문구 목록에 명사 단독을 넣지 않았습니다.** `상담원`·`agent`만으로 매칭하면 "상담원이 몇 명인가요?"가 이관됩니다. **요청 형태**만 담았습니다.

**판정은 검색 이전입니다.** 보내지 않을 답변에 모델 호출을 낭비할 이유가 없습니다.

**규칙은 신설하지 않고 수정했습니다.** 기존 규칙 5(부분 답변 시 상담원 제안)에 "연결을 약속하지 말 것"을 합쳐 **규칙 수를 10개로 유지**했습니다. 규칙이 늘수록 각 규칙의 구속력이 흐려집니다.

## 6. 검증 중 드러난 것

`상담원이 몇 명인가요?`와 `상담원분 친절하시네요`가 이관돼 처음엔 오탐으로 보였습니다. **사유를 확인하니 `low_confidence`** — 이번 변경이 아니라 기존 분기였습니다. 분류기는 두 문장을 `other`(0.90·0.94)로 정확히 구분했고, 문구 목록도 걸러냈습니다.

> **사유를 기록해 두지 않았다면 자기 변경을 의심하며 시간을 썼을 것입니다.** `handoff()`가 시스템 메시지에 `{"reason": …}`을 남기고 있던 덕분에 30초 만에 갈렸습니다.

여기서 새 사안이 나왔습니다(O5): 저신뢰 이관이 **"답을 모를 때"뿐 아니라 "답할 것이 없을 때"**(인사·감사·잡담)도 발동합니다. 칭찬 한마디에 상담원이 호출되는 것은 큐 낭비입니다.
