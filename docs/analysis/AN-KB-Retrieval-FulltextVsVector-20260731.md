# AN — KB 검색 구조 비교: MySQL FULLTEXT vs 벡터 임베딩

- 작성일: 2026-07-31
- 관련 문서: `AN-PolicyDoc-KB-Registration-20260731.md` (정책 문서 KB 등록 방안)
- 목적: 현재 ShopTalk의 MySQL FULLTEXT(ngram) 기반 검색과 벡터 임베딩 기반 검색(시맨틱 RAG)을
  비교 검토하고, AI 기반 채팅의 장기 발전 관점에서 어떤 구조가 적합한지 분석·권고

---

## 1. 현재 구조 (as-is)

| 항목 | 현재 구현 |
|---|---|
| 검색 엔진 | MySQL 8 FULLTEXT `ft_kb_title_content` (ngram parser), `MATCH … AGAINST (NATURAL LANGUAGE MODE)` — `rag.service.ts:60` |
| 임베딩 | 없음 — `embed()`는 `emb_{id}` 문자열만 기록 (`knowledge.service.ts:142`) |
| 청킹 | 없음 — `kb_documents` 1 row = 1 검색 단위 |
| 프롬프트 투입 | 상위 4건 × 각 400자 스니펫 (총 약 1,600자) |
| confidence | 검색 **건수** 기반 (`0.5 + 건수×0.12`, 1건=0.62) → 이관 임계 0.45와 비교 |
| 언어 | 검색은 저장 언어 그대로 매칭, `session.language`는 응답 생성에만 반영 |
| AI 어댑터 | `AiAdapter`에 `complete()`만 존재, `embed()` 인터페이스 없음 |

## 2. 방식별 비교

| 평가 기준 | MySQL FULLTEXT (ngram) | 벡터 임베딩 (시맨틱) | 비고 |
|---|---|---|---|
| 키워드·수치 정확 매칭 | **강함** ($29.99, 쿠폰코드, 정책 번호) | 약함 (수치·코드류에 취약) | 정책/CS 도메인에서 키워드 매칭은 여전히 중요 |
| 의미 기반 매칭 (패러프레이즈) | **불가** — "돈 언제 돌려받아요?" ↛ "환불 처리기간" | **강함** — 표현이 달라도 의미로 매칭 | 고객 질문은 정책 용어를 쓰지 않는 경우가 대부분 |
| 동의어·구어체·오타 | 불가/취약 | 강함 (오타는 중간) | CS 챗봇의 실질 질의 분포에 결정적 |
| 언어 교차 검색 (KO 질의→EN 문서) | **불가** — 언어별 문서 이중 관리 필요 | **가능** — 다국어 임베딩은 언어 무관 매칭 | ES 지원 시 격차 더 커짐(ES 원문 없이도 검색 가능) |
| 관련도 점수의 신뢰성 | 낮음 — 점수 해석 불가 → 현행 건수 기반 confidence | **높음** — 코사인 유사도 임계값으로 이관(escalation) 판단 가능 | 현행 "1건이면 0.62" 문제의 근본 해결책 |
| ngram 특성 | recall 과다(2-gram 우연 일치로 무관 문서 검색) → 잘못된 문서가 confidence를 올려 이관 억제 | 해당 없음 | 실사고 시나리오: 무관 정책 1건 매칭 → AI가 그 근거로 오답 |
| 인프라·운영 복잡도 | **최소** — 기존 MySQL만 사용 | 중간 — 임베딩 API 의존 + 벡터 저장/재임베딩 파이프라인 | MySQL 8은 VECTOR 타입 없음(9.0+부터) |
| 비용 | 0 | 소액 — KB 160건 임베딩은 무시 수준, 질의당 embed 1회 | Voyage 임베딩 단가는 토큰당 소액(하단 §4) |
| 지연시간 | ~수 ms | +100~300ms (임베딩 API 왕복) | 챗봇 UX에는 허용 범위 |
| 외부 의존성 | 없음 | 임베딩 API 장애 시 폴백 필요 | FULLTEXT를 폴백으로 유지하면 해소 |
| 데이터 규모 적합성 | 수백~수천 건에서 충분히 동작 | 수백 건이면 브루트포스 코사인으로 충분, 수만 건부터 ANN 인덱스 필요 | 현 규모(정책 ~160건)는 어느 쪽도 성능 문제 없음 |

### 소결
- **현 규모·현 데이터(정제된 정책 문서, "기본 답변" 포함)**에서는 FULLTEXT도 초기 운용이 가능하다.
  다만 품질 한계는 엔진이 아니라 **질의-문서 어휘 불일치**에서 오며, 이는 데이터를 늘려도 해결되지 않는다.
- **AI 챗봇의 장기 발전(자연어 질의 대응, 다국어, 상품 지식 확장, 신뢰도 기반 상담 이관) 관점에서는
  벡터 임베딩이 구조적으로 우월**하다. 단, 수치·코드 정확 매칭은 키워드 검색이 여전히 강하므로
  최종 형태는 **하이브리드(키워드 + 벡터 병합)**가 업계 표준이자 이 프로젝트에도 최적이다.

## 3. AI 채팅 발전 로드맵 관점의 판단

향후 예정된 확장과 각 구조의 적합도:

| 발전 방향 | FULLTEXT만 유지 시 | 벡터(하이브리드) 도입 시 |
|---|---|---|
| 정책 KB 등록(~160건, KR/EN) | 언어별 이중 등록 필수, 구어체 질의 미스 다수 | EN 단일 원문으로 KO/ES 질의 대응 가능 → KB 관리 절반 |
| ES(스페인어) 지원 | ES 원문 별도 작성·등록 필요 | 다국어 임베딩으로 원문 없이 검색 가능(응답은 AI 현지화) |
| 상품 지식자료(§11.2, 상품별 특징/성분/사용법) | 상품 수 × 항목 수만큼 키워드 관리 부담 급증 | 의미 검색으로 "지성 피부에 맞는 토너" 류 추천형 질의 대응 |
| 상담 이관 정확도 (POL/FR 이관 기준) | 건수 기반 confidence의 오탐/미탐 지속 | 유사도 임계값 기반 → "모르면 이관" 원칙(§0.4) 구현 가능 |
| Google Drive/게시판 소스 확장 | 비정형 문서에서 키워드 검색 품질 급락 | 청킹+임베딩 파이프라인으로 자연 확장 |

## 4. 벡터 도입 시 기술 선택지

### 4.1 임베딩 제공자
- **Anthropic은 자체 임베딩 API를 제공하지 않으며, 공식 문서에서 Voyage AI를 권장**한다.
  현재 스택(Anthropic 어댑터)과 병행 사용에 문제 없음.
- 권장 모델: **`voyage-4`** (범용·다국어 균형) / `voyage-4-lite`(저비용·저지연) / `voyage-4-large`(최고 품질).
  전 모델 32K 컨텍스트, 1024차원(256/512/2048 선택 가능), 다국어 최적화 — KO/EN/ES 교차 검색에 적합.
- 보조: **`rerank-2.5(-lite)`** 리랭커 — 하이브리드 검색 결과 상위권 재정렬(Phase 2).
  `voyage-context-4`(문서 문맥 반영 청크 임베딩)는 긴 문서 소스 확장 시 검토.
- 비용: 임베딩은 토큰 과금이며 KB 160건(약 40만 자) 전량 임베딩도 소액, 질의당 1회 호출 부담 미미.
  최신 단가는 Voyage pricing 페이지 확인.
- 구현 지점: `AiAdapter` 인터페이스에 `embed()` 추가 → `ai-gateway.service.ts` 라우팅(AI_FUNCTION에
  EMBEDDING 추가) → `stub.adapter`는 해시 기반 의사 벡터로 무키 개발 지원.

### 4.2 벡터 저장소 (규모별)
| 규모 | 권장 | 근거 |
|---|---|---|
| ~수천 건 (현재~중기) | **MySQL JSON 컬럼 + 앱 내 코사인 계산** | 1024차원 × 수천 건 브루트포스는 수 ms — 인프라 추가 0. Voyage 벡터는 정규화되어 dot product = cosine |
| 수만 건 이상 (장기) | MySQL 9.x `VECTOR` 타입, 또는 Redis(RediSearch 모듈) / pgvector / 전용 벡터DB | 상품·게시판·파일 소스 확장 시점에 결정. 현 Redis 이미지에는 RediSearch 미포함 주의 |

### 4.3 하이브리드 검색 설계 (목표 형태)
1. 질의 → (a) FULLTEXT 검색 + (b) 질의 임베딩 → 코사인 top-k
2. RRF(Reciprocal Rank Fusion)로 병합 → (선택) rerank-2.5로 상위 재정렬
3. **최고 유사도 점수를 confidence로 사용** → 임계 미달 시 §0.4 미확정 안내 + 상담 이관
4. FULLTEXT는 임베딩 API 장애 시 폴백으로 유지

## 5. 권고: 단계별 전환 (빅뱅 전환 비권장)

**Phase 0 — 현행 개선 (즉시, 무의존)**
- `docker/init-sql` FULLTEXT 인덱스 동기화(기존 보고서 참조), 스니펫 400자→800~1,000자 상향 및
  limit 조정 검토, LIKE 폴백 제거 여부 점검
- 정책 KB는 계획대로 FULLTEXT 기반으로 우선 등록·운영 (KR/EN 분리 등록)

**Phase 1 — 임베딩 병행 도입 (단기, 소규모 개발)**
- `kb_documents`에 `embedding` JSON 컬럼(+`embedding_model`) 추가, `AiAdapter.embed()` 구현(Voyage voyage-4)
- 등록/수정 시 임베딩 생성(현 `embed()` 스텁 대체), 검색은 하이브리드(RRF)로 전환
- **confidence를 유사도 기반으로 교체** — 이관 로직 품질 개선이 이 단계의 최대 효익
- KO/EN 이중 등록 유지하되, 교차 검색 검증 후 EN 단일화 여부 결정

**Phase 2 — 확장 (중장기)**
- 상품 지식자료·게시판·Drive 소스 도입 시: 청킹 파이프라인 + 전용 벡터 저장 + rerank-2.5 리랭킹
- `language` 컬럼·소스 status 반영 등 KB 스키마 정비 병행

### 리스크와 완화
| 리스크 | 완화 |
|---|---|
| 임베딩 API 장애/키 미설정 | FULLTEXT 폴백 유지, stub 어댑터로 개발환경 무키 동작 |
| 수치·코드 질의 정확도 저하 | 하이브리드(키워드 병합)로 상쇄 — 벡터 단독 전환 금지 |
| 모델 교체 시 전량 재임베딩 | `embedding_model` 컬럼으로 버전 관리, 160건 규모는 재임베딩 부담 미미 |
| 운영 복잡도 증가 | Phase 1은 벡터DB 없이 MySQL 내 저장 + 앱 내 계산으로 최소화 |

## 6. 결론
- **단기**: 현 FULLTEXT로 정책 KB 등록·운영 개시 가능. 단, 이는 "정제된 데이터 + 소규모"라는 조건부 판단.
- **장기(AI 챗봇 발전)**: 자연어 질의 매칭, 다국어(특히 ES), 상품 지식 확장, 유사도 기반 상담 이관을
  위해 **벡터 임베딩을 포함한 하이브리드 검색이 명확히 우월**하며, Voyage `voyage-4` + MySQL 내 벡터
  저장으로 시작하는 저비용 도입 경로가 존재한다. Phase 1(하이브리드 + 유사도 confidence)을
  정책 KB 등록 직후 착수 과제로 권고한다.
