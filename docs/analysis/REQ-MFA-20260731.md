# 관리자·고권한 계정 MFA(다중 인증) 도입 — 요구사항 분석

| 항목 | 내용 |
|---|---|
| 문서 ID | REQ-MFA-20260731 |
| 작성일 | 2026-07-31 |
| 발원 | REQ-Privacy-Control-Gap-20260731 #14 잔여분 — PLN-Privacy-Control-Gap §8 결정 D-2(별도 PLN) |
| 범위 | 시스템 관리자(super/admin) 및 테넌트 사용자(master/director 우선)의 로그인 2차 인증 |
| 제외 | 위젯 고객(세션·Shopify 연동 기반, 비밀번호 자체가 없음), SSO/WebAuthn(후속 검토) |

## 1. AS-IS

- 인증은 **비밀번호 단일 요소**: bcrypt cost 12, 로그인 rate limit, 임시 비밀번호 강제 변경,
  2026-07-31부터 강화된 비밀번호 정책(12자·복잡도·블록리스트·E1009, PR #41).
- **MFA/TOTP 코드 전무** — `totp|mfa|2fa|otpauth` 저장소 전체 0건(2026-07-31 재확인).
- JWT 발급(`auth.service.ts`): access+refresh, `passwordChangedAt` 기반 무효화.
  로그인 실패 감사(`auth.login_failed`), 성공 시 감사 기록 존재.
- 계정 모델이 **이원화**: 시스템 관리자(`admins`, super/admin)와 테넌트 사용자(`users`,
  rank master/director/manager/staff) — `Principal` union으로 코드에서 구분.

## 2. 위험 (도입 근거)

| 위험 | 영향 |
|---|---|
| 관리자 비밀번호 유출(피싱·재사용) | 시스템 관리자는 **전 테넌트** 고객 PII·감사 로그·자격증명 접근 가능 — 단일 요소로는 유출 = 즉시 침해 |
| 테넌트 마스터 계정 탈취 | 해당 테넌트 고객 전체 PII 열람, DSAR export 악용, 캠페인 발송 |
| 규정 | CCPA/GDPR 보안 조치 의무(합리적 보안), amoeba_privacy_compliance PRV 접근통제 계열 — 고권한 MFA는 사실상 표준 통제 |

## 3. TO-BE

1. **TOTP(RFC 6238) 기반 2차 인증**: 인증 앱(Google Authenticator 등) 등록, 로그인 시
   비밀번호 → 6자리 코드 검증의 2단계.
2. **적용 대상(제안)**: 시스템 관리자(super/admin) **필수**, 테넌트 master/director **필수**,
   manager/staff **선택**(본인 등록 시 적용). 필수 대상은 유예기간 내 등록 강제.
3. **복구 수단**: 일회용 복구 코드 10개(등록 시 1회 표시, 해시 저장). 시스템 관리자에 의한
   MFA 리셋(감사 기록 필수) — 관리자 본인 계정은 super가 리셋.
4. **감사**: 등록/검증 실패/비활성화/리셋 전부 `audit_logs`(PR #39 확장 스키마: result, ip,
   request_id 활용).
5. **보호 장치**: 코드 검증 rate limit(기존 login-rate-limit 패턴), TOTP 재사용 방지
   (동일 time-step 코드 1회), 시크릿 AES-256-GCM 저장(`crypto.util`).

## 5. 사용자 흐름

```
[로그인]  이메일+비밀번호 ─▶ 검증 OK ─▶ MFA 등록됨? ─예─▶ 코드 입력(6자리/복구코드)
                                        │                    │ 검증 OK ─▶ JWT 발급
                                        └─아니오─▶ (필수 대상 & 유예 경과) 등록 강제 화면
                                                   (그 외) JWT 발급(현행과 동일)
[등록]    설정 > 보안 ─▶ QR/수동키 표시 ─▶ 앱 등록 ─▶ 확인 코드 입력 ─▶ 활성화 + 복구코드 1회 표시
[분실]    복구 코드 로그인 ─▶ (권장) 재등록  /  관리자 리셋 ─▶ 다음 로그인 시 재등록
```

## 6. 제약

- 신규 백엔드 외부 의존성 최소화(TOTP는 Node `crypto` HMAC으로 구현 가능 — RFC 6238).
- QR 렌더링은 웹 콘솔(프런트) 책임 — 서버는 `otpauth://` URI만 제공.
- 이원화 계정 모델을 관통해야 함: `(actor_type, actor_id)` 축.
- staging `DB_SYNCHRONIZE=false`(2026-07-31~) — 스키마는 `sql/` 마이그레이션 선적용 필수.
- 기존 로그인 API 하위 호환: MFA 미등록 계정의 응답 형태는 변하지 않아야 함.
