## 0. 이 설계가 만드는 것

```
   고객 ──질문──▶ AI ──이관──▶ [대기] ──수락──▶ 상담원
                                                  │
   ┌──────────────────────────────────────────────┤
   │ S2 이 질문 지식에 있나?  → 답변 + 근거 문서    │   (읽기 전용, 고객에게 안 보임)
   │ S3 [고객에게 전달] ─────────────────────────▶ │ → 모더레이션 → 고객
   │ S4 [확정 지식으로 제안] → 관리자 승인 → KB 문서 → 다음 유사 질문에 인용
   │ S1 [AI에게 넘기기] ──────────────────────────┘ → status: agent → ai_active
   └──▶ 이후 고객 메시지는 AI가 다시 응답
```

**우선순위는 S1입니다.** 나머지는 개선이지만 S1은 결손 복구입니다 — 지금 스테이징에 **답 없는 고객 메시지 10건**이 그 문 하나가 없어서 쌓여 있습니다.

## 1. 단계별 계획

### S1 — AI 재위임 (요구 ①)

| 항목 | 설계 |
|---|---|
| API | `POST /agent/conversations/:id/handback` · `CONVERSATION_HANDLE` |
| 상태 전이 | `agent` → `ai_active` (**`ended` 아님** — 대화는 계속됨) |
| 배정 | 활성 배정을 `released`로, `conversations.agent_id = NULL` |
| 대화 기록 | 시스템 메시지 1건 + **고객 안내 문구**(3개 언어) |
| 안내 문구 | `tenant_ai_config.handoff_config` JSON에 `handbackNotice` 추가 — **마이그레이션 불필요**(기존 json 컬럼) |
| 감사 | `agent.handed_back` (대화 id, 직전 담당자) |
| 거부 조건 | `status !== 'agent'`이면 409 — 이미 AI가 답하고 있는 대화를 또 넘기는 건 무의미 |
| 핑퐁 대비 | 재위임 횟수를 감사 이력으로 집계해 대화 헤더에 `재위임 N회` 배지. **자동 억제는 넣지 않음**(근거 없이 라우팅을 바꾸지 않는다) |

기본 안내 문구(편집 가능):
> KO: "상담사 확인이 끝나 이후 문의는 AI 상담원이 도와드립니다. 다시 상담사 연결이 필요하시면 말씀해 주세요."

### S2 — 지식 조회 (요구 ②, D2 읽기 전용)

| 항목 | 설계 |
|---|---|
| API | `POST /agent/knowledge/ask` · **`CONVERSATION_HANDLE`** · 요청 `{ question, conversation_id? }` |
| 동작 | 기존 `RagService.answer`를 **읽기 전용**으로 호출 → `{ answer, citations[], confidence }` |
| 쓰기 | **없음** — 문서 생성·수정·삭제 경로를 일절 노출하지 않음 |
| 언어 | `conversation_id`가 있으면 그 세션 언어, 없으면 콘솔 언어 |
| 비용 방어 | 사용자당 **분당 10회** 제한(초과 시 429). 매 호출이 LLM 호출이므로 무제한은 위험 |
| 대화 오염 방지 | 조회 결과는 **대화에 저장하지 않음**. 미리보기 세션(`channel='preview'`)도 만들지 않음 — 통계·CJM에 섞이면 안 됨 |

> 기존 `/knowledge/ask`(MASTER·DIRECTOR)는 그대로 둡니다. 상담사에게 `KNOWLEDGE_SOURCE_MANAGE`를 주면 문서 생성·삭제까지 열리므로, 필요한 권한만 가진 별도 라우트를 만듭니다.

### S3 — 초안 전달 (요구 ③, D6 `rag`)

| 항목 | 설계 |
|---|---|
| 초안 생성 | S2와 **동일 엔드포인트** 재사용 — 질문 칸에 고객 마지막 메시지가 자동 채워짐 |
| 전달 | **기존 상담원 발신 경로**(`POST /agent/conversations/:id/message`) 재사용 → 모더레이션·감사·타이핑 표시가 전부 그대로 적용 |
| 두 가지 조작 | `[고객에게 전달]` 즉시 발송 / `[편집 후 전달]` 입력창에 채우기 |
| 표시 | 발송된 메시지는 **상담원 메시지**입니다. AI가 만든 문장이라도 사람이 보냈으므로 책임 주체가 상담원이라는 사실이 화면에 남아야 합니다 |
| 신규 백엔드 | **없음** — 초안 생성은 S2, 발송은 기존 라우트 |

### S4 — 확정 지식 제안·승인 (요구 ③-b, D3 승인형)

```
상담사              관리자(MASTER·DIRECTOR)
  │                        │
  ├─[확정 지식으로 제안]──▶ kb_answer_proposals (pending)
  │                        ├─ 승인 → KB 문서 생성 + 즉시 임베딩 → proposal.doc_id 연결
  │                        └─ 거절 → 사유 기록(제안자에게 표시)
```

| 항목 | 설계 |
|---|---|
| 신규 테이블 | `kb_answer_proposals` — `tenant_id, conversation_id, question, answer, status(pending/approved/rejected), proposed_by, decided_by, decided_at, reject_reason, document_id` |
| 제안 API | `POST /agent/knowledge/proposals` · `CONVERSATION_HANDLE` |
| 검토 API | `GET /knowledge/proposals` · `POST /knowledge/proposals/:id/{approve,reject}` · `KNOWLEDGE_SOURCE_MANAGE` |
| 승인 시 | 기존 문서 생성 경로 재사용 → `doc_group='counsel'`, `category` 기본 `faq`, `source_url = /live-chat?c=<id>` (PR #131과 동일한 출처 표기) |
| 중복 방지 | 같은 대화·같은 질문의 `pending` 제안이 있으면 409 |
| 우선순위 | **D5대로 가산점 없음** — 일반 문서와 동일하게 검색됨 |

## 3. 영향 범위 (side-impact)

| 영역 | 영향 | 조치 |
|---|---|---|
| **위젯** | 재위임 후에도 "상담사 연결 중" 표시가 남으면 고객이 혼란 | 위젯이 대화 상태를 폴링하므로 `ai_active` 복귀 시 대기 표시 해제되는지 **실측 검증**(V3) |
| **봇 침묵 규칙** | `agent_id`를 비우지 않으면 `waiting && agentId` 조건에 걸려 다음 이관에서 봇이 침묵 | 재위임 시 `agent_id = NULL` + 배정 released |
| **에스컬레이션** | 재위임 후 재요청은 기존 경로로 정상 동작해야 함 | 상태·배정을 초기화하므로 그대로 동작. V4로 검증 |
| **오프아워 이메일 회신** | `reply_channel='email'` 대화를 재위임하면 채널 해제 규칙과 충돌 가능 | 재위임 시 `reply_channel` 초기화 여부를 구현 시 확인(현행 해제는 상담사 근무 중일 때만) |
| **지식 충돌 스캔** | 승인된 문서가 상담 그룹에 추가 → 자동 검사 대상 | 정상 동작(상품 그룹만 제외 상태) |
| **통계** | 문서·카테고리 렌즈에 신규 문서 반영 | 별도 작업 없음 |
| **감사 로그** | `agent.handed_back`, `knowledge.proposal_*` 추가 | 기존 작업로그 화면에 자동 노출(`agent.*` 필터) |
| **비용** | 지식 조회가 LLM 호출 | 분당 10회/사용자 제한 + 조회 횟수 감사 |

## 5. 리스크와 대응

| # | 리스크 | 대응 |
|---|---|---|
| R1 | 재위임 ↔ 재이관 핑퐁 | 횟수 배지로 가시화. 자동 억제는 데이터를 보고 판단 |
| R2 | 초안이 실수로 즉시 발송 | 초안은 별도 패널에만 표시, 전달은 명시적 클릭. 초안 자체는 대화에 저장하지 않음 |
| R3 | 지식 조회 남용으로 비용 증가 | 사용자당 분당 10회 + 감사 기록 |
| R4 | 제안 적체(관리자가 안 봄) | `/knowledge` 상단에 **대기 건수 배지**, 7일 이상 미결 제안은 목록 상단 고정 |
| R5 | 승인된 답변이 기존 문서와 상충 | 기존 충돌 검출이 자동으로 잡음(상담 그룹) |
| R6 | 초안 생성 지연(RAG 실측 약 8초) | 진행 표시 + 취소. 대기 중에도 직접 입력 가능 |

## 6. 검증 계획 (TCR에서 상세화)

| # | 항목 | 기준 |
|---|---|---|
| V1 | 재위임 전이 | `agent` 대화에서 재위임 → `ai_active`, 배정 released, `agent_id` NULL, 시스템 메시지 1건 |
| V2 | **AI 응답 복귀** | 재위임 후 고객이 보낸 다음 메시지에 **AI가 답한다**(현재는 무응답) |
| V3 | 위젯 표시 | 재위임 후 "상담사 연결 중" 표시가 사라진다 |
| V4 | 재이관 | 재위임된 대화에서 고객이 다시 상담사 요청 → 대기열·알림 정상 |
| V5 | 지식 조회 권한 | **STAFF 계정**으로 조회 성공, 문서 생성·삭제는 여전히 403 |
| V6 | 조회 격리 | 조회가 대화·통계·CJM에 아무 기록도 남기지 않는다 |
| V7 | 초안 전달 | 전달된 메시지가 **상담원 메시지**로 저장되고 모더레이션을 통과한다 |
| V8 | 제안·승인 | 상담사 제안 → 관리자 승인 → 문서 생성·임베딩 → **다음 유사 질문에서 인용** |
| V9 | 거절 | 사유가 제안자 화면에 표시된다 |
| V10 | 방치분 정리 | 기존 `agent` 상태 7건을 재위임 또는 종료로 정리, 답 없는 고객 메시지 10건 해소 |

## 7. 구현 순서

```
S1 재위임  →  S2 지식 조회  →  S3 초안 전달  →  S4 제안·승인
  │              │                │                │
  스키마 없음    읽기 전용 라우트   신규 백엔드 0    SQL 선적용
  즉시 배포      +레이트리밋       (기존 경로 재사용)  +관리자 화면
```

- **S1은 단독 PR로 먼저** 내보냅니다 — 실피해가 있고, 나머지를 기다릴 이유가 없습니다
- S2·S3은 같은 패널이라 한 PR로 묶습니다
- S4는 마이그레이션이 있으므로 분리합니다
- 각 단계 후 스테이징 배포 → 실측 → TCR/RPT

## 8. 승인 요청

이 계획대로 진행할지 확인 부탁드립니다. 구현 전 확정이 필요한 잔여 사항 2건입니다.

1. **재위임 안내 문구** — 위 기본 문구로 시작할지, IVY 측 문구를 받을지 (콘솔에서 언제든 편집 가능하게 만듭니다)
2. **방치된 대화 7건** — S1 배포 후 제가 재위임으로 정리할지, 운영자가 직접 판단할지 (고객 메시지가 최대 5건까지 밀려 있어 답변 자체가 필요할 수 있습니다)
