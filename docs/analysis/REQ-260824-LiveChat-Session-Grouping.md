# REQ-260824 라이브챗 대화방 세션 그룹핑 (타임라인/프로젝트)

- 작성일: 2026-08-24
- 요청 유형: [요구사항] — 아메바톡의 타임라인/프로젝트(Bound Chat) 기능을 참조한 대화방 세션 그룹핑
- 참조: 아메바톡 V2 실구현(`~/Desktop/Site/ambTalkV2` bound-chat 모듈), ambManagement `REQ-260225-AmoebaTalk-Integration.md`

## 0. 요구사항 원문

세션은 다르지만 동일한 고객 또는 고객사의 대화를 하나의 그룹으로 모아서 보는 기능(아메바톡의 타임라인/프로젝트).
상담원이 동일 고객/고객사로 판단한 대화방세션을 묶어 **하나의 대화방에서** 볼 수 있다.
- **타임라인** = 개인 고객의 다른 세션들을 그룹핑. **프로젝트** = 동일 고객사 관련 당사자들의 대화를 묶음.
- 타임라인/프로젝트는 그룹핑 **구분자 역할만** 담당한다(동작 차이 없음).
- 그룹 대화방에서의 발신은 **수신 대상자를 선택해 1대1 송신만** 가능하다.
- 상담원/운영자가 묶을 세션을 선택하고, 성격에 따라 타임라인/프로젝트를 선택하고, **그룹 제목**을 작성한다.
- 필요 없어지면 **그룹 해제** 가능하다.

## 1. 참조: 아메바톡 Bound Chat의 실동작 (실코드 확인)

| 항목 | 아메바톡 실구현 | 본 기능에의 시사점 |
|---|---|---|
| 데이터 | `BoundChat { name, binding_type('timeline'\|'project'), conversation_ids JSON, recipients JSON, memo }` + History + Notes | 우리는 정규화 테이블 2개(그룹/멤버)로 — JSON 배열은 인덱스·정합성이 약함 |
| 구분자 | `getProject()`가 **문자 그대로 getTimeline() 위임** — 백엔드 동작 완전 동일, enum 주석도 "currently same" | "구분자 역할만"이라는 요구와 정확히 일치. 동작 분기 금지 |
| 생성 | 인박스에서 대화 다중 선택 → Bind Timeline / Make Project 다이얼로그(둘의 차이는 binding_type 리터럴뿐), 제목 입력. **수동 선택**(고객/회사 자동 매칭 아님) | 동일 UX 채택 |
| 병합 뷰 | 유사 대화방 객체를 만들어 같은 메시지 패널에 주입, 전 대화 시간순 스트림 + 메시지별 채널/고객 표기 | 동일. 우리는 `messages.id`가 전역 단조라 id 커서 하나로 병합 페이지네이션 가능 |
| 발신 | **컴포저 하드 비활성(읽기 전용)**. 수신자 선택 오버레이("전체 발송"+개별 체크)는 UI만 존재 — 백엔드 DTO에 recipients 없음, 팬아웃 코드 부재 | 아메바톡의 미구현 지점. 우리 요구는 이를 **1:1 단일 수신자 발신**으로 한정해 구현(브로드캐스트 없음) |
| 제약 | "최소 2개 대화가 묶여 있어야 함" 가드, 해제(unbind 일부/전체), bound/unbound 이력 | 최소 2 멤버 규칙 채택, 이력은 기존 audit_logs 재사용(신규 이력 테이블 불필요 — 적정기술) |
| 부가 | customer-journey 집계, AI 요약, mark-read, notes | 범위 밖(우리는 기존 브리핑·코멘트가 이미 있음 — 그룹 단위 확장은 후속) |

## 2. AS-IS (ShopTalk)

- **그룹핑 개념 전무.** `session_group`/`conversation_group`/merge 류 없음. 콘솔 목록은 단일 선택(`useState<string|null>`)이며 체크박스·벌크 툴바 없음.
- **동일 고객 판별 재료는 이미 있음**: `sessions.customer_id`(인덱스, 상담원이 `link-customer`로 재바인딩 가능), `customers.email_hash` 블라인드 인덱스, 플랫폼 고객 ID들(유니크). 단 **고객사(회사/조직) 엔티티는 전무** — B2B 조직 테이블 없음.
- **세션:대화방 = 1:N**: 대화 종료 후 고객이 다시 말하면 같은 세션에 **새 conversation이 생성**됨(`getOrCreateConversation`). 즉 "대화방(conversation)"을 묶으면 그 고객의 다음 대화는 그룹 밖에 생긴다.
- **병합 피드 기술 기반**: `messages.id`는 전역 AUTO_INCREMENT bigint — 콘솔 트랜스크립트가 이미 id 커서(`beforeId`)로 페이지네이션하며, 코드베이스가 `messages.id`를 전역 정렬 키로 취급(`MAX(id) GROUP BY conversation_id`, outbound_cursor).
- **발신 경로**: `AgentService.sendMessage(conversationId, agentId, tenantId, body, attachments)` — 테넌트 검증→동의 게이트(fail-closed)→중복 방지→모더레이션→저장→고객 통지. `ended` 상태 발신은 현재도 막지 않음. 세션→대화방 해석기는 `ChatService.findOpenConversation / findLatestConversation`이 기존재.
- 유사 선례: `chat_comments`가 conversation/session 2스코프 구조(REQ-260824 선행 건), `channel_threads`는 외부 스레드 1:1 바인딩(그룹 아님).

## 3. TO-BE — 구체화된 요구

### R1. 그룹 생성
- 라이브챗 목록에서 **선택 모드**로 전환해 세션(목록 행)을 2개 이상 체크 → [그룹 만들기] → 유형(타임라인/프로젝트) 선택 + 제목(필수, ≤100자) 입력 → 생성.
- **그룹핑 단위 = 세션(session_id)** (결정 D1): 행에서 세션을 취하며, 그 세션의 **모든 대화방(과거+미래)** 이 그룹 뷰에 포함된다. 대화 종료 후 같은 고객이 새 대화를 시작해도 자동으로 그룹에 나타남 — "동일 고객의 대화를 모아 본다"는 목적에 부합. (아메바톡은 conversation 스냅샷 방식이라 후속 대화가 빠짐 — 의도적 개선.)
- 같은 세션을 여러 그룹에 넣을 수 있다(타임라인과 프로젝트가 겹칠 수 있음). 같은 그룹 내 중복은 불가.
- 유형은 **구분자일 뿐** — 목록 필터·배지 표기 외 어떤 동작 차이도 없다(아메바톡과 동일 원칙). 고객사 마스터 데이터(회사 엔티티)는 만들지 않는다.

### R2. 그룹 대화방(병합 뷰)
- 그룹을 열면 멤버 세션들의 전체 메시지가 **시간순(전역 message id) 단일 스트림**으로 표시된다.
- 메시지마다 **발신 세션 식별 표기**(세션 별칭/고객명 + 채널 배지)가 붙어 어느 대화에서 온 메시지인지 구분된다.
- 위로 스크롤 시 과거 메시지 추가 로드(id 커서). 첨부·시스템 메시지 등 기존 트랜스크립트 표현 그대로.

### R3. 그룹에서의 발신 — 1:1 한정
- 컴포저 위에 **수신 대상 선택**(멤버 세션 목록에서 1명)이 있으며, 선택 없이는 발신 불가.
- 발신은 선택된 세션의 **열린 대화방**(없으면 최신 대화방)으로 기존 상담원 발신 경로 그대로 나간다 — 모더레이션·동의 게이트·감사·중복방지·고객 통지 전부 동일. **브로드캐스트/다중 발송 없음.**
- 수신 세션이 수신 전용 채널(SMS 릴레이)이면 해당 세션은 수신자로 선택 불가(현행 콘솔과 동일 규칙).

### R4. 그룹 관리
- 그룹 목록: 라이브챗 목록에 그룹 보기(유형 배지 + 제목 + 멤버 수 + 최근 메시지 시각).
- 멤버 추가/제거(제거로 2개 미만이 되면 거부 — 그룹 해제를 안내), 제목·유형 수정.
- **그룹 해제** = 그룹 삭제(멤버십 포함 하드 삭제, 리포 관례). 원 대화방/세션/메시지는 전혀 건드리지 않는다 — 그룹은 뷰일 뿐.
- 생성/멤버 변경/해제는 audit_logs에 기록(그룹 제목은 상담원 작성 텍스트이므로 메타데이터에 본문 미포함, id·건수만).

### R5. 권한·격리
- `CONVERSATION_HANDLE` 권한자(상담원/운영자) 전원이 자기 테넌트의 그룹을 보고 관리할 수 있다(작성자 독점 아님 — 인계 목적상 공유가 본질).
- 전 API tenant 술어 필수. 타 테넌트 세션을 멤버로 추가 시도 → 404. **위젯/고객에게는 그룹 존재가 절대 노출되지 않는다.**

## 4. 사용자 플로우

1. 상담원이 목록에서 [선택] 모드 → 동일 고객으로 판단되는 세션 3개 체크 → [그룹 만들기] → "타임라인" + 제목 "홍길동 님 반품 건" → 생성.
2. 그룹 탭에서 해당 그룹 클릭 → 세 세션의 대화가 하나의 타임라인으로 보임(메시지마다 세션·채널 표기).
3. 답장 필요 → 수신 대상에서 "홍길동(위젯)" 선택 → 메시지 발신 → 해당 세션의 열린 대화방으로 1:1 전송, 고객 위젯에 정상 수신.
4. 상담 종결 후 그룹이 더 필요 없으면 그룹 설정에서 [그룹 해제] → 그룹만 사라지고 대화들은 원래 목록에 그대로.

## 5. 제약·전제

- 멀티테넌시 MUST(읽기 경로 포함 — R2 보안결함의 교훈: 병합 조회의 모든 술어에 tenant 명시 + 테넌시 스펙).
- 스테이징 `DB_SYNCHRONIZE=false` → 신규 테이블 2종 SQL 선적용 + manifest + PR `## Migration`.
- i18n 6언어, 저장/삭제 토스트 MUST, 에러코드 E5056 블록부터 할당.
- 아메바톡 API 연동 아님 — 아메바톡은 UX/개념 참조일 뿐, 구현은 ShopTalk 자체 테이블/API.
- 범위 밖(후속 후보): 그룹 단위 AI 브리핑/코멘트, 고객사 마스터 데이터, 자동 그룹핑 제안(같은 customer_id 세션 감지), 그룹 읽음 처리, 다중 수신 발송.
